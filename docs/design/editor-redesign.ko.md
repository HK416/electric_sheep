# 에디터 재설계 — 전문가가 아닌 사람을 위한 작업 흐름 셸

`crates/es-editor`(계층 13; 패킷 M12/R4부터 그 헤드리스 절반은 `crates/es-editor-model`, 계층
12)와 이를 위해 필요한 작은 백엔드 변경에 대한 설계 노트. 스펙:
§23.1(에디터는 클라이언트), §23.3(실행 지켜보기), §13.1과 §13.3(루프와 고정된 평가),
§10(Evaluation IR), §28.9(전문가 점검), §1.4(오라클 우선), §1.5(컨텍스트 예산), §4.2(계층).
`editor-shell.md` §10–§16을 대체하지 않고 재배치한다.

상태: 2026-09-28 소유자와 합의(화면과 분할). **S1은 같은 날 구현됐다**(플랜 Y,
`docs/packets/M12/plan-y.md`, Y1–Y15; 리뷰 `docs/reviews/M12.md`);
`docs/packets/M12/YV-verification.md`의 실제 실행 전까지는 닫히지 않는다. **S2는 2026-09-29
구현됐다**(플랜 Z, `docs/packets/M13/plan-z.md`; 10절). S3–S6은 방향만 정해져 있고, 계획 전에
각자 설계를 한 번 더 거친다.

## 1. 왜

소유자 지시, 2026-09-28: 에디터 디자인을 완전히 바꾼다.

1. Unity나 Unreal처럼, 기반 지식이 없는 사람도 다가갈 수 있는 레이아웃.
2. 누구나 (비전 기반) 로봇 러닝을 수행할 수 있다.
3. 누구나 학습이 어떻게 되고 있는지 쉽게 본다.
4. 누구나 학습 결과를 쉽게 본다.

`editor-shell.md` §15는 이미 전문 용어를 쉬운 말로 바꿨다. 바꾸지 못한 것은 *모양*이다.
엔지니어용 탭 다섯 개, 그리고 레시피 경로를 묻는 실행 패널. 레시피가 있다는 것을 모르는
사람은 시작할 수 없다. 이 재설계는 모양을 바꾼다.

## 2. 소유자와 정한 것

| 질문 | 결정 |
|---|---|
| 초보자는 어디서 시작하나 | **둘 다**: 템플릿, 그리고 처음부터 만드는 프로젝트 |
| 새 과제의 시연은 어디서 오나 | **세 가지**: 동작 블록, 뷰포트 안 마우스/게임패드 원격조종, 보상만 정하는 RL (실물 리더 암은 제외) |
| 실행은 어디서 | **이 PC 먼저**; 원격 서버는 나중 하위 프로젝트 (이미 돌고 있는 주소에 붙기는 지금도 됨) |
| 기술 | **egui 유지**, 도킹 추가 (`egui_dock`); 웹 UI·Bevy 아님 |
| 전체 배치 | **단계 바 + 도킹** (B안): Unity식 패널에, 지금 어디이고 다음이 무엇인지 알려 주는 고정 단계 바 |
| 템플릿을 고른 뒤 | ①②가 완료된 채로 열리고, "학습 시작"이 한 번에 |
| 무작위화 UI | 강도 한 칸(약/보통/강) **과** 속성마다 🎲 |
| 시연을 대량으로 만드는 곳 | ③에서 학습과 함께 한 버튼으로; ②는 방법을 정하고 확인만 |
| 학습 중 뷰포트 | **중간 점검**: 체크포인트마다 시험 몇 번과 영상 (새 기능) |
| 결과 화면이 얼마나 이끄나 | 실패 원인마다 한 줄 조언, 그리고 **"실패 위주로 다시 학습"** |
| 분할 | S1 → S2 → S3 → S4 → S5 → S6, S1 먼저 |
| 크레이트 예산 | 에디터가 대신 들고 있던 코드를 원래 주인에게 돌려보냄 (6.1절) |

## 3. 화면 (모든 하위 프로젝트)

셸은 고정된 세 부분 — 위쪽 **단계 바**, **도크 영역**, 아래쪽 **상태 줄** — 과 창 전체를
쓰는 시작 화면으로 이루어진다.

```
[① 장면] [② 가르치기] [③ 학습 62%] [④ 평가] [⑤ 결과]          ⚠ 할 일 1개   [다음 ▶]
┌ 단계 패널 ───┐┌ 뷰포트 (항상 가운데) ──────────────┐┌ 인스펙터 / 요약 ───┐
│ 단계마다     ││                    ┌─────────────┐ ││ 단계마다 바뀜      │
│ 바뀜         ││                    │ 정책이 보는 │ ││                    │
│              ││                    │ 화면        │ ││                    │
└──────────────┘└────────────────────┴─────────────┘┘└────────────────────┘
 상태: 지금 하는 일 · 남은 시간 · 문제                           (콘솔, 접힘)
```

패널은 끌어서 다시 붙일 수 있다. 단계마다 기본 배치가 있고 사람이 바꾼 배치는 기억된다.
지금의 탭 다섯 개(설계 그래프, 결과 표, 관찰, 정책이 보는 것, 문제)는 **고급** 도크 탭으로
남는다 — 없어지는 기능은 없다.

**시작 화면.** "이 PC 점검" 줄(GPU, Python 학습 도구, MuJoCo, 선택 사항은 주황색);
"무엇을 해 볼까요?"와 템플릿 카드, 빈 프로젝트 카드; 최근 프로젝트, 각자 작은 단계 바와 함께
("③ 학습 중 62%", "✓ 완료 · 56%"); 그리고 파일 수준의 입구(파일 열기, 실행 결과 폴더 열기,
돌고 있는 실행에 연결). **끝까지 실제로 도는 카드만 보인다.** 템플릿이나 빈 프로젝트는 해당
하위 프로젝트가 들어올 때 나타난다.

**① 장면.** 왼쪽: 장면에 있는 것(로봇, 물체, 카메라, 조명)과 추가 목록(로봇: SO-101 또는
URDF/MJCF/USD 파일; 물체: 기본 도형 또는 메시 파일; 카메라; 조명). 가운데: 이동/회전/크기
기즈모와 물리 미리보기가 있는 3D 뷰포트, 그리고 모서리에 항상 **정책의 카메라가 보는 화면**
(정책 해상도 그대로). 오른쪽: 선택한 것의 속성과 🎲 토글, 성공·실패를 쓰는 **문장 편집기**
("[큐브]가 [상자] [안에] [1초] 동안 머물면 성공", "[36초] 안에 못 하면 실패"). 아래: 쉬운 말로
된 검사("카메라에 상자가 반만 보임").

**② 가르치기.** 단계 패널의 탭 세 개:
- *동작 블록*: 물체 기준 블록("[큐브] 위 [5cm]로", "그리퍼 닫기", "[상자] 위로"), 타임라인,
  미리보기, 🎲 "다른 위치로 다시".
- *직접 조종*: 손끝을 마우스나 게임패드로 끌어(IK) 녹화; 녹화마다 ①의 성공 조건으로 판정;
  목표 대비 개수("50개 중 11개 성공").
- *보상*: 무엇에 점수를 줄지 체크박스("성공하면 크게", "손이 [큐브]에 가까워질수록 조금씩"),
  그리고 배우는 방식 한 문장: 물체 위치를 아는 *선생*이 먼저 연습하고, 카메라만 보는 *학생*이
  선생을 따라 배운다.

셋 다 **"먼저 확인"**으로 끝난다. 시연기를 몇 번 돌려 얼마나 성공하는지 보여 주고, 실패마다
링크를 단다. 통과하기 전에는 ③이 잠긴다(§28.9 규칙 1을 쉬운 말로).

**③ 학습.** 버튼 하나가 *데이터 만들기 → (선생 연습) → 학습*을 돌린다. 진행률과 남은 시간이
있는 작업 칸; 가운데는 중간 점검(S2)과 정책이 보는 화면; 오른쪽은 **신호등**과 오차 곡선(곡선
위 점을 누르면 그 체크포인트의 점검 영상); 멈추기, "지금까지 배운 걸로 평가".

**④ 평가.** 같은 진행 화면; ⑤의 에피소드 타일이 끝나는 대로 채워진다. 끝나면 알림, 그리고
⑤로 이동.

**⑤ 결과.** 판정 카드(합격/불합격, "16번 중 9번", 합격 기준 줄마다 쉬운 말, 지난 실행보다
얼마나 변했는지 — 또는 "평가 조건이 달라 비교할 수 없어요"); 왜 실패했나와 원인마다 한 줄
조언; 재생기(바깥 카메라 / 정책의 눈 / 나란히, 타임라인에 사건 표시); 상황별 성공; 모든 시험
에피소드 타일; 자세한 지표와 해시는 접힘. 버튼: 정책 내보내기, 다시 실행, **실패 위주로 다시
학습**(S2).

## 4. 지금 코드에 있는 것과 없는 것

| 화면 | 있음 | 없음 |
|---|---|---|
| 셸 / 시작 | `es --check-deps`(텍스트); 최근 목록; 쉬운 이름표와 i18n | 도킹 크레이트(여기 egui 0.32.3에는 없음); `--check-deps --json`; **프로젝트라는 개념 자체** |
| ③ 학습 | 단계, 진행률, 총 걸음, ETA, 오차, 샘플 이미지, 체크포인트 이벤트 — 모두 전송로에 있음(`editor-shell.md` §13, §16) | 신호등 규칙; **중간 점검**(학습 중 평가는 돌지 않음) |
| ⑤ 결과 | 판정, 합격 기준, 18개 지표, CPU 3D 재생, 타임라인 표시 | **에피소드별 결과가 디스크에 없음**(전송로의 `cell.end`에만 있음); 어느 실패 조건이 발동했는지; failure set 없음 |
| ① 장면 | CPU 래스터 + 궤도 카메라(`replay_view`); `scene_to_mjcf`; 위치·색·조명·카메라 무작위화(§6.3, M11) | 선택과 기즈모; 장면에서 문서 다섯 개를 만드는 생성기(지금은 `#[ignore]`된 테스트 생성기뿐); 카메라 한 프레임 렌더 CLI; "머묾" 노드; 접촉 조건(`es-env`가 `GetContact`를 낮추지 않음) |
| ② 동작 블록 | `es loop cycle`의 전문가 점검 | 시연기는 `so101-pick-place`(`es-env/src/expert.rs`)와 SO-101 전용 닫힌 해 IK뿐; 데이터 기반 경유점 프로그램 없음 |
| ② 보상 | PPO(`[rl]`); `es loop collect --policy <번들> --frames`가 상태 정책의 롤아웃에서 이미지를 렌더 | 성공 에피소드만 거르기; 선생→학생 레시피; 충돌 감점 |
| ② 직접 조종 | — | 대화형 시뮬레이션 세션(MuJoCo는 Python 하위 프로세스로 돈다); 에디터에서 그 세션으로 가는 명령 채널 |

S1을 결정하는 사실 두 가지:

- **큐브 과제에서 카메라만 쓰는 경로가 합격한 적은 아직 없다.** *(2026-09-28 Y5 패킷이
  바로잡음; 이전 판은 반대로 적었다.)* M5/V19b의 held-out 15/16은 `observation-v19`
  (`07fad282…`, 커밋되지 않음) 위의 LeRobot ACT였다: 카메라 옆에 관절 각도 여섯 개 **와**
  시뮬레이터가 주는 `sim_cube_pose`로 된 13값 상태. M7의 IR 경로(U3, 0.5625)도 같은 특권 위치를
  읽는다. 카메라와 관절만의 경로(`observation-v8.toml`)는 V8, V11, V12에서 옛 하니스로 0–1/16이었고
  지금 하니스에서는 재 본 적이 없다. 템플릿이 어느 경로를 쓸지는 소유자의 선택이다(8절).
- **"실패 위주로 다시 학습"은 평가 시드로 학습하면 안 된다.** 다음 비교가 무의미해진다
  (§13.3). 실패한 교란 쪽으로 *학습* 무작위화를 넓히고 새 시드로 수집한다.

S2–S6에 이미 정한 방향(각자 설계를 한 번 더 거친다):

- **S2.** 중간 점검의 가장 싼 고리는 `checkpoint` 텔레메트리 이벤트다. 체크포인트 번들이 써진
  직후에 발생한다(`crates/es/src/cmd/train.rs`, `PolicyPack`). `es loop cycle`이 그때 학습기
  옆에서 짧은 평가를 돌리고, 학습기는 건드리지 않는다. 실패 위주 재학습은 새 cycle이다: 수집
  무작위화를 실패한 교란 종류 쪽으로 넓히고, 새 시드, 지난 실행의 `[init] policy`, 같은
  Evaluation IR.
- **S3.** 경유점 프로그램은 데이터 파일이다(시연기 레시피이지 IR이 아니다 — Task IR은 정책을
  갖지 않는다, §5.1 규칙 6). `ScriptedExpert` 옆의 구체 구조체가 실행하며 트레이트가 아니다
  (INV-17). 있는 IK로 SO-101부터; 그 해시는 데이터셋의 출처 기록에 들어간다.
- **S4.** 에디터는 장면 모델을 편집하고 `scene_to_mjcf`로 MJCF를 쓴다. `es project generate`
  명령이 장면과 선택을 문서 다섯 개로 바꾼다(CLI와 에디터가 공유). `es render` 명령이 선언된
  카메라의 한 프레임을 `es-render`로 렌더하므로, 미리보기는 실제 관찰이고 에디터는 여전히
  Vulkan 장치를 만들지 않는다. 문장 편집기는 `es-env`가 낮출 수 있는 것만 보여 준다.
  "1초 머묾"은 IR-D에 머묾 노드가 없으므로 "안에 있고 거의 멈춤"(데모의 정착 기준)으로
  컴파일한다. 낮추기는 여러 lane의 `GetJointState`, `Slice`, `GetBodyVelocity`를 얻는다
  (`es-ir`이 아니라 `es-env`). 접촉 조건은 `GetContact` 낮추기를 기다린다.
- **S5.** 부품은 있다: `[rl]`이 상태 선생을 학습하고, `es loop collect --policy 선생
  --frames`가 그 롤아웃에서 Task IR의 카메라를 렌더한다. 없는 것: 성공한 에피소드만 남기기,
  그리고 선생 → 수집 → 학생을 잇는 cycle.
- **S6.** 안전 평면을 켠 채(INV-12) 시뮬레이션을 한 걸음씩 진행하고, 에디터에서 손끝 목표를
  받아, `action_source = Human`으로 녹화하는 오래 사는 `es` 세션 프로세스. 텔레메트리 전송은
  지금 한 방향뿐이라 S6이 거꾸로 가는 채널을 더한다.

## 6. S1 상세

### 6.1 구조

**셸.** 단계 바(고정) + 도크 영역 + 상태 줄(고정); 시작 화면은 창 전체. 도크 탭: 뷰포트,
단계 패널(왼쪽, 단계별), 요약/인스펙터(오른쪽), 콘솔, 고급(설계 그래프, 정책이 보는 것, 문제,
원시 지표 표). 단계마다 기본 배치가 있고, 사람의 배치는 `eframe::Storage`에 다른 키들처럼
`recent.rs`에 적힌 키로 저장된다.

**도킹 크레이트.** egui 0.32와 워크스페이스 MSRV(1.85)를 지원하는 `egui_dock` 릴리스로
고정한다. 그 릴리스를 확인하는 것이 계획의 첫 작업이다. 없으면 egui 기본의 크기 조절·접기
가능한 `SidePanel`로 대신하고, 끌어서 다시 붙이기만 잃는다.

**코드 배치.** `editor-shell.md` §2의 규칙은 그대로다: **그리는 코드에서는 아무것도 결정하지
않는다.** 새 view-model, 각각 headless 테스트:

| 파일 | 맡는 것 |
|---|---|
| `model/workflow.rs` | 단계 바: 프로젝트, 디스크의 실행 결과, 실시간 실행으로부터 각 단계의 상태 |
| `model/project.rs` | 프로젝트 폴더 읽기, 실행 번호 매기기와 만들기 |
| `model/health.rs` | 신호등 |
| `model/results.rs` | 판정, 비교, 상황별 막대, 타일 |
| `model/home.rs` | 템플릿과 사용 가능 여부, `--check-deps --json` 읽기 |

`app.rs`(2,456줄)는 화면별로 `ui/`(shell, home, train, results, advanced)로 나뉘며 모두 그리기만
한다.

**에디터가 원래 주인 대신 들고 있던 코드는 주인에게 돌아간다.** `es-editor`는 §1.5의 기준
(코드 줄: 빈 줄, 주석만 있는 줄, 테스트 줄 제외; 경고 6,000, 한도 10,000)으로 지금 6,128줄이고
S1이 대략 2,000–2,500줄을 더하므로 한도가 이것을 강제하지는 않는다. 소유 위치를 바로잡고 중복을
없애기 위해 소유자가 선택했다:

- `replay_view`의 CPU 래스터라이저(그 음영은 `es_render::cpu::shade_lambert`를 다시 구현한
  것)는 `es-render`의 `raster` 모듈로; `es-env`(계층 9)가 필요한 궤적 자세 잡기는 에디터에 남는다;
- `run_view`의 끝난 실행 읽기는 그 파일들(`report.json`, `events.json`, `frames/`)을 쓰는
  `es-eval`로, 프레임 형식의 메모리 표현인 `Rgb8Image`와 함께. 사람이 읽는 문자열은 에디터에
  남는다.

계층은 바뀌지 않는다. (이 노트의 이전 판은 8,238줄이라고 적었다. 그것은 빈 줄과 주석 줄을 포함한
수이지 §1.5의 기준이 아니다.)

### 6.2 프로젝트와 템플릿

```
내-프로젝트/
  project.toml        # kind = "project", name, template = "cube-into-bin"
  runs/
    001/              # `es loop cycle --out runs/001`이 쓰는 그대로
      cycle.toml      # 이 실행이 쓴 레시피, 실행 직전에 에디터가 씀
      telemetry.txt   # 실시간 주소, 에디터를 다시 열어도 다시 붙을 수 있게
      loop.jsonl, collect/, train/, eval/, showcase/
    002/ ...
```

S1의 `project.toml`에는 이름과 템플릿 id만 있다. 직접 만든 문서를 위한 필드는 S3와 S4가
필요할 때 더한다.

**템플릿**은 저장소 루트의 `templates/<id>.toml`에 둔다: 이름과 설명(i18n 키), 로봇, 가르치는
방법, 그리고 **커밋된 문서의 경로** — `tests/fixtures/visible-learning/task.toml`,
`observation-v8.toml`, LeRobot ACT 학습 레시피, `evaluation-v8.toml` — 에 더해 새로 만드는
비전 경로 cycle 레시피(커밋된 `cycle.toml`은 특권 채널을 쓰는 IR 경로다). 문서는 복사하지 않고
가리킨다. 장면 경로는 해시 입력이다(`SceneRef::canonical`). 복사하면 아래쪽 해시가 전부 바뀌고,
템플릿은 더 이상 수치를 잰 그 문서가 아니게 된다. 그래서 `es`는 저장소 루트를 작업 폴더로
삼아 실행한다. 저장소를 받아 둔 상태에서만 되는 방식이며, 코드에 그 한계를 적은 `ponytail:`
주석을 단다(설치형 배포는 나중 항목).

### 6.3 단계 상태

`workflow.rs`는 (프로젝트, 디스크의 실행 결과, 실시간 실행)의 순수 함수다:

- 템플릿이면 ①과 ②는 **완료**이고 읽기 전용이다. ①은 CPU 래스터로 장면을 보여 주고, ②는
  요약을 보여 준다("동작 블록: SO-101 시연기, 준비됨").
- ③과 ④는 가장 최근 실행의 `loop.jsonl`과 실시간 단계로부터 *시작 전 / 진행 중(단계, %) /
  완료 / 실패(단계, 종료 코드) / 중단됨*. ③은 수집, 전문가 점검, 학습을, ④는 평가와 영상
  만들기를 덮는다.
- ⑤는 `eval/report.json`이 생기면 열린다. 실행 목록(001, 002, …)으로 다른 실행을 고른다.

**③의 시작 설정**은 두 가지다: 시연 개수, 학습 길이(짧게/보통/길게). 에디터는 템플릿의
레시피에 이 값을 덮어쓰고 train 절을 인라인으로 넣어 `runs/NNN/cycle.toml`을 쓰고 실행한다.

### 6.4 ③ / ④ 진행, 그리고 신호등

1. **시작**은 `cycle.toml`과 `telemetry.txt`를 쓴 뒤
   `es loop cycle --recipe runs/NNN/cycle.toml --out runs/NNN --telemetry 127.0.0.1:<빈 포트>`를
   `launch.rs`(`Kind::Cycle`)로 실행하고, attach-follows-launch가 붙는다.
2. **작업 칸**은 `stage.begin`/`stage.end`를 쉬운 이름으로 보여 준다. 진행률은 수집 중에는
   `episode.end` 개수 ÷ 시연 개수, 학습 중에는 걸음 ÷ `train.begin`의 총 걸음. 남은 시간은
   속도가 있는 곳에서만 보여 주고, **전체 실행의 ETA는 지어내지 않는다.**
3. **가운데**: 수집 중에는 방금 렌더된 시연 프레임과 "시범 성공 190 / 200"; 학습 중에는 정책이
   보는 샘플과 큰 오차 곡선. S2가 이것을 중간 점검으로 바꾼다.
4. **끝나면**: `ViewportCommand::RequestUserAttention`(egui 자체 기능, 의존성 없음)과 화면 안
   알림. 사람이 ③이나 ④에 있으면 ⑤로 이동한다.
5. **다시 열면**: `telemetry.txt`의 주소에 붙어 본다. 실패하면 실행은 *중단됨*이고
   [이어서](`--from <단계>`)와 [처음부터]가 나온다.

버튼: **멈추기**는 자식을 끝낸다. **지금까지 배운 걸로 평가**는 학습을 멈추고 이미 써진 가장
새 체크포인트로 `--from eval`을 돌린다. `--from`이 바뀐 `[eval] checkpoint`를 받아들이는지는
계획에서 실제로 돌려 확인하는 항목이다.

**신호등**(`health.rs`), 먼저 걸리는 규칙 하나:

| # | 표시 | 조건 | 안내 |
|---|---|---|---|
| 1 | 빨강 — *멈췄어요* | 자식 종료 코드 ≠ 0, 또는 `stage.end` 코드 ≠ 0 | 단계별 설명("시범이 너무 자주 실패했어요"), [콘솔] [다시 시작] |
| 2 | 빨강 — *망가졌어요* | 오차가 NaN이나 무한대 | 학습 속도를 낮춰 다시 |
| 3 | 주황 — *응답 없음* | 프로세스는 살아 있는데 T초 동안 텔레메트리가 없음 | 기다리거나 멈추기 |
| 4 | 주황 — *느려요* | 워밍업 뒤 초당 샘플 수가 그 실행 중앙값의 1/3 미만 | 다른 GPU 프로그램 확인 |
| 5 | 주황 — *배움이 멈췄어요* | 한 구간 동안 오차가 줄지 않음 | 데이터 늘리기 |
| 6 | 회색 — *시작하는 중* | 진행 프레임이 아직 하나도 오지 않았고 T초가 지나지 않음 | — |
| 7 | 초록 — *잘 되고 있어요* | 위에 걸리는 것 없음 | — |

T와 규칙 5의 구간은 **추측하지 않는다.** 실제 합격 확인 실행의 곡선을 녹화해 두고, "성공한
실행을 다시 틀면 처음부터 끝까지 초록"을 임계값이 통과해야 하는 테스트로 삼는다. 각 규칙의
발동은 합성 데이터로 덮는다. GPU 메모리는 지금 학습 전송로에 없으므로 있을 때만 보여 준다.

### 6.5 ⑤ 결과

`runs/NNN/eval/`에서 `report.json`, 새 `episodes.json`, `frames/`, `traj/*.estraj`를 읽는다.

- **판정.** 합격/불합격은 `report.passed`. 큰 숫자는 전체 에피소드 중 성공 수("16번 중 9번").
  그 아래 합격 기준 줄마다 쉬운 말과 ✓/✗, `labels.rs`를 거친다.
- **비교.** 프로젝트의 지난 실행과는 `evaluation_hash`가 같을 때만. 다르면 "평가 조건이 달라
  비교할 수 없어요"라고만 하고 숫자는 없다(§13.3). [다른 실행과 비교]로 다른 것을 고른다.
- **왜 실패했나.** `episodes.json`의 종료 사유와 실패 종류를 쉬운 말로: timeout → *시간 안에 못
  끝냄*; `safety_violation` → *안전 한계에 닿음*; 대체 동작 → *안전장치가 멈춤*;
  `nan_detected`/`diverged` → *시뮬레이션이 불안정*; `chunk_underrun` → *동작이 끊김*;
  `deadline_miss` → *반응이 늦음*; 실패 조건 → *실패 조건에 걸림*. 대응은 `FailureKind`와 종료
  종류 전체에 대해 빠짐없고 와일드카드 가지가 없다(`labels.rs`의 규칙). 원인마다 문자열표의 한
  줄 조언. 과제 맞춤 원인("큐브를 떨어뜨림")은 S2.
- **상황별.** `episodes.json`을 suite로 묶어 "성공 / 에피소드" 막대. 이름은 작성자가 정한 suite
  이름이 아니라 suite의 **교란 종류**로 만든다 — 열두 개 `PerturbationKind` 전체에 대한 빠짐없는
  대응(교란이 없으면 *기본*), 여러 개면 이어 붙임. 작성자의 이름은 마우스를 올리면 보인다.
- **타일과 재생기.** 모든 에피소드를 타일로(전체 / 성공 / 실패), 마지막으로 녹화된 프레임이
  썸네일. 타일은 가운데 뷰포트에서 기존 재생(6.1절에 따라 `es-render`로 옮긴 것)과 타임라인
  표시로 재생된다. 카메라: 바깥(궤도) / 정책의 눈(녹화 프레임) / 나란히; 속도 0.5× / 1× / 2×.
- **접힘**: 18개 지표(지금의 결과 표)와 그 실행의 설정·해시.
- **버튼**: 정책 내보내기(저장 대화상자로 `.esb` 복사); 다시 실행(같은 설정으로 ③). *실패
  위주로 다시 학습*은 S2에서 합류한다.

### 6.6 백엔드 변경 (모두 작음)

- `es --check-deps --json`: 지금 텍스트와 같은 사실을 기계가 읽는 형태로, 시작 화면용.
- `es eval run`(따라서 cycle의 평가 단계)이 `episodes.json`을 쓴다: 에피소드마다 suite, 셀,
  시드, 종료 사유, 실패 종류별 개수, 안전 평면 위반과 대체 동작, 걸음 수, 녹화했다면 프레임
  폴더와 궤적 경로.
- 큐브 템플릿의 비전 경로 cycle 레시피와 `templates/cube-into-bin.toml`.
- `es policy init`: cycle의 `[collect] policy`가 가리키는 번들을 커밋된 문서로 만든다. 새로 받은
  저장소에는 지금 그것을 만들 방법이 없고(`untrained.esb`는 테스트 헬퍼와 서버 산출물에서 왔다),
  수집 단계는 정책이 전혀 행동하지 않을 때에도 그 Deployment IR — 시연기가 그 아래에서 도는
  안전 평면 — 때문에 그것이 필요하다.

### 6.7 오류

어떤 경로도 에디터를 죽이지 않는다. 무슨 일인지 쉬운 말로 말하고 다음 행동을 내민다.

| 상황 | 표시 |
|---|---|
| `es` 실행 파일 없음 | PC 점검 줄에 빨강, `es_binary()`의 이유와 함께 |
| Python / LeRobot / MuJoCo 없음 | 템플릿 카드 비활성, "필요: LeRobot 학습 도구"와 설치 방법 |
| 깨진 `project.toml` | 알림; 시작 화면에 머묾 |
| 실행이 죽었거나 실행 중에 에디터를 닫음 | *중단됨*, [이어서] / [처음부터] |
| 평가가 코드 0으로 끝났는데 `report.json`이 없음 | 빨강 — "결과 파일이 없어요"(성공으로 취급하지 않음) |
| `episodes.json`이 없는 옛 실행 | ⑤가 타일을 숨기고, 막대는 `report.json`의 suite 지표로 그리고, 이유를 말함 |

### 6.8 오라클 (§1.4)

모두 `cargo xtask ci` 아래:

- **Headless model 테스트**: `workflow`(상태 표 전체); `health`(합성 데이터로 각 규칙 발동;
  **녹화한 성공 실행을 다시 틀면 처음부터 끝까지 초록**); `results`(판정, 비교, 해시 불일치,
  막대, 타일, 옛 실행 대체 표시); `home`(`--check-deps --json` 해석, 템플릿 사용 가능 여부);
  `project`(생성, 읽기, 실행 번호).
- **`episodes.json`**: 에피소드 개수가 report의 `n_episodes`와 같고, **성공 수 ÷ 에피소드 수가

## 7. 이 설계가 지키는 것

- **에디터는 학습을 호스팅하지 않는다**(§23.1): 모든 실행은 에디터가 붙는 `es` 자식이다.

- **새 확장 지점 없음**(INV-17): S3의 경유점 시연기는 구체 구조체다.
- **문자열표와 이름표 규칙**(`editor-shell.md` §15)이 새 단어 전부에 적용된다.

  *오류로 멈춤*이 **아니다**: `es loop cycle`은 합격 기준을 넘지 못하면 eval(그리고 eval의
  코드를 되풀이하는 showcase)을 1로 끝내고, ④는 회색으로 "끝남 - 시험 불합격"을 보이며 ⑤가
  열린다.
- **실행 폴더:** `write_run`은 `runs/NNN`을 배타적으로 만들며, 실행이 도는 동안은 거부된다.

## 10. 구현된 S2 (플랜 Z, 2026-09-29)

플랜 Z(`docs/packets/M13/plan-z.md`, Z1–Z6)는 첫 실제 실행이 방향을 바꾼 뒤 S2를 구현했다: 큐브
작업은 실패 조건을 선언하지 않으므로 실패한 시도는 모두 시간 초과로 끝나고, "어느 조건이
걸렸는가"는 아무것도 가리키지 않는다. 5절의 방향과 다른 점은 둘이다: 실패 원인은 물체가 간
곳에서 읽고, 다시 모으기는 무작위화를 넓히는 대신 Evaluation IR 자신의 교란 아래에서 한다(새
문서 필드 없음).

- **체크포인트 점검(Z1).** 사이클의 선택적 `[eval.preview]`(`episodes` 4, `suite`는 Evaluation
  IR의 첫 스위트, `frames` 켬). 체크포인트 번들이 생기자마자 — IR·RL 경로는 표시마다 `es policy
  pack` 뒤, LeRobot 경로는 `lerobot-train`이 `checkpoints/<NNNNNN>/pretrained_model`을 다 쓴
  뒤 — `es loop cycle`이 파생된 Evaluation IR(그 스위트, 처음 N개 시드, acceptance 없음)로 `es
  eval run --jobs 1`을 자식으로 돌려 `<run>/preview/<step>/`에 쓴다. 한 번에 하나씩, 학습기를
  막지 않는다. 끝난 점검마다 한 행이 `<run>/preview/index.jsonl`에 간다 — 원장이 아니므로 어떤
  해시 입력도 움직이지 않는다 — 그리고 스트림 1이 `preview.begin` / `preview.end`를 나른다.
  사이클은 자기 평가 전에 마지막 점검을 기다린다. 에디터가 쓰는 모든 실행에 `[eval.preview]`가
  있다(템플릿의 사이클에 없으면 `write_run`이 넣는다). 커밋된 사이클과 그 골든은 그대로다.
- **③이 보여 준다(Z5a).** 걸음 수 칩 한 줄, 보이는 점검의 제목("점검: 1번 성공 / 전체 4번 —
  1000걸음 때"), 그리고 그 첫 실패를 재생하는 시도 재생기 — Z5a부터 ⑤와 공유(`ui/player.rs`).
  손실 곡선 위의 점이 점검을 표시하고, 누르면 그 점검을 고른다. 점검은 아무것도 판정하지
  않는다(§13.3): 그 수치는 acceptance와 비교되지 않는다.
- **왜 실패했는가, 물체가 간 곳에서(Z4a).** 템플릿의 `[outcome]`(`object`, `target` 접두,
  `lift_m`, 두 언어의 두 이름)이 시간 초과로 끝난 시도를 그 `.estraj`로 나눈다: 마지막에 목표
  영역 안 → *너무 늦게 들어감*; 아니면 시작 위치보다 `lift_m` 위로 한 번도 오르지 않음 → *들어
  올리지 못함*; 아니면 *들어 올렸지만 밖에 남음*. 목표 영역은 그 접두의 지오메트리에 대해
  렌더러가 만든 삼각형의 상자이고, 장면의 자세 기준이다. 궤적이 없는 시도는 분류가 없고, 다른
  것이 끝낸 실패는 자기 원인을 유지한다. 후속 R4(첫 실제 실행에서 발견: 큐브는 1,800틱 중
  451틱에 통 안에 들어갔지만 집게가 0.09 rad 넘게 열린 적이 없었다): 선택 항목 `[outcome]
  release = { joint, above }`가 있으면 안에 있는 시도 가운데 물체가 마지막으로 들어간 뒤 그
  관절(궤적의 `qpos`, 장면의 관절 순서로 찾은 위치)이 `above`를 한 번도 넘지 않은 것은 *안에
  넣었지만 놓지 않음*이고, *너무 늦게 들어감*보다 먼저 묻는다. 두 큐브 템플릿은 Task IR 자신의
  성공 조건 문턱 `gripper` 0.85를 쓴다.
- **교란 아래 수집(Z2).** `es loop collect --perturb <evaluation.toml> --suites a,b`는 에피소드
  i를 `suites[i % n]` 아래에서, `es eval run`이 쓰는 같은 `PerturbationPlan`으로, 같은 Safety
  Plane 아래에서 돌린다. 에피소드별 시드 `seed..seed+N`은 Evaluation IR의 모든 시드를 피해야
  한다(이름을 대며 거부, §13.3). `meta/perturbations.jsonl`이 에피소드마다 스위트를 적는다.
  관측 나이를 배포의 `stale_observation` 감시 한도 너머로 늘릴 수 있는 스위트는 거부된다 —
  수집기는 그 나이를 plane에 넘길 수 없기 때문이다.
- **"다시" 사이클(Z3).** `[collect] perturb = { config, suites }`, `[collect] merge = [roots]`
  (합치기 단계: `es loop distill`로 `collect/merged`에, 전부 학습용, 프레임 타일은 합친 순서로
  배치; 합친 루트를 학습한다), `[train] init`(IR·RL 경로: `[init] policy`; LeRobot 경로:
  `--policy.path`).
- **"실패 위주로 다시 학습"(Z4b, 리뷰 후속 R1).** ⑤의 버튼은 다음 실행을 ③의 시작 패널에
  준비한다 — 무엇을 연습할지 쉬운 말로, 시범 수와 길이는 여전히 바꿀 수 있고, 취소도 있다 — 그리고
  시작을 누르면 쓰고 시작한다: `perturb`는 이전 실행의 `[eval] config`와, 수집기가 실현할 수 있는
  스위트 중 성공률이 가장 낮은 것들(동률이면 모두; 후속 R2는 관측 나이를 `stale_observation` 감시
  한도 너머로 늘릴 수 있는 스위트를 `es loop collect`와 같은 `es_eval::perturb::unseen_age` 검사로
  뺀다); 시드는 프로젝트의
  모든 실행 뒤에서 시작해 평가의 시드를 건너뛴다; `merge`는 사슬의 이전 데이터셋 루트 전부
  (`collect/merged`는 절대 아님); `init`은 이전 평가가 판정한 체크포인트로, 원장의
  `policy_hash`에서 찾는다. 같은 Evaluation IR이 새 실행을 판정하므로 두 보고서를 비교할 수
  있다. 실행에 설정 파일이 없거나, 모은 것이 없거나, 평가나 실패가 없거나, 수집기가 실현할 수
  있는 실패 스위트가 없거나, 체크포인트가 사라졌으면 버튼은 이유와 함께 꺼진다.
- **실패 원인을 정직하게 세기(후속 R3).** Safety Plane의 걸음 카운터(`fallback`, `violation.*`)는
  시도 걸음의 1 % 이상을 차지할 때만 그 시도의 원인이 된다: 제어 주기 하나의 선언된 지연이 있으면
  모든 시도가 — 성공한 것도 — 폴백 한 걸음과 청크 부족 한 번으로 시작하는데, 첫 실제 실행에서
  이것이 ⑤ 맨 위에 "안전 장치가 멈춰 세움"과 "동작이 끊김 — 더 빠른 컴퓨터를 쓰면"을 올려놓았다.
- **S2 이후 예산:** `es-editor-model` 6,582줄(목표 6,000 초과, 상한 아래), `es-editor` 3,842,
  `es` 6,543.

- **시범 숫자의 출처는 하나.** `--expert so101-pick-place`는 커밋된 프로그램
  `templates/teach/so101-pick-place.toml`이 되고, 컴파일해 넣는다. 리팩터링은 그 전에 기록한 오늘의
  청크열 골든으로, 시뮬레이터가 필요 없는 완벽한 추종자 상태열에서 비트 단위로 증명한다. 사람이
  바꿀 일이 아닌 것 — 관절 허용 오차, 집게의 열림·닫힘 각도, Deployment IR의 봉투가 허용하는 속도 —
  은 코드에 남으므로 파일은 *무엇을* 할지만 말한다.
- **장소는 정확히 해석된다:** 그 점은 해당 스템의 가장 낮은 지오메트리(통의 바닥)의 세계 좌표
  위치이며, `demo_cfg`의 리터럴 통 중심을 재현한다.
- **사람의 사본.** `Project::create`는 템플릿의 프로그램을 프로젝트로 복사하고, `write_run`은
  `[collect] expert`를 그것으로 향하게 하며, 원장은 프로그램의 blake3를 `expert` 이름 옆에
  기록한다(새 출처 정보, 해시는 움직이지 않는다).
- **S3에서 만든 ②.** 쉬운 말의 블록 목록. Task IR이 그릴 수 있는 어떤 물체 위치에서 닿지 못하는
  블록에는 표시가 붙는다. 선택한 블록의 인스펙터. "한 번 해 보기"(파생된 시드 하나짜리 Evaluation
  IR로 시범 에피소드 하나를 `<project>/try/<n>/`에 만들고, 공유 재생기에서 결과 분류와 함께 재생)와
  "🎲 다른 위치로"(다음 시드). 경고는 해 보기를 막지 않는다: 시범기가 닿지 못하는 블록을 이름을 대며
  실패시키고(스펙 17.2), 해 보기가 보여 주는 것이 바로 그것이다.
- **S3가 하지 않는 것:** 시범의 타임라인(재생기의 타임라인이 대신한다), 손목을 돌리는 블록(롤은
  0으로 유지하며, 도구의 가로 오프셋이 일정하게 유지된다), SO-101 이외의 로봇(`so101_ik`는 그
  형태에 맞는 닫힌 형식이다), 뷰포트에서 목표 끌기(S4의 기즈모).
