# Learning IR → PyTorch lowering

Review class **C** (spec 1.3): this note is the artifact, the code in `crates/es-policy` is
downstream of it. Spec: spec 8.1, spec 8.3, spec 8.4, spec 8.5, spec 8.7, spec 8.8, spec 8.9,
spec 1.4, spec 2.4.

PyTorch is the **reference oracle** for the Learning IR (spec 1.4): the same `LearningGraph`
run in PyTorch is the ground truth that every other `PolicyRuntime` is judged against. So this
lowering is not a deployment path. It is deliberately the most literal, most boring translation
available — a `nn.Module` per node, one forward line per node, no fusion, no reordering.

## 1. What is lowered, and what is not

Spec 8.7 splits the graph three ways:

| part | spec 8.7 target | here |
|---|---|---|
| encoder front end (preprocessing) | Slang kernels, GPU-resident | already Observation IR's; `es-compile` owns the CPU reference |
| `PolicyHandle` forward pass | `PolicyRuntime` | this note |
| `ActionChunker` / `Normalizer` / blend | deterministic CPU code, identical sim and real | **also lowered here** |

The third row is a deliberate departure and the reason for it is spec 8.9: the oracle has to
produce the same tensor the deployment path produces, end to end. If the chunker and the
unnormalizer lived outside the lowered module, the tier-4 comparison would compare a prefix of
the pipeline and silently exempt exactly the two nodes most likely to disagree (an off-by-one
in `execute_chunk`, a transposed mean/std). They are pure and deterministic in both places, so
lowering them costs one slice and one affine expression.

The rule stated positively: **`lower_to_torch` covers the whole `LearningGraph`, boundary to
boundary.** `PolicyRuntime::infer` receives already-preprocessed tensors named per
`PolicyContract::inputs` and returns the graph's declared outputs. The runtime itself adds
nothing — no normalization, no chunking, no dtype policy. That is spec 2.4's "the IR owns
pre/post-processing, not the runtime" (`INV-15`), and it is why `TorchRuntime` has no knobs.

## 2. Generated file shape

`lower_to_torch` emits one complete, self-contained Python file:

```python
# generated by es-policy; do not edit
import torch
import torch.nn as nn
# (import torchvision  -- only when a VisionEncoder is present)

class EsPolicy(nn.Module):
    def __init__(self):
        super().__init__()
        self.n1 = nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Linear(8, 8))
        self.n4 = nn.Linear(8, 6)

    def forward(self, **inputs):
        v1_out = self.n1(inputs["joint_state"])
        v4_chunk = self.n4(v1_out).reshape(3, 2)
        v5_actions = v4_chunk[:3]
        return {"actions": v5_actions}
```

- The member for node `NodeId(k)` is always `self.n<k>`. A node with no parameters emits no
  member.
- The value of output port `p` of node `k` is always the local `v<k>_<p>`.
- Nodes are emitted in `Graph::topo_order()` order, which is deterministic and independent of
  edge order (it pops from a `BTreeSet`). Every other collection in the lowering is a
  `BTreeMap` or a `Vec` built in that order, so **the same graph produces byte-identical
  source**. That is a unit test, not an aspiration: `lowering_hash = blake3("es.lowering.v1" ||
  source)` and two lowerings of the same graph must agree.
- No batch axis. Spec 5.2 gives the Learning IR free batch semantics and spec 5.4 keeps the
  batch axis out of every declared shape; the generated module is written for one sample and
  torch's broadcasting makes a leading batch axis work anyway for the `Linear` path. The
  reshape in `PolicyHead` uses `.reshape(H, A)`, which pins the no-batch convention. A batched
  lowering is a later packet, not a flag.

## 3. Node table

Layouts are row-major, dtype `f32` throughout (`PolicyContract::runtime.dtype`; anything else
is rejected). Initialisation is irrelevant — every parameter is overwritten from the
safetensors file before the first `forward`, and a missing key is an error, never a default.

| `LearningNode` | PyTorch | forward line | weights |
|---|---|---|---|
| `StateEncoder { Identity }` | — | `v = x` | none |
| `StateEncoder { Mlp { hidden } }` | `nn.Sequential(Linear, ReLU, …, Linear)` | `v = self.nk(x)` | exact |
| `VisionEncoder { ResNet18/34 }` | `torchvision.models.resnet{18,34}` with `fc = Linear(512, out_dim)` | `v = self.nk(x)` | prefix |
| `VisionEncoder { other }` | — | — | `Unsupported` |
| `LanguageEncoder` | — | — | `Unsupported` |
| `Fusion { Concat }` | `Linear(Σin, out_dim)`, or nothing when `Σin == out_dim` | `v = self.nk(torch.cat([a, b], dim=-1))` | exact / none |
| `Fusion { TokenConcat }` | — | `v = torch.cat([a, b], dim=-2)` | none |
| `Fusion { CrossAttention, FiLm, AdaLn }` | — | — | `Unsupported` |
| `TemporalEncoder { None }` | — | `v = x` | none |
| `TemporalEncoder { Transformer }` | `nn.TransformerEncoder(nn.TransformerEncoderLayer(d_model=out_dim, nhead=8, batch_first=True), 1)` | `v = self.nk(x)` | prefix |
| `TemporalEncoder { TemporalConv, Gru, Mamba }` | — | — | `Unsupported` |
| `PolicyHead { Regression }` | `Linear(in, horizon * action_dim)` | `v = self.nk(x).reshape(H, A)` | exact |
| `PolicyHead { Diffusion, FlowMatching, Discrete, Energy }` | — | — | `Unsupported` |
| `PolicyBundle` | — | — | `Unsupported` |
| `ActionChunker` | — | `v = x[:K]` | none |
| `Normalizer { MeanStd / MinMax }` | `register_buffer(..., persistent=False)` | `v = (x - mean) / std` or its inverse | none |
| `Normalizer { Dataset }` | — | — | `Unsupported` |

Notes on the entries that are not obvious:

- **`Fusion { Concat }`.** Spec 8.3 gives fusion an `out_dim`, and concatenation alone cannot
  honour it. The rule is: concatenate on the last axis, then project with a `Linear` **iff**
  the concatenated width differs from `out_dim`. Conditional weights are a hazard, so the rule
  is stated by shape and not by a flag, and the projection's keys appear in `weight_keys` only
  when it exists.
- **`TemporalEncoder { Transformer }` on a pooled feature.** When `token_count == 0` the port is
  `[dim]`, which has no token axis. The lowering inserts `unsqueeze(0)` before the encoder and
  `squeeze(0)` after it, i.e. a one-token sequence. `nhead = 8` is fixed; spec 8.3's node
  parameters do not carry it, so it is a lowering constant, and a checkpoint trained with a
  different head count will fail the shape check rather than silently reinterpret.
- **`ActionChunker`.** Everything about it except `execute_chunk` — `replan_hz`, `mode`,
  `blend`, `buffer_chunks` — is runtime scheduling (spec 8.6), not a tensor operation. The
  lowering consumes `execute_chunk` and ignores the rest **by design**; the async buffer and
  the blend policy live in the env runtime, are compared against their own oracle, and a
  `TemporalEnsemble` blend is not observable in a single `infer`.
- **`Normalizer` conventions.** `MeanStd` forward is `(x - mean) / std` and inverse is
  `x * std + mean`. `MinMax` maps to `Normalized { lo: -1, hi: 1 }` (`learning::action_unit`),
  so forward is `2 (x - lo) / (hi - lo) - 1` and inverse is `(x + 1) / 2 * (hi - lo) + lo`.
- **`Normalizer` statistics.** They are inlined as non-persistent buffers so they never appear in
  `state_dict` and therefore never appear in the weight key set: the values come from the IR,
  which means the checkpoint cannot disagree with the IR about them. `StatsSource::Dataset`
  is `Unsupported` here because resolving a `dataset_hash` is `es-data`'s job (layer 10), and
  `es-policy` is layer 8.

## 4. Weight naming

The safetensors key scheme is

```
nodes.<node_id>.<param path>
```

where `<param path>` is exactly the `state_dict` path **below** the node's member. Loading is
therefore a pure rename: `nodes.<k>.<rest>` ↔ `n<k>.<rest>`. Node **ids** and not node names
are used because `Graph` keys nodes by `NodeId` and nothing else is guaranteed unique; the ids
are authoring identity and are excluded from `learning_hash` (spec 11.2), so a relabelled graph
lowers to a different key set but the same architecture hash — which is correct, since the
checkpoint is bound to the graph by `policy_hash`, not by `learning_hash`.

For the ACT-shaped fixture (`es_ir::learning::testing::act_like`):

```
nodes.0.*                       ResNet18 backbone + fc          (prefix claim)
nodes.1.0.weight  [256, 8]      state MLP, first Linear
nodes.1.0.bias    [256]
nodes.1.2.weight  [512, 256]    state MLP, second Linear
nodes.1.2.bias    [512]
nodes.2.weight    [512, 1024]   fusion projection (2*512 -> 512)
nodes.2.bias      [512]
nodes.3.*                       transformer encoder             (prefix claim)
nodes.4.weight    [400, 512]    regression head (H*A = 50*8)
nodes.4.bias      [400]
```

**Two kinds of entry.** An *exact* key names one tensor and carries its shape. A *prefix claim*
ends in `.*` and covers a sub-module whose internal parameter names belong to torchvision or to
`torch.nn`, not to us. Re-deriving ResNet18's 122 keys in Rust would put a copy of torchvision's
internals in this crate and break the moment torchvision renames one; the claim says "everything
under this prefix is node `k`'s business" and validation treats it accordingly:

- every exact key must be present, with the declared shape, or it is `missing` / `shape`;
- a file key under a prefix claim is accepted unchecked;
- a file key matching neither is `unexpected`.

So a checkpoint for the wrong architecture still fails loudly, and the failure names the node.

## 5. ACT

ACT maps onto the node set as the fixture does, and the only piece this lowering does not write
itself is the vision backbone. **`torchvision` is the provider**: `torchvision.models.resnet18()`
with `fc` replaced by `Linear(512, out_dim)`. It is referenced, never re-implemented — a
hand-written ResNet is exactly the sort of thing that is 99.9% right and therefore worse than
useless as an oracle. `pretrained` is ignored at lowering time (weights come from the
checkpoint) and `frozen` is ignored too (there is no training loop here; spec 8.1 keeps the
optimizer out of the IR).

The consequence to state plainly: **the generated file needs `torchvision` whenever the graph
has a `VisionEncoder`, and needs only `torch` otherwise.** The state-only path — which is what
the tier-4 harness test exercises — has no torchvision dependency.

ACT's own transformer encoder/decoder is *not* modelled node-by-node. Spec 8.1 is explicit that
layer-level authoring is PyTorch's job; the IR describes the interface. `TemporalEncoder
{ Transformer }` is therefore a single opaque `nn.TransformerEncoder` with a prefix claim, and a
real LeRobot ACT checkpoint will need a key remap in the M1 gate packet (§8.9) — that remap is
data, not code, and does not belong here.

## 6. Tier-4 tolerance (spec 8.9)

Spec 8.9's table is about pairs of `PolicyRuntime`s:

| compared | tolerance |
|---|---|
| PyTorch(fp32) ↔ ONNX(fp32) | max abs action error ≤ 1e-5 |
| PyTorch(fp32) ↔ ONNX(int8) | per-task; success-rate drop ≤ 2 pp |
| PyTorch(fp32) ↔ Vulkan(fp32) | ≤ 1e-4 (small policies only) |
| same runtime, re-run | bitwise |

`compare_actions(a, b, tol) -> Equivalence { max_abs, max_rel, pass }` is the harness. Defaults:
`Tolerance::TIER4_FP32` is `abs = 1e-5`, `rel = 1e-5`; `Tolerance::TIER4_VULKAN` is `1e-4`;
`Tolerance::BITWISE` is `abs = 0`, `rel = 0` and additionally requires equal bit patterns, so a
`-0.0` against a `+0.0` fails it while passing `abs = 0`. A pair passes when, elementwise,
`|a-b| <= abs` **or** `|a-b| <= rel * |b|` — `b` is the reference side, which makes the relative
term well-defined and asymmetric on purpose.

The comparison is over the raw action chunk `[H, action_dim]` in the graph's output space, i.e.
after the unnormalizer, because that is the tensor the Safety Plane and the actuator see. Shape
or dtype disagreement is not a large error, it is `Equivalence::pass = false` with
`max_abs = inf`; a harness that quietly broadcasts is a harness that passes when it should not.

## 7. Deferred

Nothing below is a "later, maybe". Each is deferred because its oracle is not in this packet.

- **Diffusion and FlowMatching sampling loops.** `HeadKind::Diffusion { n_steps, scheduler }`
  and `FlowMatching { n_steps }` are iterative samplers with their own noise schedule and their
  own RNG. Determinism of the noise draw (spec 3.4 forbids a global RNG) is the actual design
  problem and it dwarfs the lowering. `Unsupported` until a packet owns the sampler contract.
- **`PolicyBundle` (SmolVLA, π₀).** Spec 8.3 is explicit that a 3.5 B VLA is referenced whole
  and not decomposed. The eventual lowering is a *passthrough*: load the bundle's own module,
  check the interface against `PolicyContract`, call it. It is `Unsupported` here rather than
  half-implemented, because a passthrough that cannot verify the bundle's interface is worse
  than an error message.
- **`LanguageEncoder`.** Needs a tokenizer and `transformers`; a Python dependency on the
  inference path that spec 2.4 wants confined to the learning path.
- **`DiscreteHead`, `EnergyHead`.** No consumer yet.
- **Batched lowering, ONNX export, `libtorch` FFI.** Spec 2.4 puts `OnnxRuntime` at M2 and
  `VulkanRuntime` at M3. The subprocess is the M1 shape and is meant to be slow.
- **Real LeRobot ACT checkpoint key remap.** The M1 gate (spec 8.9) needs it; it is a fixture,
  and fixtures belong with the gate.
