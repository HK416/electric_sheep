# 렌더러 — 타일 아틀라스, 컴퓨트 래스터라이저, 컴퓨트 패스 트레이서

Spec: 사양 §15 (비전 데이터 플레인: 렌더 → 관측, 타일 아틀라스, 렌더 경로, 가속 구조), §3.1 (OpenCV 카메라 및 이미지 컨벤션, sRGB 기본값), §3.3 (렌더링은 FP32, 카메라 상대 좌표), §3.4 (결정론적 실행 계약), §7.2 (`ImageSpec`), §16.2 (스플랫 경로는 별도 기능이 아니라 *렌더 경로*다), §28.3 W2 (타일 아틀라스 + 채널 계약), §28.6 (PT + ReSTIR + SVGF), §1.4 (골든 이미지가 오라클), §1.9 항목 2 (패스 트레이서가 두 번째로 삭감되는 대상).

Crate: `es-render`, layer 5 (§4.2). `es-core`, `es-math`, `es-gpu`, `es-assets`, `es-sensor`만 사용할 수 있고 그 위는 사용할 수 없다. 특히 `es-ir`(layer 6)를 볼 수 없으므로, §7.2의 전체 `ImageSpec`은 여기서 사용할 수 *없다* — [§2.2](#22-imagespec-at-layer-5) 참고.

## 0. 이것은 무엇이고 무엇이 아닌가

`es-render`는 §15.1의 채널 계약을 다수의 카메라에 대해 한 번에, GPU에서, 프레임 내부에 호스트 왕복 없이 생산한다. 두 개의 렌더 경로가 있으며, 둘 다 **컴퓨트 셰이더**다:

| 경로 | 무엇인가 | 상태 |
|---|---|---|
| `Rs` | 화면 공간 스캔 래스터라이저 | §15.3의 비전 학습 기본값 |
| `Pt` | 패스 트레이서, 선택적 ReSTIR DI 및 SVGF 패스 | §1.9 항목 2, 삭감 가능 |

`es-gpu`는 컴퓨트 파이프라인만 제공한다 — 그래픽스 파이프라인 없음, `VK_KHR_ray_tracing_pipeline` 없음, 가속 구조 확장 없음(`docs/design/gpu-foundation.md` 참고). 따라서 §15.4의 TLAS/BLAS 설계는 하드웨어로는 **구현되지 않는다**. M7/R1 이후 두 경로는 CPU에서 프레임마다 빌드한 소프트웨어 BVH를 순회한다(8절); 그 전에는 평평한 삼각형 배열을 인덱스 순서로 순회했고, 골든이 "수백 개의 삼각형" 씬인 이유와 히트 규칙이 스캔의 규칙으로 서술된 이유가 그것이다.

여기 없는 것, 의도적으로:

- **스플랫.** §16.2는 3DGS를 이 crate의 세 번째 렌더 경로로 둔다. `es-splat`(layer 5, 같은 layer, 어느 방향으로도 의존 없음)이 오늘 자산 측을 소유한다. 나중을 위한 훅은 `RenderPath`다: `Splat` variant가 `Rs`/`Pt` 옆에 놓여 같은 채널을 같은 아틀라스에 쓴다. 아틀라스, 채널, `Atlas::read_tile` API의 어느 것도 삼각형을 전제하지 않는다.
- **센서 리얼리즘**(§18.3: 왜곡, 롤링 셔터, 모션 블러, 노출, 샷 노이즈, 깊이 홀). 렌더러는 깨끗한 채널을 방출하고, 리얼리즘은 아틀라스에 대한 이후 패스다. 그 결과 §7.2의 `DistortionModel::None`과 `ShutterModel::Global`만 지원되며, 렌더러는 그 외를 요청하는 뷰를 조용히 무시하는 대신 *거부한다*.
- **옵티컬 플로우 및 속도 채널.** `Channel::Flow`는 프리미티브별 이전 프레임 변환이 필요한데, 렌더러는 아직 이전 프레임 개념이 없다. 요청하면 에러이지, 빈 버퍼가 아니다.
- **텍스처와 머티리얼.** geom당 평평한 알베도 하나, `Geom::rgba`에서. UV 없음, 텍스처 샘플링 없음, PBR 없음.

## 1. 타일 아틀라스 (§15.2)

### 1.1 레이아웃

`maxMultiviewViewCount`는 데스크톱 GPU에서 32이므로, 수백 대의 카메라는 멀티뷰가 될 수 없다(§15.2). 모든 카메라는 하나의 **타일**을 받고, 타일은 채널당 하나의 아틀라스에 `tiles_per_row` 폭으로 행 우선 순서로 패킹된다:

```
TileAtlasCfg { tile_w, tile_h, tiles_per_row }

rows          = ceil(n_tiles / tiles_per_row)
atlas_w       = tiles_per_row * tile_w
atlas_h       = rows          * tile_h
tile_origin(i) = ( (i % tiles_per_row) * tile_w,
                   (i / tiles_per_row) * tile_h )
```

`tile_origin`은 테이블 조회가 아니라 닫힌 형식이다: 레이아웃이 결정론적이므로, 다운스트림 소비자는 호스트 전송 없이 산술만으로 환경별 텐서를 재구성한다(§15.2). `n_tiles`가 고르게 나누어떨어지지 않으면 마지막 행은 패딩되며, 패딩된 타일은 채널의 배경값으로 초기화되고 `read_tile`이 절대 읽지 않는다.

채널**당** 하나의 아틀라스이지, RGBA+깊이를 인터리브한 아틀라스 하나가 아니다. 이유: §15.1의 채널들은 원소 타입이 서로 다르고(`u8` ×3, `f32` ×1, `u32` ×1, `f32` ×3), 컴퓨트 셰이더는 `StructuredBuffer<T>`를 쓰므로, 인터리빙은 비트캐스트 계층과 패킹 규칙을 요구할 뿐 아무 이득이 없다. 그래서 `Atlas`는 `BTreeMap<Channel, Buffer>`를 보유한다.

제약 확인(§15.2): `atlas_w`와 `atlas_h`는 모두 `maxImageDimension2D`(§15.2가 언급하는 데스크톱 GPU에서 16384) 이하여야 한다. 여기서 아틀라스는 `VkImage`가 아니라 버퍼이므로 이 한계가 물리적으로 구속하지는 않지만, 그래도 강제된다 — `es-compile`의 예산 모델이 강제하기 때문이며, 이 crate가 받아들이지만 예산이 거부하는 레이아웃은 거짓말이 되기 때문이다.

### 1.2 `atlas_bytes()`

이 공식은 `crates/es-compile/src/budget.rs`(§20.2)의 `render_tile_atlas` 항목의 **거울상**이다. `es-compile`은 layer 7이고 layer 5에서 의존할 수 없으므로, 산술은 중복되며 테스트로 고정된다:

```
atlas_bytes(cfg, n_tiles, channel)
  = rows * tiles_per_row * tile_w * tile_h * components * dtype_bytes * 2
                                                                       ^ 더블 버퍼
```

`components`는 `Channel::n_components()`, `dtype_bytes`는 `Channel::dtype()`에서 온다. `* 2`는 `budget.rs`가 적용하는 더블 버퍼 계수다.

`Renderer`는 그것을 **할당하지 않는다**: 대신 `device_bytes()`를 할당하는데, 단일 버퍼이고 컴포넌트당 32비트 워드 하나다. 컴퓨트 셰이더가 워드 단위로 주소되는 스토리지 버퍼에 쓰기 때문이다. 그래서 `Rgb8`은 디바이스에서 픽셀당 패킹된 `RGBA8` 워드 하나이며(셰이더는 워드의 3바이트만 이웃과 경합 없이 쓸 수 없다), 사용하지 않는 알파는 `Atlas::read_tile`에서 버려진다. 따라서 `device_bytes`는 `atlas_bytes / 2`가 아니며, 두 이름이 모두 존재하는 이유는 어느 쪽도 다른 쪽인 것처럼 조용히 보고되지 않게 하기 위해서다: `atlas_bytes`를 할당량으로 보고하면 과대평가이고, `device_bytes`를 예산에 보고하면 정상 상태 계획을 과소평가하는 것이다.

§15.2와 대조할 참고 수치: 224×224 `Rgb8` 타일 512개, `tiles_per_row = 23` → 행 23, 아틀라스 5152×5152, `atlas_bytes` = 23·23·224·224·3·1·2 = 159,258,624 B ≈ 152 MiB (사양의 87 MB는 단일 버퍼 512타일 수치이며, 5376×5376으로 다르게 패딩된 것이다 — 둘 다 `tiles_per_row`가 다를 뿐 같은 공식이다).

## 2. 입력

### 2.1 씬

`Renderer::upload_scene(&SceneDesc)`는 `SceneDesc` 순서로 바디를 순회하며, 각 바디의 부모 체인으로부터 월드 포즈를 합성하고, 모든 `Geom`을 월드 공간 삼각형으로 테셀레이션한다:

| `Shape` | 테셀레이션 |
|---|---|
| `Box` | 삼각형 12개 |
| `Plane` | 유한 반폭에 대해 삼각형 2개; 무한 평면(`half_x == 0`)은 고정 100 m 반폭 사용 |
| `Sphere` | UV 구, 고정 16×8 |
| `Capsule` | 실린더 16 세그먼트 + 16×4 반구 캡 2개 |
| `Cylinder`, `Ellipsoid` | 각각의 반지름으로 `Capsule`/`Sphere`와 동일 |
| `Mesh` | 파일의 삼각형: `SceneDesc::meshes[asset]`(`es_assets::mesh::load`가 채움, M10/W2a), 인덱스 세 개당 삼각형 하나, 위치는 `f32`→`f64`로 정확히 확장; `meshes`에 없는 자산은 `es_assets::mesh::load`를 명시하는 `RenderError::UnsupportedShape` (M10/W2b) |
| `HeightField` | `RenderError::Unsupported` |

테셀레이션 개수는 품질 설정이 아니라 상수다: 개수를 바꾸면 모든 골든이 바뀌므로, 실수가 아니라 의도적인 편집이어야 한다.

메시에는 고를 개수가 없다: 삼각형은 파일의 것이고, geom 포즈는 프리미티브와 같은 `push_geom`이 프레임마다 `f64`로 적용하며, 노멀은 다른 모든 삼각형처럼 와인딩에서 나온다 — 메시 전용 셰이딩 경로는 없다. `SceneCache`는 geom의 로컬 삼각형을 `(Shape, AssetRef::hash)`(프리미티브는 0)로 키잉하므로, 이름은 같지만 파일이 다른 메시 geom을 가진 두 씬이 섞일 수 없다. 로딩은 임포터와 렌더러 사이에서 호출자가 밟는 단계다(`es_assets::mesh::load(&mut scene, scene_dir)`); `EnvRenderer`는 받은 씬을 메시째로 복제한다. 골든: `tests/golden/render/mesh_box_*`(`mesh_box.xml`, 64×64, `Rs` rgb8/depth/seg와 흰 하늘 아래 `Pt` 1 spp, `es_render::cpu`로 생성); RTX 3060은 depth에서 0 ULP, 나머지는 비트 단위로 일치한다. 후속 과제: SO-101 업스트림 모델(~350 k 삼각형)의 ms/프레임을 9-지표 세트로(§12.4); 누락된 메시가 첫 프레임이 아니라 생성 시점에 실패해야 한다면 `EnvRenderer::new`에서 `tri_scene` 드라이런.

각 삼각형은 다음을 갖는다: 월드 위치 3개(f32), 월드 기하 노멀(f32×3, 삼각형 와인딩에서), 알베도(f32×3, `Geom::rgba`의 RGB), 이미션(f32×3, 이름이 `_light`로 끝나는 geom에서만 0이 아님 — [§4.2](#42-restir-di) 참고), 세그멘테이션 id(u32). 세그멘테이션 id는 `1 + 순회 순서에서의 geom 인덱스`이며, `0`은 배경을 의미한다. id는 1부터 시작하는 밀집값이라 `SegmentationId` 채널에서 `0`이 "히트 없음"을 명확히 나타낸다.

버퍼 레이아웃은 삼각형당 스트라이드 20 floats(80 B)의 평평한 `f32` 배열이다 — `v0 v1 v2 n albedo emission seg pad`, 세그멘테이션 id는 슬롯 18에 `asuint` 비트캐스트된다. 버퍼 하나, 스트라이드 하나, 양쪽에서 동일하다.

### 2.2 layer 5의 `ImageSpec`

§7.2의 `ImageSpec`은 `es-ir`(layer 6)에 있다. `es-render`는 자신만의 **부분집합**인 `es_render::ImageSpec`을 정의하며, 렌더러가 준수하는 필드만 담는다:

```rust
pub struct ImageSpec {
    pub width: u32,
    pub height: u32,
    pub intrinsics: Intrinsics, // fx, fy, cx, cy — 스큐 없음
    pub near: f32,
    pub far: f32,
}
```

`color_space`는 `Rgb8`에 대해 `SRgb`로, `RgbF32Linear`/`PtRadiance`에 대해 `Linear`로 고정된다(§3.1: sRGB가 기본값이고 선형 변환은 암묵적이 아니라 명시적 노드다). `camera_model`은 `Pinhole`로, `distortion`은 `None`으로, `shutter`는 `Global`로 고정된다. 이것들이 필드가 아닌 이유는 필드가 선택을 암시하는데 여기에는 선택이 없기 때문이다; `es-ir`가 다운스트림에 붙이는 *Observation IR*의 `ImageSpec`은 전체 집합을 유지하며, `ImageSpec::to_contract()`는 §7.2의 타이밍 절반을 경계 너머로 나르는 `es_sensor::CameraContract`를 만든다.

렌더러는 모든 뷰에 대해 `width == tile_w && height == tile_h`를 검증한다. 타일과 해상도가 다른 뷰는 리샘플이 아니라 에러다: 조용한 리샘플은 intrinsics를 바꿀 것이고(§7.2 `OBS-034`, INV-14), 이 crate에는 그것을 올바르게 할 `ImageSpec::resized`가 없다.

### 2.3 카메라 컨벤션 (§3.1)

`Intrinsics::from_fovy`는 골든 카메라 경로 위에 있다: `fx`/`fy`는 뷰별 파라미터 버퍼로 들어가고, 모든 골든 픽셀이 이들의 함수다. 그래서 자산이 저장하는 `f64` `fovy`를 받아 한 번 캐스트한 뒤, 나머지는 `es_math::approx::tan`을 거쳐 고정된 순서로 — 절반, `tan`, 나눗셈 — `f32`로 처리한다. 이를 대체하기 전의 호스트 `libm` `tan`은 아무것으로도 고정되어 있지 않았고(리뷰 M4 S-11), `approx::tan`으로 옮기면서 64×64 / `fovy = 1.2`에서 `fy`가 정확히 1 ULP만큼 이동했다(`46.774269` → `46.774265`) — 이것이 `Rs` 골든이 재생성된 이유다 — [§5](#5-cpu-references-14) 참고.

`CameraView { pose, spec }`. `pose`는 `T_world_camera`다. 카메라 프레임은 OpenCV다: **+Z 전방, +X 오른쪽, +Y 아래**. 이미지 원점은 좌상단, x는 오른쪽, y는 아래쪽. 픽셀 `(px, py)`에 대한 주 광선은, 카메라 공간에서,

```
d_cam = ( (px + 0.5 - cx) / fx,
          (py + 0.5 - cy) / fy,
          1 )                         // 정규화되지 않음
```

이고, 월드 공간에서는 `o = pose.position`, `d = pose.orientation.rotate(d_cam)`이다. `d_cam.z == 1`이 정확히 성립하므로, 광선 파라미터 `t`는 나눗셈이나 별도의 깊이 재구성 없이 **곧** 미터 단위의 카메라 공간 깊이이며, `Depth32`의 `unit_m`은 `1.0`이다.

§3.3은 카메라 상대 좌표를 요구한다. 렌더러는 이를 문자 그대로 취한다: 삼각형 위치는 한 번 `f64`→`f32`로 월드 공간에 업로드되고, 셰이더는 교차 전에 카메라 원점을 뺀다. 따라서 월드 원점에서 먼 정점도 *카메라로부터의* 거리만큼만 f32 가수부를 잃는다.

## 3. `Rs` — 컴퓨트 래스터라이저

아틀라스 픽셀당 스레드 하나; `[numthreads(8, 8, 1)]`; 디스패치는 아틀라스 전체를 덮으므로 패딩된 타일도 같은 커널에 의해 지워진다. 픽셀당:

1. 타일 좌표(역변환된 `tile_origin`)에서 뷰 인덱스를 읽고, 그다음 뷰별 파라미터 버퍼에서 뷰의 포즈와 intrinsics를 읽는다.
2. §2.3처럼 주 광선을 만든다.
3. 삼각형 `0..n_tri`를 오름차순 인덱스로 **스캔**한다. 각각에 대해: Möller–Trumbore 교차; `t <= near` 또는 `t >= far`이면 거부(이것이 near/far 클립이다); 가장 작은 `t`를 가진 히트를 유지하고, 동률은 낮은 삼각형 인덱스로 깨뜨린다.
4. 셰이딩하고 네 채널을 쓴다.

이 루프에 대해 세 가지:

- **스캔은 이제 BVH 순회다**(M7/R1, 8절). 정확히 스캔의 답을 돌려준다: 가장 가까운 `t`, 동률은 낮은 전역 인덱스, 모든 후보에서 비교. 위의 (3)은 *규칙*이고, 트리는 후보를 찾는 방법이다. §15.4의 2단계 TLAS가 업그레이드 경로이며 역시 Vulkan 확장이 필요하지 않다.
- **순회 순서가 곧 출력의 정체성이다.** 오름차순 인덱스, `t`에 대한 엄격한 `<`는 히트에 대한 전순서이므로, 승자는 스레드 스케줄링에 의존하지 않는다. 깊이 버퍼도 없고 읽기-수정-쓰기도 없으므로 원자적 연산도 없다(어차피 §3.4가 FP 원자적 연산을 금지한다).
- **커버리지와 깊이는 패스 트레이서가 쓰는 것과 동일한 광선-삼각형 교차에서 나온다.** 화면 공간 에지 함수와 보간된 `1/z`에서가 아니다. 이것이 §15.3의 요구사항 "깊이, 세그, 노멀은 RS와 PT 사이에 비트 동일"이 근사가 아니라 *구성상* 성립하는 이유의 전부다 — [§6](#6-pt--rs-channel-agreement-14) 참고. 그렇다면 이것을 래스터라이저라고 부르는 것은 고정 함수 삼각형 셋업이 아니라 *루프 구조*(픽셀당 스레드 하나, 프리미티브 스캔, 깊이 테스트)에 대한 진술이다.

### 3.1 셰이딩

플랫 + 램버트, 방향광 하나 `L`(`RenderConfig` 필드, 광원을 *향한* 월드 공간 방향, 그리고 앰비언트 항):

```
n        = geometric normal, flipped to face the ray
lambert  = ambient + max(0, dot(n, L)) * (1 - ambient)
rgb_lin  = albedo * lambert
```

이것이 `#[derive(Default)]` 기본값인 `Shading::Lambert`이며, 모든 골든과 커밋된 모든 관측 문서가
바이트 단위로 고정하는 것이다. 그림자 광선은 없다: 이것이 유일한 셰이딩이던 시절, 그림자 광선은
픽셀당 전체 삼각형 배열을 다시 한번 스캔하는 것이었고, `Pt` 경로가 제대로 모델링하는 효과 하나를
위해 기본 비전 경로의 비용을 두 배로 만들었다.

M7/R2부터는 두 번째 **옵트인** 셰이딩이 있다 — `Shading::Full`: R1의 any-hit 순회를 쓰는 그림자 광선
하나, 반구 앰비언트, 블린-퐁 하이라이트, 그리고 슈퍼샘플링:

```
n        = geometric normal, flipped to face the ray
vis      = shadows ? (any_hit(p + n * RAY_EPS, L, 0, SHADOW_FAR) ? 0 : 1) : 1
diffuse  = max(0, dot(n, L)) * vis
h        = normalize(L - d)
spec     = specular * pow(max(0, dot(n, h)), shininess) * vis      // 0 when dot(n, h) <= 0
hemi     = ground + (sky - ground) * ((n.z + 1) * 0.5)
rgb_lin  = albedo * (hemi + diffuse * (1 - hemi)) + spec + emission   // per channel
```

그다음은 아래의 동일한 sRGB 전달 함수다. `pow`는 `es_exp(es_ln(x) * shininess)`이며 `std`도
`GLSL.std.450`도 아니다. 이를 위해 `Lambert`는 아무것도 움직이지 않았다: 커널 하나가 파라미터
버퍼에서 읽은 플래그로 분기하고, 새 슬롯은 기존 슬롯 뒤에 덧붙였다. 박스 필터의 누적 순서,
파라미터 레이아웃, 관측 경로에 이 옵션을 주지 않은 이유, GPU와 CPU가 무엇에 일치하고 무엇에
일치하지 않는지는 [§9](#9-rs-룩-m7r2)가 전부 담는다.

`Rgb8`은 `rgb_lin`을 **정확한 조각별 sRGB 전달 함수**로 인코딩한 것이다(§3.1: sRGB가 기본 색공간):

```
srgb(c) = 12.92 * c                              c <= 0.0031308
        = 1.055 * c^(1/2.4) - 0.055              otherwise
u8      = round_half_away_from_zero(255 * clamp(srgb, 0, 1))
```

`c^(1/2.4)`는 양쪽에서 `es_exp(es_ln(c) * (1/2.4))`다 — CPU에서는 `es_math::approx`, GPU에서는 `approx.slang`(§3.2 `DET-010`: 관측 경로에서 `std`/`GLSL.std.450` 초월함수 금지). §28.7 게이트 3이 이미 그 둘이 비트 단위로 일치함을 증명하며, 이것이 `Rgb8`을 CPU에서 생성된 골든과 비트 비교할 수 있게 만드는 이유다.

### 3.2 기록되는 채널

| 채널 | 값 | 배경 |
|---|---|---|
| `Rgb8` | 위 참고, u8 × 3 | `0, 0, 0` |
| `Depth32 { unit_m: 1.0 }` | 카메라 공간 미터 단위 `t` | `far` |
| `SegmentationId` | geom id, 1부터 시작 | `0` |
| `Normal` | 카메라 공간의 면 노멀(`Channel::Normal`은 카메라 공간이라고 문서화됨), 단위 길이, f32 × 3 | `0, 0, 0` |

이 집합 밖의 채널(`Rs` 경로에서 `Flow`, `RgbF32Linear`, `PtRadiance`)을 요청하는 `RenderConfig`는 `RenderError::UnsupportedChannel`이다.

## 4. `Pt` — 컴퓨트 패스 트레이서 (§28.6, §1.9 항목 2)

`Pt { spp, bounces, nee, restir, svgf }`. 픽셀당 스레드 하나, `spp` 샘플, `bounces` 비스페큘러 바운스, 모두 디퓨즈. `PtRadiance`(선형 f32×3), [§10](#10-패스-트레이서가-자라다-m7r3)의 톤 매핑된 `Rgb8`, 그리고 §15.3이 `Rs`와 일치하기를 요구하는 `Depth32`/`SegmentationId`/`Normal` 채널(**샘플 0의 1차 히트**에서)을 쓴다.

샘플당 추정자. `nee`는 기본값이 `false`이고 그때 오른쪽 열 전체가 `1.0` 곱셈이 되므로, `cornell_pt1spp`는 어느 쪽이든 바이트 동일하다:

```
throughput = 1
radiance   = 0
ray        = primary
prev_pdf   = 0                            // the camera ray: no light strategy made it
for bounce in 0..bounces:
    hit = scan(ray)                       // same routine as Rs
    if !hit:
        radiance += throughput * sky * w_sky      // w_sky = 1, or 1/2 under nee
        break
    radiance += throughput * emission(hit) * w_bsdf   // w_bsdf = 1, or the power
                                                      // heuristic vs the light pdf
    n = face_forward(hit)
    p = hit_point + n * RAY_EPS
    if nee:
        radiance += throughput * nee_direct(p, n, albedo, last = bounce + 1 == bounces)
    throughput *= albedo(hit)             // cosine-weighted sampling cancels
                                          // the cos term and the 1/pi BRDF
    ray = cosine_hemisphere(n, rng)
    prev_pdf = dot(n, ray) / pi
radiance /= spp                           // accumulated in a fixed sample order
```

코사인 가중 반구 샘플링은 디퓨즈 throughput 갱신을 알베도 곱셈만으로 만들어, pdf로 나누는 일도 0/0의 가능성도 없다. 러시안 룰렛은 **사용하지 않는다**: 픽셀당 작업량을 데이터 의존적으로 만들 것이고, 어차피 바운스 개수는 고정된 작은 값이다. NEE도 데이터 의존성을 들여오지 않는다: 세 가지 광원 종류는 디스패치 전체에서 균일한 *설정*에 대한 `if` 세 개이므로, 한 렌더의 모든 픽셀은 같은 양의 작업을 한다.

`spp` 누적은 오름차순 샘플 인덱스로 하는 평범한 순차 `+=`이지, 트리도 `DeterministicAcc`도 아니다. §18.4의 비닝 누적기는 *순서*가 고정되지 않은 리덕션을 위한 것이다; 여기서는 루프가 순서를 고정하므로 저렴한 방법이 곧 재현 가능한 방법이다.

### 4.1 RNG

카운터 기반이며 스텝이 아니라 주소로 접근한다. `es_env::rng`(§3.4: 전역 RNG 없음)와 정확히 같은 설계다: 값은 자신의 좌표만의 순수 함수다.

```
key(view, px, py, sample, bounce, stream)
    = mix32( mix32( mix32( mix32( mix32(seed ^ view) ^ (px*73856093 ^ py*19349663) )
                           ^ sample ) ^ bounce ) ^ stream )
```

`mix32`는 32비트 파이널라이저 `(z ^= z>>16) *= 0x85eb_ca6b; (z ^= z>>13) *= 0xc2b2_ae35; z ^= z>>16`이다. **32비트이지 `es_env::rng`의 splitmix64가 아니다**: Slang의 `uint64_t`는 `shaderInt64`가 필요한데, 이 crate가 실행되어야 하는 모든 타깃(특히 MoltenVK)에서 §3.3이 그것을 보장하지 않는다. 반면 32비트 믹서는 능력 검사 없이도 Rust와 Slang 사이에서 비트 동일하다. "고정 바운스 디퓨즈 패스 트레이서에 충분히 비상관"을 넘어서는 통계적 품질은 `미검증 (unverified)`이며, 렌더링 이외에는 어디에도 쓰이지 않는다.

`[0, 1)`의 `f32`는 `(x >> 8) as f32 * (1 / 16777216)`이며 — 양쪽에서 정확하고, 절대 1.0이 되지 않는다.

**스트림 표.** `stream`은 같은 좌표에서의 독립적인 용도를 분리하는 것이며, 새 용도는 기존 id를 다른 `index`로 재사용하는 대신 **새 id**를 받는다: 재사용하면 추정자가 독립이라고 가정하는 두 추출이 조용히 상관된다. 표는 `crates/es-render/src/rng.rs`와 여기에 고정되어 있고, 둘 다 계약이다:

| id | 용도 | 추출 단위 |
|---|---|---|
| 0 | 코사인 가중 BSDF 바운스 방향 | 샘플, 바운스 |
| 1 | ReSTIR 초기 후보(광원 선택, 면적 샘플, 예비 수락) | 픽셀 |
| 2 | ReSTIR 공간적 재사용(이웃별 예비 수락) | 픽셀 |
| 3 | ReSTIR 시간적 재사용(예비 수락) | 픽셀 |
| 4 | NEE: 어느 이미셔티브 삼각형인가 (M7/R3) | 샘플, 바운스 |
| 5 | NEE: 그 삼각형 위의 균일 점 | 샘플, 바운스 |
| 6 | NEE: 코사인 가중 하늘 방향 | 샘플, 바운스 |

NEE의 그림자 검사에는 스트림이 없다: 난수를 추출하지 않는다. 스트림 4–6은 `nee`가 켜졌을 때만 추출되므로, `nee: false` 렌더는 M7/R3 이전과 정확히 같은 추출을 한다.

### 4.2 ReSTIR DI

교과서적인 ReSTIR DI이며, `Pt { restir: true }`로 켜지고 기본값은 꺼짐이다. 세 개의 패스, 세 번의 디스패치, 패스당 예비 버퍼 하나(제자리 갱신이 없으므로 읽기/쓰기 위험도, 패스 내 디스패치 순서 의존도 없음):

1. **초기 후보.** 이미셔티브 삼각형(이름이 `_light`로 끝나는 geom; `Geom::rgba`의 RGB가 방출 복사휘도) 위에서 균일 샘플 `M = 8`개. 비가려짐 타겟 함수 `p̂ = |albedo/π · Le · G|`에 대한 가중 예비 샘플링. **M7/R3 이후 여기에 그림자 광선은 없다**: 가시성은 공간적 패스에서, 그 패스가 실제로 선택한 샘플에 대해 한 번 검사된다 — [§10.2](#102-이제-restir은-편향이-없고-숫자는-이렇다) 참고.
2. **시간적 재사용**, 패스 하나: 같은 픽셀에서 이전 `render()` 호출이 남긴 예비와 결합한다. 모션 벡터 재투영은 없다 — 이전 예비는 *같은* 픽셀에서 읽히며, 이는 정적 카메라와 정적 지오메트리에서만 옳다. 첫 `render()`에서는 이전 버퍼가 모두 0이므로 이 패스는 아무 일도 하지 않고 프레임은 공간적 재사용만 한다. 숨기지 않고 문서화됨: 움직이는 카메라는 오래된 재사용을 겪으며 이는 지연으로 보인다.
3. **공간적 재사용**, 패스 하나: 고정 오프셋 `(±3, 0), (0, ±3)`의 이웃 4개와 결합하며, 각각 깊이가 10% 이내이고 노멀이 25° 이내일 때만 받아들인다(표준 기하 유사성 테스트). RNG로 흔들린 것이 아니라 고정 오프셋이다: 지터는 덜 상관된 노이즈를 사서 결과가 오직 픽셀 격자만의 함수라고 말할 수 있는 능력을 대가로 치른다. 결합은 `1/M`이 아니라 **pairwise MIS**이며(M7/R3), 패스는 선택한 샘플을 향한 그림자 광선 하나로 끝난다.

여전히 건너뛴 것: ReSTIR **GI** 전체(이것은 직접광만이며, 간접 바운스는 위의 패스 트레이스 추정자를 통과한다), 예비 안의 이미셔티브 삼각형 이외의 광원 타입([§10.1](#101-next-event-estimation과-mis)의 NEE 경로는 세 가지를 갖지만 예비는 하나다 — 환경맵 없음, 예비 안의 해석적 광원 없음), `M`을 20에서 클램핑하는 것 이상의 예비 노화. **더는 건너뛰지 않는 것**, 그리고 §28.6이 요구했던 것: 재사용을 편향 없이 만드는 MIS 가중치와, 가시성 검사의 편향 보정 위치. 전후 숫자는 [§10.2](#102-이제-restir은-편향이-없고-숫자는-이렇다)에 있다.

### 4.3 SVGF

`Pt { svgf: true }`로 켜지고 기본값은 꺼짐이다. à-trous 패스 세트 **하나**, `n`번 반복(`svgf_iterations`, 기본 4), 2D에 걸쳐 스트라이드 `1 << i`로 분리된 표준 5탭 B-스플라인 웨이블릿 커널 `(1, 4, 6, 4, 1)/16`, 깊이와 노멀에 대한 에지 스토핑:

```
w = w_depth * w_normal * w_luminance
w_depth     = exp(-|z_p - z_q| / (sigma_z * |grad z| + eps))
w_normal    = max(0, dot(n_p, n_q))^sigma_n
w_luminance = exp(-|l_p - l_q| / (sigma_l * sqrt(var_p) + eps))     // M7/R4, sigma_l = 4
```

**`w_luminance` 항은 M7/R4부터 존재하며 히스토리가 없으면 `1.0`이다.** 이 항에는 픽셀당 분산이 필요하고 분산에는 추정할 프레임이 필요하므로, 항은 `RenderConfig::temporal`이 `Some`일 때 정확히 켜진다 — `None`이면 정확히 `1.0`을 곱하는 것이고 필터 출력은 M4 시절과 바이트 단위로 같다. 분산은 색상과 나란히 **제곱** 가중치로 필터링되어, 각 반복이 자신이 실제로 읽는 값의 분산을 읽는다. [§11](#11-정지-카메라를-위한-시간적-누적-m7r4)이 전부다: 누적, 디스오클루전 규칙, 모멘트, 그리고 숫자들.

M7/R4 시점에서 여전히 건너뛰는 것, 정직한 목록:

- **히스토리 길이 기반 커널 확장.** 논문은 히스토리가 짧은 곳에서 커널을 넓히지만, 여기서는 항상 스트라이드 `1 << i`의 5탭이다. 분산 항이 이미 추정이 불확실한 곳에서 *실효* 커널을 넓히며, 데이터 의존적 탭 수는 데이터 의존적 루프 경계(§3.4)다.
- **모션 벡터 재투영.** §11의 유효성 규칙은 정지 카메라의 것이다: 히스토리를 다른 픽셀에서 리샘플하는 일은 절대 없다.
- **분산 *프리필터*.** `n < 4` 동안은 §11의 7×7 추정이 모멘트를 대신하지만, 논문은 첫 à-trous 반복 *안에서* 분산을 한 번 더 프리필터한다. 하지 않았다 — 추정값은 필터링 없이 반복으로 들어간다.
- **`ReSTIR` GI**, 그리고 [section 10.7](#107-r3이-여전히-건너뛰는-것)이 나열하는 나머지 전부.

M7/R4 이전에 건너뛰었고 이제는 아닌 것: 색상의 시간적 누적, 픽셀당 분산 추정, 분산 유도 luminance 항, 짧은 히스토리를 위한 공간적 추정, 디스오클루전 처리.

## 5. CPU 레퍼런스 (§1.4)

오라클은 GPU가 아니다. `es_render::cpu`는 순수 Rust로, `es-gpu` 없이, `unsafe` 없이 작성되었고, `tests/golden/render/`의 모든 골든을 생성하는 것이 바로 이것이다.

```rust
pub fn rasterize(scene: &TriScene, view: &CameraView, cfg: &RenderConfig) -> CpuFrame
pub fn path_trace(scene: &TriScene, view: &CameraView, cfg: &RenderConfig) -> CpuFrame
```

`CpuFrame`은 채널당 `Vec` 하나와 타일 형태를 보유한다. 두 함수는 셰이더와 *같은 알고리즘*이며, 식 단위, 같은 순서로 — 같은 교차 루틴, 같은 순회 순서, 같은 `es_math::approx` 호출, 같은 누적 순서다. 두 텍스트가 갈리는 곳에서는 Slang이 틀린 것이지, Rust가 틀린 것이 아니다.

이것이 골든을 GPU 경로가 아니라 **한 번** CPU 경로로 생성하는 이유다: RTX 4060에서 만들어진 골든은 그 드라이버의 산술을 저장소에 구워 넣을 것이고, 다음 디바이스는 실제로는 디바이스 차이일 뿐인 테스트를 "실패"할 것이다. 골든 파일은 CI 읽기 전용이며(§1.4), `xtask verify-goldens`가 강제한다.

골든을 위한 씬: Rust로 만든 Cornell box(`es_render::cornell`) — 벽 5개(흰색, 빨간 왼쪽, 초록 오른쪽), 내부 상자 2개, 이미셔티브 천장 패널 `ceiling_light` 1개, 64×64 타일, 카메라 1개, 방향광 1개. geom 8개, 삼각형 96개.

**그 씬에는 동일 평면 위의 면이 두 개도 없으며**, 내부 두 상자는 바닥에 파묻혀 있다. 이것은 스타일이 아니라 정확성 요구사항이다: 두 삼각형이 평면을 공유하는 곳에서는 광선이 정확히 같은 `t`에서 둘 다 맞고, 승자는 barycentrics가 `u + v <= 1`의 어느 쪽에 떨어지는지로 결정되는데 — 이는 CPU와 GPU가 1 ULP만큼 다르게 답할 수 있는 것이다. 벽이 바닥과 천장에 단순히 맞닿기만 했을 때는, 4096 픽셀 중 9개가 GPU에서 다른 면을 골랐고(반올림이 아니라 전체 픽셀 색상 차이), 깊이와 세그멘테이션은 여전히 일치했다. 벽을 바닥과 천장에 겹쳐 넣자 그 아홉 개가 모두 사라졌다.

| 골든 | 채널 | dtype | shape |
|---|---|---|---|
| `cornell_rs_rgb8` | `Rgb8` | u8 | 64×64×3 |
| `cornell_rs_depth` | `Depth32` | f32 | 64×64 |
| `cornell_rs_seg` | `SegmentationId` | u32 | 64×64 |
| `cornell_pt1spp` | `PtRadiance` | f32 | 64×64×3 |

처음 작성된 이후 한 번 재생성되었다, 리뷰 M4 S-11 때문에(`Intrinsics::from_fovy`가 호스트 `tan`에서 `es_math::approx::tan`으로 옮겨간 것, [§2.3](#23-camera-convention-31) 참고). `fy`의 1 ULP 이동은 광선 방향의 서브픽셀 변화이므로, 차이는 실루엣 에지에 국한된다:

| 골든 | 차이 |
|---|---|
| `cornell_rs_rgb8` | 12288 바이트 중 57개 차이(에지 픽셀이므로 빨간 벽/흰 상자 경계에서 최대 183까지) |
| `cornell_rs_depth` | 4096 floats 중 1604개 차이, 최대 절대값 4.05e-6 m, 최대 17 ULP |
| `cornell_rs_seg` | 4096 픽셀 중 19개가 이웃 geom을 취함 |
| `cornell_pt1spp` | **바이트 단위로 동일** |

GPU는 재생성된 파일과 여전히 정확히 일치한다(`Rgb8`/`SegmentationId` 비트 동일, RTX 4060에서 `Depth32`/`Normal` 0 ULP) — 이것이 핵심이다: 이동은 공유된 입력에 있는 것이지, 어느 경로의 산술에 있는 것이 아니다.

`cornell_pt1spp`는 1 spp, 바운스 2, ReSTIR와 SVGF는 꺼짐이다 — RNG, 바운스 루프, 이미셔티브 히트를 모두 운동시키는 가장 작은 것이며, 64 샘플의 노이즈까지 고정하지 않고도 골든이 비트 정확하게 고정할 수 있는 유일한 PT 구성이다.

### 5.1 허용 오차

주장된 허용 오차와, NVIDIA RTX 4060 Laptop GPU(드라이버 592.82, Slang 2026.8)에서 64×64로 **측정된** 값:

| 비교 | 주장 | 측정 |
|---|---|---|
| CPU `Rs`/`Pt` vs 골든 | 비트 동일(생성한 주체이므로) | 비트 동일, 골든 4개 모두 |
| GPU `Rs` `Rgb8` vs 골든 | 비트 동일 | 12288 바이트 중 0개 차이 |
| GPU `Rs` `SegmentationId` vs 골든 | 비트 동일 | 비트 동일 |
| GPU `Rs` `Depth32` vs 골든 | ≤ 1 ULP | **0 ULP** |
| GPU `Rs` `Normal` vs 골든 | ≤ 1 ULP | **0 ULP** |
| GPU `Pt` 1 spp vs CPU `Pt` 1 spp | 비트 동일 | 0 ULP |
| GPU `Pt` + SVGF vs CPU | 비트 동일 | 0 ULP |
| GPU `Rs` 실행 A vs 실행 B | 비트 동일, 모든 채널 | 비트 동일 |
| GPU `Pt` + ReSTIR (+ SVGF) vs CPU | ≤ 1e-5 정규화 | **1.3e-7 정규화, 최대 10 ULP** |

`Depth32`와 `Normal`이 0이 아니라 1 ULP까지 허용되는 이유는 Möller–Trumbore 나눗셈이 두 텍스트가 정당하게 다를 수 있는 유일한 지점이기 때문이다 — 한쪽의 `(1/det) * x`와 다른 쪽의 `x / det`는 소스 차이가 아니라 컴파일러 선택이다. 이 디바이스는 우연히 0을 준다. 테스트는 측정된 ULP를 출력하므로, 0에서 1로의 회귀는 1이 통과하더라도 눈에 보인다.

**ReSTIR는 비트 동일하지 않은 유일한 경로**이며, 이미지 피크의 10 ULP / 1.3e-7이다. 예비 패스들은 이웃에 걸쳐 `p̂ · W · M`을 합산하는데, 셰이더 컴파일러는 `NoContraction` 아래에서도 단일 식 내에서 재결합할 자유가 있다. 그 결과는 숫자가 보여주는 것보다 나쁘다: 재샘플링 결정은 임계값 `rand · w_sum < weight`이므로, 가중치의 1 ULP 차이가 픽셀에서 *다른* 광원 샘플을 고를 수 있다. 이 디바이스, 이 해상도에서는 일어나지 않았고, 설계상 그것을 막는 것은 아무것도 없다 — 이것이 허용 오차가 픽셀당이 아니라 이미지 피크에 대해 명시되는 이유다(렌더링된 이미지 대부분은 0에 가깝고, 1e-7 픽셀에서의 1e-7 차이는 아무도 구별할 수 없는 이미지에 대해 100% 상대 오차다).

## 6. PT ↔ RS 채널 일치 (§1.4, §15.3)

§15.3의 출력 계약은 깊이, 세그멘테이션, 노멀이 렌더 경로 사이에서 **비트 동일**하고 RGB만 유사성 임계값이라고 말한다. 테스트 `pt_and_rs_agree_on_geometry`는 같은 씬을 두 경로로 렌더링하여 정확히 그것을 단언하며, CPU에서(어디서나 실행되도록) 그리고 GPU에서(디바이스 고유 발산도 잡히도록):

```
rs.depth == pt.depth        bitwise
rs.seg   == pt.seg          bitwise
rs.normal == pt.normal      bitwise
```

이것이 구성상 성립하는 이유는 두 경로 모두 1차 광선에 대해 같은 순서로 같은 삼각형 배열에 대해 같은 `nearest_hit`을 호출하고, `Pt`가 어떤 바운스나 RNG 추출 이전에 샘플 0의 1차 히트에서 이 세 채널을 쓰기 때문이다. 나중에 누군가 `Rs` 스캔을 진짜 고정 함수 스타일 래스터라이저로 바꾸면 이 테스트가 실패할 것이고, 그 수정은 문서화된 깊이 허용 오차이지 골든 변경이 아니다.

RGB는 경로 사이에서 비교되지 *않는다*: `Rs`는 원바운스 해석적 셰이딩이고 `Pt`는 다른 적분의 몬테카를로 추정이다. 둘 사이의 SSIM 임계값(§15.3이 요구하는 것)은 수렴된 PT 렌더와 SSIM 구현이 필요하다. M7/R3이 둘 다 만들었고 — `es_render::ssim`과 `Pt` 경로의 톤 매핑된 `Rgb8` — [§10.4](#104-153의-ssim-숫자가-마침내-존재하고-그것은-낮다)가 그 측정이다. **임계값은 여전히 정해지지 않았다**: 그 숫자는 두 렌더러보다 두 조명 모델에 관해 더 많이 말해 주며, 그로부터 임계값을 고르는 것은 패킷이 아니라 소유자의 결정이다.

## 7. 결정론 (§3.4)

- 컴퓨트 큐 하나, 레코더 하나, 모든 디스패치 뒤에 전체 배리어 — 모두 `es-gpu`에서 상속되며 여기서는 선택 사항이 아니다.
- 원자적 연산 없음. 공유 메모리 없음. 서브그룹 연산 없음. 워크그룹 개수에 대한 의존 없음: 모든 커널은 `SV_DispatchThreadID`만으로 인덱싱하고 경계를 검사한다.
- 모든 초월함수는 `approx.slang` / `es_math::approx`를 거친다.
- `ExecModes`는 `Gpu::deterministic_execution_modes()`에서 오며 모든 `SlangCompiler::compile_file` 호출에 전달되므로, `NoContraction`과 §3.4 3단계 실행 모드가 모든 모듈에 들어간다.
- `HashMap` 없음. 채널 맵은 `BTreeMap`, 나머지는 모두 뷰로 인덱싱되는 `Vec`.
- RNG는 `(view, pixel, sample, bounce, stream)`으로 주소되므로, 샘플 순서, 스레드 순서, 디스패치 형태가 추출값을 바꿀 수 없다.

이것이 **사지 않는 것**: 디바이스 *간* 비트 동일. §3.5 tier 1은 실행 해시에 같은 `hardware_capability`를 요구하고, 위의 `Depth32` 1 ULP 허용 오차는 이미 GPU와 CPU가 같은 텍스트의 서로 다른 두 구현이라는 인정이다. 이 crate가 하는 주장은: 같은 디바이스, 같은 바이너리 → 같은 비트; 그리고 명시된 허용 오차에서의 CPU → GPU 일치, 그것뿐이다.

## 8. 프레임 시간은 어디로 가는가, 그리고 소프트웨어 BVH (M7/R1)

`docs/packets/M7/R1-bvh.md`. §28.10은 SO-101 데모 셀에 대해 1280×720에서 **80 ms/프레임**을 기록하고 있고(`visible-learning.md` 7.17 항목 4, RTX 4090 한 대), 두 가지 용의자를 지목한다: 장면이 매 프레임 재테셀레이션되어 새로 할당된 버퍼에 재업로드된다는 것, 그리고 셰이더가 픽셀마다 모든 삼각형을 스캔한다는 것. 둘 다 측정된 적이 없다. §1.4는 먼저 측정하라고 말한다.

### 8.1 측정된 기준선

`cargo test -p es-render --release -- --ignored --nocapture frame_profile`은 한 프레임의 네 단계 — 테셀레이션, 업로드, 디스패치+대기, 리드백 — 를 데모 장면(`tests/fixtures/mjcf/so101_pick_place.xml`, 테셀레이션 후 **2,754** 삼각형; §28.10의 "2,978"은 이전 수치)에 대해 `es video showcase`의 카메라(`--eye 0.66,-0.46,0.52 --look-at 0.14,-0.04,0.04 --fov 36`)로 100 프레임 측정한다. `upload`은 `Renderer::upload_tris`, `dispatch+wait`은 파라미터 버퍼 업로드와 펜스 대기까지 포함하는 `Renderer::render`, `readback`은 `Atlas::read_tile`이다.

**변경 전, RTX 3060 (드라이버 591.12, Slang 2026.8), 중앙값 / p95 ms:**

| 단계 | 1280×720 | 96×96 |
|---|---|---|
| 테셀레이션 | 0.232 / 0.326 | 0.255 / 0.321 |
| 업로드 | 0.334 / 0.490 | 0.203 / 0.345 |
| 디스패치+대기 | **38.633 / 41.374** | 0.913 / 1.354 |
| 리드백 | **83.575 / 86.850** | 1.135 / 1.311 |
| 프레임 합계 | 122.856 / 141.384 | 2.512 / 3.106 |
| `camera_frames_per_sec` (중앙값) | 8.1 | 398.1 |
| `pixels_per_sec` (중앙값) | 7.50e6 | 3.67e6 |

결론은 둘이고, 그중 하나는 이 패킷의 것이 아니다.

1. **스캔이 1280×720 프레임의 38.6 ms** — 921,600 픽셀 × 2,754 삼각형 = 2.5 G 번의 Möller–Trumbore 테스트. BVH가 없애는 것이 이것이고, §28.10이 지목한 두 용의자 중 측정이 뒷받침하는 것은 이것뿐이다.
2. **리드백은 83.6 ms이고, 그것은 렌더러가 아니다.** 같은 테스트가 동일 크기의 호스트 가시 버퍼를 직접 읽는다: **3,600 KiB에 80.7 ms, 44 MiB/s**. `es_gpu::Buffer::download`는 디바이스 로컬 버퍼에 대해 `Usage::Staging`(`MemoryLocation::CpuToGpu`) 버퍼를 할당하고 복사한 뒤 `to_vec()`하는데, CpuToGpu 메모리는 *write-combined*이므로 호스트 읽기가 캐시되지 않는다. 해법은 `es-gpu`의 `GpuToCpu` 리드백 버퍼이고, `crates/es-gpu/**`가 이 패킷의 범위 밖이므로 다음 패킷의 몫이다. 다시 발견되지 않도록 여기에 기록한다. 그것이 들어오기 전까지 1280×720 프레임 합계에 대한 ~84 ms 미만의 목표는 무엇이든 `목표 / 상태: 미검증 (unverified)`이다.

테셀레이션 0.23 ms, 업로드 0.33 ms: 합쳐서 프레임의 0.5 %다. 그럼에도 캐시하고 영속화하는 이유는 고치는 비용이 싸고, 평가에서 모든 관측 프레임이 렌더링되는 크기인 96×96에서는 2.5 ms 프레임 중 0.46 ms, 즉 18 %이기 때문이다.

### 8.2 무엇이 바뀌었고, 왜 출력은 한 비트도 안 바뀌었나

세 가지 수정이며, 각각 대체한 코드와 비교하는 테스트로 고정된다.

1. **`SceneCache`**(`scene.rs`)는 각 지옴의 *로컬* 테셀레이션 — `tessellate()`가 만드는
   `approx::{sin, cos}` 정점 — 을 프레임 사이에 보관하고, 포즈는 이전과 같은 `push_geom`으로 프레임마다
   `f64`로 적용한다: 같은 `pose.transform_point`, 같은 `to_f32`, 같은 `face_normal`, 같은 push 순서.
   `cached_tessellation_is_bit_identical`이 Cornell과 SO-101 씬의 세 포즈에서 캐시된 `TriScene`과
   캐시 없는 것을 `PartialEq`로 비교한다. `TriScene::from_scene_with_poses`는 이제 빈 캐시로의 호출
   하나이므로 호출자의 의미는 바뀌지 않았다.
2. **영구 버퍼**(`renderer.rs`): 삼각형+BVH 버퍼, params 버퍼, 픽셀별 `hit_tri` 버퍼를 프레임 사이에
   유지하고 키우기만 하며 줄이지 않는다(`grow`). 채널 버퍼 넷은 `Atlas`가 소유해 호출자에게 넘기므로
   프레임마다 그대로다.
3. **단일 레벨 BVH**(`bvh.rs`; `common.slang`의 `es_nearest`/`es_any_hit`; `cpu.rs`의
   `nearest_hit`/`any_hit`): 무게중심 경계의 최장 축을 따라 무게중심 중앙값 분할, 리프당 ≤ 4 삼각형,
   노드는 평평한 배열로 삼각형 *뒤에* 같은 버퍼에 업로드(`params`의 슬롯 17–19가 오프셋을 담아
   디스크립터는 움직이지 않았다). 순회는 64칸 스택의 고정 순서 하강이고, 빌드가 깊이를 제한한다(2,754
   삼각형 씬에서 11, Cornell에서 6 — 테스트가 출력).

**BVH의 답이 평면 스캔의 답인 이유.** 평면 스캔의 히트 규칙은 "`(near, far)` 안에서 가장 가까운 `t`,
동률은 낮은 전역 삼각형 인덱스"다. 순회는 그 규칙을 그대로 지킨다 — 방문 순서를 믿지 않고 모든 후보에서
`(t, index)`를 비교한다 — 그래서 스캔이 받아들일 모든 삼각형을 *방문*하기만 하면 스캔의 승자를 돌려준다.
그것을 확률이 아니라 확실로 만드는 두 세부: 모든 노드 상자는 `PAD = 1e-4` m 바깥으로 패딩된다 —
Möller–Trumbore가 삼각형의 정확한 경계에서 한 올 바깥을 지나는 광선을 받아들일 수 있기 때문이다; 그리고
슬랩 테스트는 Ize의 강건 계수(`1 ∓ 2^-22`)를 써서 자기 반올림으로 광선이 들어가는 노드를 거부하지 않는다.
둘 다 후보를 *더할* 뿐 빼지 않으며, 후보가 늘어도 `(t, index)` 최솟값은 바뀌지 않는다. 교차 루틴 자체는
건드리지 않았으므로 `t`는 같은 비트이고 — 그래서 두 GPU 모두에서 `Depth32`와 `Normal`이 CPU 대비 0 ULP를
유지했다. `bvh_traversal_is_the_flat_scan`은 씬당 광선 10,000개를 두 루틴에 쏜다(평면 스캔은
`nearest_hit_flat`으로 남겨 둔다): Cornell과 SO-101, nearest와 any-hit 모두 전부 같다. 트리는 어떤
해시에도 들어가지 않는다: 이미 해시된 데이터 위의 탐색 구조일 뿐이다.

§15.4의 2단계 TLAS/BLAS는 업그레이드 경로로 남는다(`Bvh::build`의 `ponytail:`): 프레임별 `f64` 포즈
적용이 정점을 커밋된 모든 골든과 비트 동일하게 유지하는 것이고, 3,000 삼각형 리빌드는 0.1–0.2 ms다.

## 9. Rs 룩 (M7/R2)

`docs/packets/M7/R2-rs-look.md`. §28.10은 `Rs` 경로를 "램버트에 상수 앰비언트; 그림자 없음,

하늘, 하이라이트, 안티에일리어싱을 가질 수 있는가이다.

```rust
pub enum Shading {
    #[default] Lambert,                       // §3.1, 그대로, 모든 골든이 고정한다
    Full { shadows, specular, shininess, sky_rgb, ground_rgb, ssaa },

```

`RenderConfig::rs()`는 `Lambert`를 유지한다. `RenderConfig::rs_full()`은 의견이 담긴 프리셋

ground [0.25, 0.22, 0.20], ssaa: 2`. `es video showcase --look lambert|full`이 이를 고르며 기본값은
`lambert`다.

### 9.1 셰이딩, 정확히

수식은 [§3.1](#31-셰이딩)에 있고, 여기는 그 뒤에 있는 것들이다.

- **그림자 광선은 R1의 any-hit 순회다**(`cpu::any_hit` / `es_any_hit`). `p + n * RAY_EPS`에서
  광원 방향으로 `(0, SHADOW_FAR)` 구간, `SHADOW_FAR = 1e30`. 광원은 *방향광* — 무한히 멀다 —
  이므로 차폐물이 카메라의 far 평면 바깥에 서 있을 수 있고, 뷰 프러스텀의 `far`는 틀린 경계다.
  무한대가 아니라 `1e30`인 이유: `rcp_safe`가 슬랩 테스트에서 `0 * inf`를 없애려고 역수를
  ±1e30으로 클램프하는데, 무한한 `far`는 그것을 도로 불러들인다.
- **`vis`는 디퓨즈와 스페큘러에만 곱해지고 앰비언트에는 곱해지지 않는다.** 그림자 속 표면도 반구
  앰비언트를 유지하며, 그것이 코넬 박스의 그림자진 바닥이 새까매지지 않게 하는 것이다.
- **퐁이 아니라 블린-퐁**: `h = normalize(L - d)`이고 `d`는 카메라가 만든 그대로의 뷰 광선 —
  정규화되지 않은, 카메라 공간에서 `z = 1`인 벡터다. `d`를 먼저 정규화하면 측정이 아니라 룩인
  하이라이트를 위해 서브샘플마다 `sqrt`가 하나 더 붙는다.
- **`pow`는 `es_exp(es_ln(x) * shininess)`**이며 양쪽 모두 `x <= 0`에서 가드한다(§3.2 `DET-010`:
  골든을 생성하는 경로에 `std`도 `GLSL.std.450`도 없다).
- **반구는 월드 공간이다**: `n.z = +1`에서 `sky`, `n.z = -1`에서 `ground`, `(n.z + 1) * 0.5`로 보간.
  `lerp`/`mix`가 아니라 양쪽 모두 `ground + (sky - ground) * t`로 적어 둔 이유는 HLSL의
  `lerp(x, y, s) = x + s * (y - x)`와 GLSL의 `mix(x, y, a) = x * (1 - a) + y * a`가 같은 식이
  아니며 두 텍스트는 같은 방식으로 반올림해야 하기 때문이다.
- **아무것도 맞히지 못한 광선은 여전히 검정을 반환한다**, `sky_rgb`가 아니라. `sky_rgb`는 배경이
  아니라 위쪽에서 오는 *앰비언트*다: 배경에 색을 주는 것은 `SegmentationId == 0`의 모습을 바꾸는
  일이고, 셰이딩 결정이 아니라 씬 결정이다.
- **앰비언트와 디퓨즈의 혼합은 에너지 보존적이다** — 채널별 `hemi + diffuse * (1 - hemi)`,
  `Lambert`가 상수 앰비언트에 쓰는 것과 같은 형태(`ambient + ndl * (1 - ambient)`)다. 빛을 온전히
  받는 표면은 정확히 자기 albedo를 반환하고 그림자 속 표면은 `albedo * hemi`를 반환하므로, sRGB
  변환 이전에 아무것도 클리핑되지 않는다. **리뷰에서 수정됨**: 패킷의 원래 식
  `albedo * (hemi + diffuse)`는 빛을 받는 모든 표면에서 albedo를 넘는다 — `sky`가 0.85이고
  `ndl`이 0.87이면 SO-101 테이블이 순백으로 렌더링되었다 — 그리고 그것은 톤 맵에게 감추라고 할
  일이 아니라 식 자체의 결함이다. `spec`은 덧셈으로 남는다: 하이라이트는 날아가도 된다, 그것이
  하이라이트다.

`Full`이 여전히 아닌 것: 텍스처 없음, 소프트 섀도 없음(광선 하나, 방향광 하나), 다중 광원 없음,
톤 맵 없음(그것은 R3), 전역 조명 없음(그것은 `Pt`).

**코넬 골든이 고정하지 못하는 것.** 박스는 닫힌 방이므로 안에서 나가는 모든 그림자 광선은 천장을
맞힌다: 프리셋에서는 `cornell_rs_full_rgb8`의 모든 픽셀이 `vis = 0`이고 `diffuse` 항은 0이며,
골든은 위 수정 전후로 바이트까지 동일하다. 골든은 반구와 그림자 광선과 박스 필터를 고정하지만
혼합에는 눈이 멀어 있다. 그것이 못 하는 것을 두 테스트가 덮는다:
`full_shading_is_energy_conserving`은 `shade_full`을 직접 호출해 빛을 받는 표면이 albedo를,
그림자 속 표면이 `albedo * hemi`를 반환함을 단언하고, `gpu_full_shading_matches_the_cpu`는
GPU/CPU 비교를 `shadows: false`로 한 번 더 돌린다 — 이 씬에서 디바이스가 빛 분기를 실행하는
유일한 방법이다.

### 9.2 SSAA는 순서가 고정된 박스 필터다

`ssaa: k`는 픽셀당 `k × k` 서브샘플을 `px + (sx + 0.5) / k`에서 셰이딩하고 박스 필터로 묶는다:

```
acc = 0
for sy in 0..k:            // row-major, sy가 바깥, sx가 안쪽, 순차 += 하나
    for sx in 0..k:
        acc += shade(sub_sample(sx, sy))     // 아무것도 맞히지 못한 서브샘플은 0을 더한다
lin = acc * (1 / (k * k))  // 곱셈 한 번, 그다음에 sRGB 전달 함수
```

스펙 §3.4는 스케줄링에 의존하는 누적 순서를 금지하므로 순서는 두 텍스트에 적혀 있고 합은 `f32`
순차 합이다 — 페어와이즈 트리 없음, 아토믹 없음, 공유 메모리 없음. 그리고 **커널은 하나다**:
슈퍼샘플링은 출력 픽셀을 소유한 스레드 안에서 일어나며, 더 큰 아틀라스를 두 번째 패스로 리졸브하지
않는다. 아틀라스도 버퍼도 `Atlas::read_tile`의 모양도 바뀌지 않은 이유가 그것이다: `ssaa: 2`에서
스레드 하나가 1개와 0개 대신 기본 광선 4개와 그림자 광선 4개를 쏜다.

`k = 1`은 유일한 서브샘플을 `px + 0.5` — 픽셀 중심, 비트까지 — 에 놓으므로 `primary_dir`은 이제
`primary_dir_sub(.., 0, 0, 1.0)`이고 `Lambert`는 움직이지 않았다.

**기하 채널은 어떤 셰이딩에서도 중심 광선의 것이다.** `Depth32`, `SegmentationId`, `Normal`은
예전 그대로 `es_primary_dir(vw, px)`에서 나오고, 테스트는 그것이 `Lambert`가 쓰는 것과 비트 단위로
같음을 CPU(`cpu_full_shading_reproduces_its_golden`)와 GPU(`gpu_full_shading_matches_the_cpu`)
양쪽에서 단언한다. 이것은 기하 채널이 "각 블록의 첫 서브샘플"에서 온다는 **패킷 문구로부터의
이탈**이다. 그럴 수 없다: `ssaa: 2`에서 블록의 첫 서브샘플은 `px + 0.25`에 있고 그 깊이는 중심의
깊이가 아니다. 중심 광선이야말로 패킷이 실제로 요구하는 등식을 참으로 만들고, §15.3의 `RS`/`PT`
채널 일치(`Pt`의 샘플 0 기본 히트, 역시 중심 광선에 대한 것)도 공짜로 지킨다.

### 9.3 GPU와 CPU가 일치하는 것

코넬 박스 64×64, NVIDIA RTX 3060(Slang 2026.8)과 RTX 4090에서 측정:

| 비교 | 주장 | 실측 |
|---|---|---|
| CPU `Full` `Rgb8` vs `cornell_rs_full_rgb8` | 비트 동일(그것이 생성했다) | 비트 동일 |
| CPU `Full` vs `Lambert`, depth/seg/normal | 비트 동일 | 비트 동일 |
| GPU `Full` vs `Lambert`, depth/seg/normal | 비트 동일 | 비트 동일 |
| GPU `Full` `Rgb8` vs CPU, 프리셋 | **엣지 픽셀을 제외하고** 비트 동일 | 12,288바이트 중 3바이트, 4,096픽셀 중 1픽셀 |
| GPU `Full` `Rgb8` vs CPU, `shadows: false` | 동일 | 12,288바이트 중 3바이트, 같은 픽셀 |

간직할 가치가 있는 발견은 마지막 행이다. 차이 나는 픽셀은 (37, 49), 짧은 박스의 윗면과 먼 면이
만나는 곳이다: 네 서브샘플 중 하나가 공유 모서리를 스치고, CPU는 먼 면에 GPU는 윗면에 히트를
주며, 두 면의 반구 앰비언트가 다르다 — 그래서 픽셀 색의 4분의 1이 255단계 중 5~9만큼 바뀐다
(`sky - ground`가 파랑에서 가장 크므로 파랑이 가장 크다). 이것은 셰이딩 차이가 아니라 **커버리지**
동점이다: `dot`의 합산 순서는 두 구현 사이에 고정되어 있지 않고(SPIR-V의 `OpDot`은 `NoContraction`
아래에서도 원하는 대로 결합할 수 있다), 광선이 삼각형 경계로부터 1 ULP 안쪽을 지나면 "가장 가까운
히트, 동점은 낮은 인덱스" 의 승자가 달라질 수 있다. 픽셀당 샘플 하나는 이 씬에서 그런 모서리에
결코 내려앉지 않았다; 2×2 서브샘플은 4천 픽셀 중 하나에서 내려앉는다.

그래서 `gpu_full_shading_matches_the_cpu`는 한 디바이스에서만 참인 숫자 대신 정직한 것을 단언한다:
차이 나는 모든 픽셀은 네 서브샘플이 **모두** 같은 삼각형을 맞히지는 않는 픽셀이어야 하고, 최대
64단계(255/4, 네 서브샘플 중 하나가 한 채널을 움직일 수 있는 상한 — 안전장치이며 판별하는 쪽은
서브샘플 단언이다)까지만 차이 나야 하며, 차이 나는 픽셀은 전체의 0.1%를 넘을 수 없다. 네 서브샘플이 삼각형에
합의하는데도 차이 나는 픽셀은 셰이딩 발산이며 테스트를 실패시킨다.

대안 — `es_intersect`에서 `a.x*b.x + a.y*b.y + a.z*b.z`로 적어 `dot`을 고정하는 것 — 은 *기본*
경로 커널의 산술을 바꾸는 일이고 이 패킷이 금지한다. 그 자체로 할 가치가 있으며, 그때는 골든을
다시 검증해야 한다.

### 9.4 파라미터 레이아웃

셰이딩 블록은 M4의 전역 슬롯 **뒤에** 덧붙였고, 기존 슬롯은 하나도 움직이지 않았다:

| 슬롯 | 의미 |
|---|---|
| 0..20 | M4의 전역: 삼각형 수, 아틀라스 모양, 광원, 앰비언트, 하늘, 시드, spp, 바운스, 광원 수, BVH base/nodes/prim-base |
| 20 | 셰이딩: `0` = `Lambert`, `1` = `Full` |
| 21 | shadows, `0`/`1` |
| 22, 23 | specular, shininess |
| 24..27, 27..30 | `sky_rgb`, `ground_rgb` |
| 30 | `ssaa` |
| 31.. | 뷰당 레코드, 각 16 float (`ES_PARAM_VIEW_BASE`) |

`PARAM_VIEW_BASE`는 `renderer.rs`와 `common.slang`에서 함께 20에서 31로 옮겨졌다; 양쪽 각각
상수 하나이고 모든 커널은 `es_view(v)`로 뷰를 읽는다. `Lambert`는 플래그만 쓰고 21..31은 0으로
남긴다. `u32` 값은 삼각형 수가 늘 그래 왔듯 `f32::from_bits`로 버퍼에 실린다.

### 9.5 관측 경로에 이 옵션을 주지 않은 이유

`EnvRendererCfg`에는 `shading` 필드가 없고 `es_env::render::config`도 그것을 설정하지 않는다:
관측은 `Lambert`를, 오직 `Lambert`만 렌더링한다. §28.10 규칙 1이 그 이유다 — 커밋된 문서가
기술하는 픽셀은 그 문서의 것이고, 호출자가 그것을 다르게 다시 렌더링하게 해 주는 플래그는
호출자가 조용히 체크포인트를 무효화하게 해 주는 플래그다. 관측 경로에 이 룩을 제공한다는 것은
`observation_hash`를 옮기고 데이터셋을 다시 모으고 다시 학습시킨다는 뜻이다; 그것은 필드가 아니라
소유자의 결정이 뒤에 있는 해시 인식 패킷이다.

`es video showcase --look full`은 그 어느 것도 해당하지 않는 경우다: 쇼케이스 카메라는 어떤 씬에도
어떤 IR에도 없고, 그 프레임은 정책이 아니라 사람이 본다.

### 9.6 비용

`ssaa: 2`의 `Shading::Full`은 `Lambert`가 기본 광선 하나를 쏘는 자리에서 기본 광선 4개와 최대
그림자 광선 4개를 쏜다 — 하이라이트의 추가 `exp`/`ln` 이전에, 셰이딩되는 픽셀당 순회 작업이 8배다.
SO-101 데모 셀(V19b `nominal-00`, 224틱, 1280×720, RTX 4090, `es video showcase`)에서 측정했고,
§8.4의 리드백은 여전히 모든 프레임에 들어 있다:

| 룩 | ms/프레임, 224프레임 교차 실행 |
|---|---|
| `lambert` | 6.7, 6.6 |
| `full` (`ssaa: 2`, 그림자 켬) | 10.1, 9.9, 9.9 |

광선이 8배인데 **+3.1 ms/프레임, 약 +46%** — 프레임이 광선에 묶여 있지 않기 때문이다. 이 숫자는
명령 전체의 벽시계 시간을 프레임 수로 나눈 것이고(테셀레이션, 업로드, 디스패치, 리드백, 디스크
쓰기), 다른 컴퓨트 프로세스가 올라와 있지 않은 카드에서 쟀다(`nvidia-smi`: 컴퓨트 앱 없음, P8, 0%).
배수가 광선 수보다 훨씬 작은 이유는 §8.4에 있다: 1280×720 프레임의 대부분은 리드백과 파일 쓰기이며,
R1b의 호스트 캐시 스테이징 버퍼가 이 카메라를 §8.3의 118.6 ms에서 `lambert` 행이 재는 6~7 ms로
끌어내린 것이다(§8.4의 R1b 실행은 같은 셀에서 6.2를 기록했다). `Rs`
스캔 자체는 그중 약 1 ms였고, `ssaa: 2`의 `Full`은 그것을 약 4로 만든다.

관측 크기인 96×96에는 이 중 어느 것도 해당하지 않는다: 관측 경로는 `Lambert`를, 오직 `Lambert`만
렌더링하므로(§9.5) 그 비용은 1나노초도 움직이지 않았다.

위 숫자는 수정된 혼합의 것이다; 에너지를 보존하는 데 드는 비용은 없고(덧셈 하나가 뺄셈 하나와
곱셈 하나로 바뀔 뿐), `show-full/000120.bin` 프레임에는 포화된 픽셀이 **하나도** 없다 — 덧셈
형태는 테이블 전체를 255로 남겼다.

## 10. 패스 트레이서가 자라다 (M7/R3)

`docs/packets/M7/R3-pt-quality.md`. 이 패킷 이전의 `Pt` 경로는 그림을 만들 수 없었다: next-event estimation이 없었고(바운스가 우연히 광원에 *착지해야만* 무언가가 밝아졌다), `ReSTIR`은 편향된 `1/M`으로 예비를 결합했으며, 출력은 톤 매핑 없는 선형 복사휘도여서 `Channel::Rgb8`이 `PT_CHANNELS`에 없었고 `es video showcase`가 이를 쓸 방법이 없었다(`visible-learning.md` 7.17 항목 5). 네 가지 추가가 있고, 각각은 기본값이 오늘의 바이트를 재현하는 `RenderConfig` 필드 뒤에 있다(§28.10 규칙 1) — `cargo xtask verify-goldens`는 **0 changed**를 보고하고, `tests/fixtures/visible-learning/frames` 픽스처는 손대지 않았다. 관측 경로가 이 필드들을 전혀 보지 못하기 때문이다([§9.5](#95-관측-경로에-이-옵션을-주지-않은-이유)가 그대로 적용된다: `EnvRendererCfg`에는 `nee`도 `exposure`도 `tonemap`도 없다).

### 10.1 Next-event estimation과 MIS

`Pt { nee }`, 기본값 `false`. 모든 디퓨즈 히트에서 추정자는 광원을 직접 샘플링하고 그 결과를 **power heuristic**(β = 2, PBR 4e 13.10)으로 BSDF 전략과 MIS 가중한다. 세 가지 광원 종류가 양쪽에서 하나의 코드 경로를 지난다:

| 광원 | 샘플링 방법 | MIS | 그림자 광선 |
|---|---|---|---|
| 이미셔티브 삼각형(`*_light` 이름의 geom) | 광원 목록에서 균일 선택 하나, 그다음 그 삼각형 위의 균일 점; 입체각 pdf는 `d² / (\|cos_l\| · A · n_lights)` | 예, `cos_s/π`에 대해 | 하나, `dist · (1 − 1e-3)`까지 |
| 방향광 `light_dir`, 복사휘도 `light_rgb`(신규, 기본 `[0,0,0]`) | 델타: 방향이 곧 `light_dir` | 아니오 — 가중할 pdf가 없다 | 하나, `SHADOW_FAR`까지 |
| 하늘 `sky`(미스는 여전히 이를 반환한다) | 코사인 가중 반구 방향 | 예, 그리고 pdf가 BSDF의 것과 같으므로 heuristic은 정확히 각 1/2을 준다 | 하나, 그리고 **탈출해야** 한다 |

`light_rgb`의 기본값이 0이므로 방향광을 요청하지 않은 `Pt` 렌더는 아무것도 기여하지 않는 광원을 얻는다; `sky`는 이미 0이 기본이었다. 세 가지 각각은 디스패치 전체에서 균일한 *설정*에 대한 `if`이므로, 픽셀당 작업량은 여전히 고정이다(§3.4가 금지하는 것은 데이터 의존적 루프 경계이지 컴파일 타임에 균일한 분기가 아니다).

**마지막 정점은 MIS 가중치를 버린다. 여기서 자명하지 않은 것은 이 하나다.** `bounce == bounces - 1`에서는 연속 광선이 샘플링되지만 추적되지 않으므로, 그 정점의 직접광 중 상보적인 `w_bsdf` 몫이 어디에서도 추정되지 않는다. 가중치를 남겨 두면 `B` 바운스의 NEE는 같은 `B`의 BSDF-only 트레이서보다 측정 가능한 만큼 *어둡다*; 버리면 `B` 바운스의 NEE는 BSDF-only 트레이서가 `B + 1`에서 추정하는 것과 정확히 같은 것 — 같은 경로 길이 집합 — 의 추정자가 된다. Cornell, 16×16, 4,096 spp에서 측정:

| 비교 | 이미지 평균의 차이 |
|---|---|
| NEE @ 3 바운스 vs NEE 없음 @ 3 바운스, 마지막 정점에도 MIS | **+3.72 %** (편향이 아니라 절단 차이) |
| NEE @ 3 바운스 vs NEE 없음 @ 4 바운스, 마지막 정점에서 MIS 제거 | **−0.45 %** |

`nee_converges_to_the_same_image`는 둘째 행이 1 % 미만임을 단언한다. 이 테스트는 패킷에서 두 번 벗어나며, 두 일탈은 같은 발견이다: `B` 대 `B`가 아니라 `B` 대 `B + 1`을 비교하고, 픽셀별 평균 절대 차이가 아니라 **이미지 평균**에 대해 단언한다. 4,096 spp에서도 각 추정자는 여전히 자신의 노이즈 ~0.0015를 지니고 있어서, 추정자들이 아무리 옳아도 픽셀별 수치는 평균의 3.0 %이기 때문이다. 픽셀별 수치는 단언 옆에 10 % 백스톱과 함께 출력되므로, 진짜 불일치 — 빠진 가중치, 틀린 pdf — 는 여전히 시끄럽게 실패한다.

**NEE가 사 오는 것**, `nee_at_low_spp_has_lower_variance`, Cornell 16×16, 16 spp, 3 바운스, 4,096 spp NEE 레퍼런스에 대한 RMSE:

| 추정자 | 16 spp에서의 RMSE |
|---|---|
| NEE 꺼짐 | 0.024110 |
| NEE 켜짐 | **0.016565** (1.46배 낮음) |

RMSE 1.46배는 같은 노이즈를 위해 ~2.1배의 샘플에 해당하며, 이는 유일한 광원이 코사인 바운스가 꽤 자주 찾아내는 큰 천장 패널인 씬에서의 수치다. NEE가 보통 자릿수 단위로 이기는 작은 광원은 커밋된 어느 씬에도 없다; 그 숫자는 `목표 / 상태: 미검증 (unverified)`이다.

### 10.2 이제 ReSTIR은 편향이 없고, 숫자는 이렇다

공간적 패스에 두 가지 변경:

1. **Pairwise MIS**(Wyman et al. 2023 §5)가 편향된 `1/M`을 대체한다. 정준(중심) 기법 `c`와 이웃 `N`개에 대해 `m_i(X) = (1/N)·(M_i p̂_i(X)) / (M_i p̂_i(X) + M_c p̂_c(X))`, `m_c(X) = (1/N)·Σ_i (M_c p̂_c(X)) / (M_i p̂_i(X) + M_c p̂_c(X))`이며, 이들은 *임의의* `X`에 대해 항별로 1이 된다. 후보의 재샘플링 가중치는 `m · p̂_destination(X) · W`가 되고 결합 기여 가중치는 `w_sum / p̂_destination(Y)`가 된다 — `m`들이 이미 정규화를 담고 있으므로 나눌 `1/M`도 `1/Z`도 남지 않는다. 이는 패킷의 `W = (1/p̂_y)·(w_sum/Z)`에서 `Z`를 후보별 가중치로 접어 넣은 형태이며, 샘플을 생성할 수 *있었던* 이웃에게 간신히 그럴 수 있었던 이웃보다 더 큰 가중치를 주는 형태이기도 하다(그럴 수 없었던 이웃을 제외하기만 하는 것이 아니라). 비용은 이웃당 타겟 함수 평가 세 번(자기 샘플에서의 자기 타겟, 그리고 정준 샘플에서의 자기 타겟)이며 추가 광선은 없다; 이웃의 셰이딩 점은 중심의 것과 같은 방식으로 g-buffer에서 온다.
2. **가시성 검사가 이동**했다. 초기 패스의 생존자에서, 목적지에서 최종적으로 선택된 샘플로. 픽셀당 그림자 광선은 여전히 하나. 이것이 중요한 이유는, *원본*에서 `W`를 0으로 만들면 이웃의 예비가 다른 셰이딩 점에서 결정된 가시성을 지니게 되기 때문이다. 목적지에서 검사하면 추정자는 비가려짐 타겟으로 만든 `W`에 대한 `f_shadowed(y) · W(y)`가 되고, 이는 편향이 없다. 예비는 **비가려짐** `W`를 저장하므로, 다음 프레임의 시간적 재사용도 여전히 타겟 함수가 정의된 양을 재사용한다.

`restir_is_unbiased_within_tolerance`: 독립적인 1 spp `ReSTIR` 프레임 256개(시간적 끄고 공간적 켬)를 평균하여, *같은 적분*의 4,096 spp 패스 트레이스와 비교한다 — 직접광만이며, 이는 NEE 없는 2 바운스다. `ReSTIR` DI가 추정하는 것이 그것이기 때문이다. Cornell, 16×16, 레퍼런스 평균 복사휘도 0.037287:

| 가중 방식 | 평균 | 편향 | 오라클 |
|---|---|---|---|
| `1/M` + 원본측 가시성 (**M7/R3 이전**) | 0.036631 | **−1.759 %** | 실패 |
| `1/M` + 목적지측 가시성 | 0.036616 | −1.798 % | 실패 |
| pairwise MIS + 목적지측 가시성 (**현재**) | 0.037324 | **+0.099 %** | 통과 |

가운데 행이 귀속이다: 편향의 본질적으로 전부가 `1/M` 가중치였고, 가시성 검사의 이동은 ~0.04 % 기여한다 — 256 시드 평균의 노이즈 안이다. 패킷 자신의 `미검증` TODO가 이제 양쪽에 숫자를 갖는다.

`gpu_restir_and_svgf_match_the_cpu_within_tolerance`는 1e-5 정규화 허용 오차를 유지하며 두 카드 모두에서 여전히 통과한다; 이 테스트는 GPU를 골든이 아니라 CPU에 대해 고정하며, 그것이 가중 방식 교체를 애초에 합법으로 만든 것이다.

### 10.3 톤 맵

`RenderConfig::{exposure, tonemap}`, 기본값 `1.0`과 `Tonemap::Reinhard`:

```
Reinhard(c) = (c·e) / (1 + c·e)                                    // Reinhard et al. 2002
Aces(c)     = clamp( x(2.51x + 0.03) / (x(2.43x + 0.59) + 0.14) )  // Narkowicz 2015, x = c·e
```

그다음 기존의 정확한 조각별 sRGB 전달 함수와 기존의 반올림. **두 연산자 어디에도 초월 함수가 없다** — 채널당 덧셈, 곱셈, 나눗셈 하나 — 따라서 오라클은 ULP 예산이 아니라 비트 동일성이다: `tonemap_is_bitwise_on_both_sides`는 64×64 Cornell `PtRadiance` 타일을 1 spp로 렌더링하고(`gpu_path_tracer_matches_the_cpu_reference_at_1spp`가 이미 비트 동일로 고정한 설정이므로 차이가 있다면 그것은 톤 맵의 것이다) 두 연산자 × 노출 1과 8로 통과시켜 `Rgb8`을 비교한다: 네 경우 모두 **12,288바이트 중 0바이트가 다르다**, RTX 3060에서도 RTX 4090에서도. 같은 테스트가 CPU에서 세 노출에 대해 `[0, 64)` 구간의 단조성을 단언하는데, 이것이 `Rgb8`을 룩업 테이블이 아니라 쓸 수 있는 이미지로 만드는 성질이다.

따라서 `Channel::Rgb8`이 `PT_CHANNELS`에 합류한다. GPU에서 이는 **별도 디스패치**인 `pt.slang`의 `tonemap` 엔트리 포인트이며, 마지막에 기록되므로 트레이서가 쓴 것이 아니라 `ReSTIR`과 `SVGF`가 복사휘도 버퍼에 남긴 것을 읽는다. CPU에서는 `cpu::path_trace`의 마지막 블록이다. 새 골든 하나, `cornell_pt_nee_rgb8`(4 spp, 3 바운스, NEE, Reinhard, 노출 1, CPU 레퍼런스가 생성): GPU는 두 카드 모두에서 이를 **비트 단위로** 재현하고, 바탕의 `PtRadiance`는 정규화 9.1e-7 / 216 ULP로 일치한다 — ULP 수치가 크고 정규화 수치가 작은 이유는 §5.1이 이미 말한 그것, 이미지의 대부분이 0 근처라는 것이다.

`Rs` `Full`에는 톤 맵을 **주지 않았다**. M7/R2에서 그랬듯 클램프하고, 골든은 손대지 않았다; 두 연산자는 `es_render::cpu`에서 `pub`이므로 나중 패킷이 자신의 골든과 함께 래스터라이저에 넘겨줄 수 있다.

### 10.4 §15.3의 SSIM 숫자가 마침내 존재하고, 그것은 낮다

`es_render::ssim(a, b, w, h) -> f64` — Wang et al. 2004의 단순 윈도우 형태: Rec.709 루마 평면 위를 한 픽셀씩 미끄러지는 8×8 윈도우, 균일 가중(11×11 가우시안이 아니다), `K1 = 0.01`, `K2 = 0.03`, `L = 255`, 윈도우별 점수의 평균, 전부 `f64`. `ssim(a, a)`는 `1.0 ± 1e-12`가 아니라 **정확히** `1.0`이다: 분산, 공분산, 두 평균이 동일 입력에서 분자와 분모를 같은 비트로 만들도록 작성되어 있다.

`rs_pt_ssim`(`--ignored` 측정이지 단언이 아니다)은 R2 프리셋(`ssaa 2`)의 `Rs` `Full`을 수렴된 `Pt` NEE 렌더와 비교하며 노출을 훑는다:

| 노출 | Cornell 64×64 SSIM | Cornell PT 평균 바이트 | SO-101 320×180 SSIM | SO-101 PT 평균 바이트 |
|---|---|---|---|---|
| 0.5 | 0.2282 | 23 | 0.2207 | 14 |
| **1** (기본) | **0.3247** | 33 | **0.2910** | 23 |
| 2 | 0.4246 | 47 | 0.3775 | 35 |
| 4 | 0.5099 | 65 | 0.4742 | 50 |
| 8 | 0.5646 | 87 | 0.5685 | 69 |
| 16 | 0.5861 | 112 | 0.6470 | 92 |
| 32 | 0.5865 | 140 | 0.7069 | 118 |
| 64 | 0.5861 | 168 | 0.7562 | 145 |
| 128 | 0.5912 | 193 | 0.8016 | 168 |

(`Rs` `Full` 자신의 평균 바이트는 Cornell에서 **130**, SO-101에서 **173**이다. Cornell은 1,024 spp의 CPU 레퍼런스이고, SO-101은 64 spp 청크 16개를 GPU로 돌려 호스트에서 평균한 것이다 — 단일 디스패치가 데스크톱 드라이버 워치독을 건드릴 수 없도록. 1,024 spp 단일 디스패치와는 다른 추정자이지만 똑같이 편향이 없고, 윈도우에서 돌아가는 유일한 것이다. 두 카드의 표는 마지막 자리까지 동일했다.)

**임계값은 여기서 정하지 않으며, 그 이유가 이 표다.** 기본 노출에서 두 이미지의 유사도는 0.29–0.32이고, 이는 실패처럼 보이지만 실패가 아니다: `Rs` `Full`은 상호반사가 없는 반구 앰비언트 + 방향광이고, `Pt`는 전역 조명이 있고 방향광은 아예 없는 ~1 W/sr/m²의 0.24 m 이미셔티브 패널 하나다. 둘은 *서로 다른 조명*의 그림이며, SSIM 결손의 대부분은 밝기 오프셋이다 — 점수는 Reinhard가 모든 것을 평탄화하는 지점까지 노출과 함께 단조롭게 오른다. 세 가지가 따라 나오고, 이것들은 이 패킷이 아니라 M7 리뷰의 결정이다:

1. 이 숫자들로 §15.3 임계값을 정하면, 그것은 렌더러가 아니라 씬의 조명 설정에 대한 임계값이 된다;
2. 정직한 비교는 `Pt` 측에 `Rs` 측의 광원을 준다 — `light_rgb`를 방향광의 복사휘도로, `sky`를 반구로 — R3은 이를 *가능하게* 했지만(§10.1의 광원 표) 조율하지는 않았다;
3. 또는 §15.3의 계약을 "기하 채널은 비트 동일하고 RGB는 조명 모델이 말하는 대로"로 다시 진술한다. 이것이 오늘 코드가 실제로 보장하는 것이다.

셋 중 하나가 선택되기 전까지 어떤 §15.3 SSIM 임계값도 `목표 / 상태: 미검증 (unverified)`이다.

### 10.5 `es video showcase --path pt`

```
es video showcase ... --path rs|pt [--spp 64] [--bounces 3] [--exposure 1.0]
                      [--tonemap reinhard|aces]
```

`rs`가 기본으로 남으므로 V9의 비트 동일성 오라클은 의미를 유지한다: 커밋된 런의 재렌더는 기록된 프레임을 재현한다. `pt`는 **NEE 켬, `ReSTIR`과 `SVGF` 끔**으로 돈다 — `ReSTIR`의 시간적 재사용은 움직이지 않는 카메라를 전제하는데, 쇼케이스는 궤적 전체를 재렌더한다. `es_env::render::config`는 여전히 렌더 경로가 `RenderConfig`가 되는 유일한 장소다; `--exposure`와 `--tonemap`은 M7/R2가 `shading`을 설정한 것과 같은 방식으로 `--look` 옆에서 반환된 설정에 적용된다. `--svgf` 플래그는 없다: 아무도 요청하지 않았고 필드는 Rust에서 접근 가능하다.

### 10.6 비용, RTX 4090, V19b `nominal-00` (224 틱, 1280×720)

같은 셀, 같은 카메라(`--eye 0.66,-0.46,0.52 --look-at 0.14,-0.04,0.04 --fov 36`), [§9.6](#96-비용)과 같은 교차 실행 방법 — 명령 전체의 벽시계 시간을 224 프레임으로 나눈 것이므로 테셀레이션, 업로드, 디스패치, 리드백, 디스크 쓰기가 모두 들어 있다.

**카드는 유휴 상태가 아니었다.** `nvidia-smi`는 내내 다른 컴퓨트 프로세스 6–7개를 보고했다(다른 에이전트의 학습); §9.6의 숫자는 그런 것이 하나도 없는 카드에서 잰 것이다. 아래 `lambert` 행은 §9.6의 3.0배이며 그것이 경합의 크기이고, 실행이 교차되어 있으므로 모든 행이 동등하게 그것을 지닌다. 따라서 절댓값은 카드의 능력이 아니라 **하한**이다:

| 경로 | ms/frame, 이번 실행(부하 있는 카드) | §9.6, 유휴 카드 |
|---|---|---|
| `Rs` `lambert` | 20.8, 20.0 | 6.7, 6.6 |
| `Rs` `full` (`ssaa 2`) | 25.0, 26.3 | 10.1, 9.9, 9.9 |
| `Pt` NEE, 64 spp, 3 바운스, Reinhard e=1 | **562.3, 561.2** | — |
| `Pt` NEE, 64 spp, 3 바운스, Reinhard e=32 | 560.8 | — |
| `Pt` NEE, 256 spp, 3 바운스, Reinhard e=32 | **2264.3** | — |

표가 말하는 세 가지. **톤 맵은 공짜다**: 562.3 대 560.8 ms/frame은 `exposure`만 다른 같은 숫자이며, 트레이서에서 0.5초를 쓰는 프레임에 픽셀당 곱셈 하나·덧셈 하나·나눗셈 하나짜리 디스패치 하나가 붙는 것이니 그래야 한다. **`spp`는 선형이다**: 샘플 4배가 시간 4.03배(2264.3 / 561.2)이므로 이름을 붙일 만한 프레임당 오버헤드가 없고, 호출자는 "내게 시간이 얼마나 있나"를 바로 읽을 수 있다. 그리고 **`Pt`는 같은 부하 카드에서 64 spp일 때 `Rs` `lambert`의 ~27.5배**다; 유휴 카드에서는 비율이 *더 커질* 것이다. 6.7 ms의 `lambert`는 대부분 리드백과 파일 쓰기인 반면 560 ms의 `Pt`는 거의 전부 트레이서이기 때문이다. 유휴 카드의 `Pt` 수치는 모두 `목표 / 상태: 미검증 (unverified)`이다 — 이번 실행의 정직한 독해는 "쇼케이스의 PT 경로는 4090에서 64 spp에 프레임당 0.5초이고, 64 spp는 눈에 띄게 노이즈가 있다; 프레임당 2.3초의 256 spp가 `~/artifacts/plan-v/m7-r3/show-pt-256/` 아래의 그림이다"이다.

### 10.7 R3이 여전히 건너뛰는 것

[§4.2](#42-restir-di)가 자신의 생략 목록을 두는 방식대로, 그리고 같은 이유로 — §1.9 항목 2가 패스 트레이서를 두 번째로 삭감되는 대상으로 만들므로, 그것의 모든 단계는 자신이 무엇이 아닌지를 말한다:

- **`ReSTIR` GI.** 여전히 직접광만. 간접 바운스는 패스 트레이스 추정자를 지나며, 그래서 `restir: true`와 높은 `spp`는 하나가 아니라 서로 다른 두 도구다.
- **나머지 두 광원 종류에 대한 `ReSTIR`.** 예비는 이미셔티브 삼각형만 담는다. 방향광과 하늘은 NEE 전용이다; 혼합 광원 목록에 대한 예비는 예비 스트라이드에 광원 *타입*이 필요하고, 이는 버퍼 레이아웃 변경이다.
- **환경맵.** `sky`는 코사인 pdf로 샘플링되는 상수 색 하나다. 진짜 환경맵은 이미지, 그 위에 구축된 중요도 샘플링 분포, 그리고 BSDF의 것이 아닌 pdf가 필요하다 — 바로 그 지점에서 여기의 MIS가 값을 하기 시작한다.
- **글로시/스페큘러 BSDF.** 모든 것이 여전히 램버시안이다. `Shading::Full`의 Blinn-Phong 하이라이트에는 `Pt` 대응물이 없고, 마이크로패싯 모델도 프레넬도 굴절도 완전 스페큘러 경로도 없다. 여기의 MIS 기계는 마이크로패싯 BSDF가 필요로 할 바로 그 기계이며, 그것이 지금 만들어 둔 이유다.
- **스펙트럼 관련 전부.** 세 채널, RGB, 파장 없음, 분산 없음, §3.1의 sRGB 전달 함수 이상의 색 관리 없음.
- **텍스처.** 여전히 geom당 평평한 알베도 하나(§0).
- **적응적 샘플링, 파이어플라이 클램핑, 러시안 룰렛.** 셋 다 작업량이나 추정자를 데이터 의존적으로 만들며, 비트 단위로 재현해야 하는 경로에서 §3.4가 이를 금지한다. 수렴된 이미지는 `spp`이고, `spp`는 고정된 숫자다.
- **`Rs` 경로의 톤 맵.** §10.3.
- **시간적 `ReSTIR` 패스는 여전히 우연히 편향이 없다**: 모션 벡터 재투영이 없으므로 두 후보가 하나의 셰이딩 점을 공유하고, 따라서 거기서는 `1/M`이 *실제로* 올바른 MIS 가중치다. 재투영을 주는 순간 공간적 패스가 받은 것과 같은 pairwise 처리가 필요해진다.

## 11. 정지 카메라를 위한 시간적 누적 (M7/R4)

`docs/packets/M7/R4-temporal-accumulation.md`. 쇼케이스 카메라는 움직이지 않고, 팔이 움직인다. 이 패킷 이전에는 모든 프레임이 샘플 0에서 시작했고, 그래서 224틱 셀은 매번 95%가 같은 그림인 장면을 224번 독립적으로 렌더링하는 값을 치렀다. 패킷이 묻는 것은 장면이 바뀌지 않은 픽셀에서 1 spp `N` 프레임이 `N` spp 한 프레임이 *될* 수 있는가 — 근사가 아니라 **비트 단위로** — 그리고 거기서 떨어져 나오는 픽셀당 분산이 마침내 [§4.3](#43-svgf)의 필터를 구동할 수 있는가다.

```rust
pub struct Temporal { pub max_history: u32 }
pub struct RenderConfig { ..., pub temporal: Option<Temporal> }   // 기본 None
```

`None`이 기본이고 그것은 오늘의 바이트다: `cargo xtask verify-goldens`는 **0 changed**에 1 added를 보고하고, `tests/fixtures/visible-learning/frames` 픽스처는 건드려지지 않는다 — 관측 경로가 이 필드를 설정하지 않기 때문이다([§9.5](#95-관측-경로에-이-옵션을-주지-않은-이유)가 그대로 적용된다; `EnvRendererCfg`에는 `temporal`도 없다).

### 11.1 정확함을 만드는 것은 샘플 인덱싱 규칙이다

카메라 슬롯의 프레임 `f`는 `rng::key`에서 `sample = f * spp + s`로 샘플을 뽑고, 커널의 누산기는 0이 아니라 **히스토리 합에서 시작한다**:

```
acc = history_sum * k                       // 상한 아래에서는 k = 1; 11.3 참조
for s in 0..spp:  acc += <샘플 f*spp + s>    // 큰 프레임 하나와 같은 좌→우 체인
sum := acc ;  n := n + 1
out  = sum * (1 / (n * spp))                 // 나눗셈은 마지막에 한 번
```

두 절반 모두 필요하다. 인덱싱은 `N` 프레임이 `N * spp` 한 프레임과 같은 샘플을 같은 순서로 뽑게 하고, 누산기를 히스토리 합에서 시작하는 것은 *덧셈*이 끊기지 않은 하나의 체인에서 일어나게 한다 — 부동소수점 덧셈은 결합법칙을 따르지 않으므로 `(a+b) + (c+d)`는 `((a+b)+c)+d`가 아니다. `accumulation_of_n_frames_is_n_spp`가 Cornell 64×64, NEE, 3 바운스에서 그 결과를 단언한다:

| 비교 | `PtRadiance` | `Rgb8` |
|---|---|---|
| 8프레임 × 1 spp vs 1프레임 × 8 spp | **비트 단위 동일** | **비트 단위 동일** |
| 8프레임 × 4 spp vs 1프레임 × 32 spp | **비트 단위 동일** | **비트 단위 동일** |

`f`는 픽셀의 히스토리 길이가 아니라 *슬롯의* 프레임 카운터이고, 이것이 패킷 문구(`n * spp + s`)와의 유일한 편차다. 히스토리가 한 번도 떨어지지 않은 곳에서는 둘이 같은 수이고 — 위 표가 고정하는 경우가 그것이다 — 픽셀이 다시 시작한 곳에서만 갈린다. 거기서 픽셀의 `n`을 쓰면 `max_history` 상한에 앉은 픽셀이 이미 가진 샘플을 매 프레임 다시 뽑게 되고, 수렴한 추정 대신 *한 프레임짜리* 추정으로 수렴한다. 카운터는 항상 앞으로 가고, 평균만 다시 시작한다.

### 11.2 유효성: 정지 카메라, 비트 단위 g-buffer, 재투영 없음

픽셀은 **둘 다** 성립할 때 히스토리를 유지한다:

1. 슬롯의 `CameraView`가 직전 프레임과 비트 단위로 같다 — 호스트가 `ViewParams` 16개 float를 비트 패턴으로 비교해 뷰 레코드의 패드 슬롯 13에 답을 쓰므로, 1 ULP 움직인 카메라는 그 카메라의 타일 전체를 리셋한다;
2. 픽셀 자신의 **깊이, 카메라 공간 노멀, 프리미티브 id**가 직전 프레임과 비트 단위로 같다.

아니면 그 픽셀은 `n := 0`이고 처음부터 시작한다. 모션 벡터 재투영은 없다: 히스토리를 다른 픽셀에서 리샘플하지 않으므로, 움직이는 카메라가 이 패킷에서 얻는 것은 리셋뿐이다. 이것이 디스오클루전 규칙 전부이며, 구조적으로 "장면은 움직이고 카메라는 멈춰 있다" 규칙이다.

프리미티브 id는 geom id가 아니라 **삼각형** 인덱스이고, 이는 들리는 것보다 엄격하다: `history_drops_where_the_scene_moved`는 4프레임 뒤 Cornell의 tall 블록을 0.6 m 이동시키고 4,096 픽셀 중 464가 떨어지고 3,632가 유지되는 것을 확인하는데, 464 중 일부는 같은 평평한 면 위에 머물렀지만 그 아래로 쿼드의 대각선이 지나간 픽셀이다. 그것들을 유지하려면 테셀레이터가 들고 있지 않은 면(face) 단위 id가 필요하고, 떨어뜨리는 비용은 실루엣 모양 경계에서 히스토리 한 프레임이다. 바뀐 `CameraView`는 모든 곳에서 `1`을 주며, 같은 테스트가 그것도 단언한다.

**규칙이 잡지 않는 것, 의도적으로:** 기하는 그대로인데 *조명*이 바뀐 픽셀 — 테이블을 가로지르는 팔의 그림자. 히스토리는 유지되고 지연이 생긴다. 그 지연을 제한하는 것이 §11.3이다.

### 11.3 상한은 리셋이 아니라 지수 이동 평균이다

`max_history`는 `n`의 상한이다. 상한에서는 히스토리를 버리는 대신 가장 오래된 프레임의 몫을 합(과 두 모멘트)에서 `k = (max_history - 1) / max_history`로 덜어내므로, 추정은 `alpha = 1 / max_history`의 지수 이동 평균이 되고 조명이 바뀐 픽셀은 약 `max_history` 프레임 안에 따라잡는다. 상한 아래에서는 `k`가 정확히 `1.0`이고 합은 정확하며, 그래서 §11.1의 표는 `max_history >= 8`인 어떤 값에 대해서도 비트 단위 주장이다.

상한에서 픽셀을 얼려 합을 영원히 정확하게 두는 선택지는 기각했다: 팔의 그림자가 테이블에 영영 나타나지 않는다.

### 11.4 분산, 그리고 그 평균이 말하지 못하는 것

픽셀마다 트레이서는 **프레임당** luminance의 1차·2차 raw 모멘트를 유지한다(`l`은 이 프레임 자신의 기여를 `spp`로 나눈 것이고, 누산기의 루프 전후 차이로 구한다 — 약 `n` ULP까지 정확하며, 이미지가 아니라 가중치로 들어간다):

```
var = max(0, E[l^2] - E[l]^2) / n                        // n >= 4: 모멘트
var = <누적 luminance의 7x7 깊이/노멀 가중 공간 분산> / n   // n < 4
```

추가 `/ n`은 논문이 아니라 패킷의 것이고 의도적이다: 필터에 필요한 것은 픽셀이 들고 있는 **평균**의 분산이지 한 프레임의 분산이 아니다. `n = 4` 아래에서는 모멘트가 너무 적어 값어치가 없어 논문의 공간적 추정이 대신 들어가고, 같은 이유로 `n`으로 나뉜다. 그래서 전환 지점에서 양이 연속이고 항상 "이 픽셀은 얼마나 불확실한가"를 뜻한다.

`variance_falls_with_history`, Cornell 64×64, 1 spp 프레임:

| n | 평균 | 중앙값 | p99 | 최대 |
|---|---|---|---|---|
| 1 (공간적) | 3.42e-3 | 4.50e-4 | 1.08e-1 | 1.91e-1 |
| 4 (모멘트) | 3.31e-4 | 2.45e-5 | 5.13e-3 | 2.44e-1 |
| 16 (모멘트) | 4.54e-3 | **2.32e-5** | **1.15e-3** | 1.79e+1 |

**평균은 떨어지지 않으며, 그래서 오라클은 중앙값과 p99에 대해 단언한다** — 패킷 문구와의 편차이고, 위 측정이 그 이유다. 1 spp 패스 트레이스는 꼬리가 무겁다: 4,096 픽셀 중 파이어플라이 한 픽셀이 `n = 16`에서 분산 17.9에 이르러 평균을 혼자 가져간다. `n` 프레임에서 얻는 `sigma^2` 추정도 `n`이 커질수록 참값을 향해 자라므로(4프레임은 보통 꼬리를 통째로 놓친다), 평균은 픽셀이 아니라 추정자 자신의 수렴을 재고 있다. 필터가 전형적인 픽셀과 나쁜 픽셀에서 실제로 겪는 값인 중앙값과 p99는 단조로 떨어지고, p99는 `n = 4`에서 `n = 16`까지 4.5배 떨어진다.

### 11.5 Luminance 가중치

`w_l = exp(-|l_p - l_q| / (sigma_l * sqrt(var_p) + eps))`, `sigma_l = 4`, `eps = 1e-10`, `w_depth * w_normal`에 곱해지고, 분산은 색상과 나란히 제곱 가중치로 필터링된다(`var_out = sum(w^2 var_q) / (sum w)^2`). `sqrt`는 IEEE 정확이라 허용되고, `exp`는 플랫폼의 것이 아니라 `es_math::approx`의 것이다(§3.4).

`luminance_weight_narrows_the_filter_where_variance_is_low`, 기하가 평평해서 깊이·노멀 가중치가 모든 곳에서 1인 합성 64×32 타일 — 왼쪽 절반은 분산 0에 4픽셀 줄무늬, 오른쪽 절반은 분산 0.25의 노이즈. à-trous 4회 반복 뒤 입력 대비 RMSE:

| 절반 | `w_l` 있음 | 없음 |
|---|---|---|
| 수렴(var 0) | **0.000000** | 0.490636 |
| 노이즈(var 0.25) | 0.285117 | 0.288394 |

수렴한 절반은 전혀 움직이지 않고 노이즈 절반은 전과 같이 필터링된다. SVGF의 V가 하는 일이 정확히 그것이다.

### 11.6 장치가 하는 일, 그리고 비트 단위 일치가 끝나는 지점

렌더러당 지속 버퍼 하나, 아틀라스 픽셀당 `HIST_STRIDE = 12` float(합 3, 모멘트 2, `n`, 직전 깊이·프리미티브 id·노멀, 분산), 할당 시 0으로 채움 — 디바이스 로컬 메모리는 초기화되지 않으며 쓰레기 `n`은 존재한 적 없는 샘플을 재사용하게 만든다(M4가 `ReSTIR` 버퍼를 0으로 채우는 것과 같은 이유). `pt.slang`이 유효성 검사·누적·모멘트를 하고, 새 `accumulate.slang`이 분산을 자기 dispatch에서 한다 — 짧은 히스토리 대체 경로가 7×7 이웃을 읽으므로 모든 픽셀의 누적 색상이 먼저 쓰여 있어야 하기 때문이다. `Channel::History`(`u32`, 이 프레임 이후의 `n`)가 `PT_CHANNELS`에 합류한다 — 스키마 변경이 아니라 진단이자 마스크다: Observation IR 노드는 이것을 읽지 않고, `temporal`이 `None`이면 모든 곳에서 `1`이다.

`gpu_accumulation_matches_the_cpu`, RTX 3060(드라이버 591.12, Slang 2026.8), 8프레임 × 1 spp:

| 비교 | 실측 |
|---|---|
| CPU `Rgb8` vs 새 골든 `cornell_pt_accum8_rgb8` | 비트 단위 동일 |
| GPU `Channel::History` vs CPU | **비트 단위 동일**(전부 8) |
| GPU `PtRadiance` vs CPU | 정규화 5.79e-7, 89 ULP |
| GPU `Rgb8` vs 골든 | **12,288 바이트 중 0개 차이** |
| GPU `PtRadiance` vs CPU, 분산 유도 SVGF 포함 | **6.99e-5** 정규화 |
| GPU `Rgb8` vs CPU, 분산 유도 SVGF 포함 | 12,288 바이트 중 0개 차이 |

`History` 채널이 "가깝다"가 아니라 비트 단위로 같은 이유는, 각 쪽이 **자기 자신의** 직전 프레임과 비교하는 g-buffer 위의 정수 논리이고 각 쪽은 프레임 간에 자기 자신과 비트 단위로 같기 때문이다([§7](#7-결정론-34)).

새 허용 오차가 필요했던 것은 끝에서 두 번째 행이다: **분산 유도 필터에 1e-3**, 유도 없는 필터는 1e-5를 지킨다. `exp(-|l_p - l_q| / (sigma_l * sqrt(var) + 1e-10))`은 분산이 작은 곳에서 입력에 대해 거의 불연속인 함수이므로, 두 패스 트레이서가 이미 벌어져 있는 ~1e-7([§10.3](#103-톤-맵): 216 ULP)이 몇 픽셀에서 다른 탭 가중치로 증폭된다. 그림은 영향을 받지 않는다 — 톤 맵된 바이트가 동일하다 — 그래서 의미 있는 단언은 `Rgb8` 행이고 정규화 값은 여유를 둔 상한이다.

### 11.7 비용과 쇼케이스

`es video showcase --path pt --accumulate [--max-history N]`(기본 32). 히스토리는 쇼케이스가 이미 틱마다 유지하는 `Renderer` 하나에 살고, 그래서 누적은 쇼케이스 자신의 프레임을 순서대로 누적한 것이다. `--accumulate`는 `pt` 플래그다: `--path rs`와 함께 요청하면 조용히 무시되는 대신 usage 오류다. `--accumulate`가 켜지면 픽셀당 히스토리 길이가 `<out>/history/NNNNNN.bin`(u32)으로 프레임 옆 자기 하위 디렉터리에 쓰인다 — 인코더가 훑는 프레임 glob이 절대 집어갈 수 없는 자리이고, 장면이 어디서 움직였는지의 마스크다.

RTX 4090, V19b `nominal-00`, 1280×720에서 224틱, [section 10.6](#106-비용-rtx-4090-v19b-nominal-00-224틱-1280720)과 같은 카메라·노출·교차 2패스 방법 — 명령 전체의 벽시계를 224프레임으로 나눈 값이므로 테셀레이션, 업로드, dispatch, 리드백, 디스크 쓰기가 모두 들어 있다. **이번 카드는 유휴였다**(`nvidia-smi`: 사용률 0%, 다른 컴퓨트 프로세스 없음; 1분 부하는 실행 전 0.00, 후 0.53). section 10.6의 카드는 아니었고, 그래서 64 spp 행이 여기서는 254 ms, 거기서는 562 ms다.

| 렌더 | ms/frame (1패스, 2패스) |
|---|---|
| `Pt` NEE, 64 spp — R3의 행 | 254.0, 254.6 |
| `Pt` NEE, 4 spp | 24.3, 23.6 |
| `Pt` NEE, 4 spp, `--accumulate --max-history 32` | **29.2, 28.5** |
| `Pt` NEE, 1,024 spp (SSIM 레퍼런스, 2프레임) | 4356.4 |

**누적의 비용은 4.9 ms/frame**이다 — 히스토리 읽기/쓰기, 분산 dispatch, 그리고 `History` 채널 자신의 리드백과 파일 쓰기(측정이 두 번 낼 필요는 없는 비용)까지 포함한 값이다. 64 spp 행 대비로는 8.7배를 번다.

그 대가로 얻는 화질은, 같은 틱(틱 120)의 1,024 spp NEE 레퍼런스에 대한 SSIM을 `History` 채널로 나눈 값이다: **static** = 921,600 중 `max_history` 상한에 있는 838,797 픽셀, **arm** = 히스토리가 4프레임 이하인 56,669 픽셀.

| 렌더 | SSIM, static 픽셀 | SSIM, arm 픽셀 | 프레임 전체 | 평균 바이트 |
|---|---|---|---|---|
| `Pt` 64 spp | 0.4369 | **0.5224** | 0.4386 | 119.5 |
| `Pt` 4 spp | 0.1623 | 0.1009 | 0.1544 | 81.5 |
| `Pt` 4 spp 누적 | **0.7547** | 0.1130 | 0.6990 | 118.4 |

이 표의 두 절반이 패킷의 답이자 그 비용이고, 둘 다 소리 내어 말할 가치가 있다. 장면이 바뀌지 않은 픽셀에서는 **29 ms/frame의 4 spp 누적이 254 ms/frame의 64 spp보다 SSIM 1.7배**다 — 배경은 8.7배 싸게, 눈에 띄게 더 좋게 수렴한다. 팔이 지나간 픽셀에서는 4 spp 이미지 그대로이고(0.1130 vs 0.1009) 64 spp가 여전히 4.6배 낫다: **누적은 배경을 사 주고, 이 장면의 주인공은 팔이다.** 둘 다 원하는 쇼케이스는 `--accumulate`와 함께 더 높은 `--spp`를 쓰거나, section 11.8이 갖고 있지 않은 재투영을 원하는 것이다. 평균 바이트가 같은 말을 반대편에서 한다: 4 spp 단독은 81.5인데 레퍼런스 근방은 118–120이다. Reinhard가 오목 함수라 픽셀당 노이즈가 프레임 평균을 *어둡게* 만들기 때문이고, 누적하면 118.4로 돌아온다.

그림은 `target/plan-u/r4/`에 있다: `pt-4-accum-000000/8/32/120.png`(히스토리가 차오르는 모습), `pt-64-tick120.png`, `ref-1024-tick120.png`, 그리고 마스크 자신인 `history-000120.png` — 팔의 깨끗한 실루엣과 그것이 끌고 다니는 흔적이다.

### 11.8 R4가 건너뛰는 것

- **재투영, 따라서 움직이는 카메라.** 가장 큰 하나. 움직이는 카메라는 매 프레임 완전 리셋을 받으므로 플라이스루에서 `--accumulate`는 아무것도 벌지 못한다. 필요한 조각은 모션 벡터(렌더러가 가진 것은 속도 버퍼가 아니라 직전 프레임의 포즈다), 히스토리의 바이리니어 리샘플, 그리고 같은 시점에 시간적 `ReSTIR` 패스가 필요로 할 pairwise 처리([section 10.7](#107-r3이-여전히-건너뛰는-것)의 마지막 항목)다.
- **히스토리 길이 기반 커널 확장**과 분산 프리필터 — [§4.3](#43-svgf)의 목록.
- **`ReSTIR`와 `temporal`의 결합.** `restir: true`는 누적이 라디언스 버퍼를 쓴 *뒤에* 그것을 직접광 추정으로 대체하므로 둘은 결합되지 않는다. 호출자가 둘 다 켜는 것을 막지는 않으며, 결과는 누적되지 않은 `ReSTIR` 이미지이고 `History` 채널은 여전히 프레임을 센다. 결합은 예비(reservoir)를 누적하는 것이고, 그것은 이 패스가 아니라 ReSTIR 자신의 시간적 패스다.
- **면(face) 단위 프리미티브 id**(§11.2), 그리고 *재질* 기반 유효성 검사: 여기서 평평한 한 면의 두 삼각형은 서로 다른 프리미티브다.
- **적응적 `max_history`.** 논문의 `alpha`도 고정이다; 시간적 그래디언트가 구동하는 픽셀별 `alpha`가 누구나 다음에 추가할 것이고, 그것은 결정론적으로 만들어야 할 데이터 의존 양이 하나 더 느는 일이다.

## 12. 관측 경로가 렌더 경로를 갖는다 (M7/R5)

패킷 `docs/packets/M7/R5-pt-observations.md`. 이 절 위의 모든 것은 *사람*이 보는 렌더러 이야기다. 이 절은 *정책*이 보는 렌더러 이야기이고, 답하는 질문은 소유자의 것이다: **PT 기반 학습은 없는가?** 없었다. 그리고 그 이유는 패스 트레이서가 아니었다 — [section 10](#10-패스-트레이서가-자라다-m7r3)이 NEE와 톤맵과 `Rgb8` 출력을 주었다 — 어떤 문서도 그것을 *요청할* 수 없었던 것이다. `EnvRendererCfg`를 만드는 세 곳(`es loop collect --frames`, `es eval run --frames`, `es video showcase`)이 `RenderPath::Rs`를 하드코딩했고, R3은 의도적으로 PT 노브를 그 config 바깥에 두었다([section 9.5](#95-관측-경로에-이-옵션을-주지-않은-이유)).

### 12.1 선언은 Task IR의 것이고, 쓰이기 전까지는 공짜다

`es_ir::task::ObsSource::Sensor`가 필드 하나를 얻는다:

```rust
SensorRender { path: Rs | Pt { spp, bounces }, exposure: f32, tonemap: Reinhard | Aces }
```

`ImageSpec`의 필드도 아니고 관측 IR의 필드도 아니다. 센서가 **무엇**인지 — 96×96, Rgb, sRGB, 이 내부 파라미터 — 는 `ImageSpec`의 것이고, 시뮬레이션이 그것을 **어떻게** 만드는지는 Task IR의 것이다. 이 분리가 하나의 관측 IR 그래프가 `Rs` 태스크와 `Pt` 태스크를 그대로 섬길 수 있게 하고, 여기서 `INV-14`가 문제가 되지 않는 이유이기도 하다: 리사이즈도 리스케일도 없다.

**부재 = 기본값 = 오늘의 정규형.** `ObsSource::canonical`은 `render != SensorRender::default()`일 때만 블록을 쓴다. 그래서 커밋된 모든 문서의 인코딩은 늘 그대로의 바이트 열이고 `task_hash eb6efefa…`는 움직이지 않는다 — `crates/es-ir/tests/sensor_render.rs`가 커밋된 `task.toml`에 대해 그 숫자를 단언하고, 기본값 블록을 손으로 써 넣어도(`render = { path = "rs", exposure = 1.0, tonemap = "reinhard" }`) 같은 해시가 나오는 것도 단언한다. 픽셀이 아니라 IR 필드에 적용된 §28.10 규칙 1이다.

`Pt` 센서는 `task_hash`를 움직이며, 그것이 요점이다: 다른 비교(§13.3)이므로 커밋된 문서로 조용히 심사받는 대신 자기 문서를 갖는다.

### 12.2 아무도 원하지 않았던 발견: 새 Task IR은 새 관측 IR을 끌고 온다

패킷은 `task-pt.toml`과 `evaluation-pt.toml`을 예상했다. 세 번째 문서가 필요하고, 이유는 취향이 아니라 구조다:

* `ObservationIr::task_ref`는 **해시 입력**이고(`crates/es-ir/src/observation.rs`),
* `XIR_001`은 `task_ref`가 태스크 자신의 해시와 같기를 요구한다.

그래서 §7.4의 "여러 관측 IR이 하나의 `task_hash`를 공유한다"에는 거울상이 없다: **하나의 관측 IR이 두 Task IR을 섬길 수는 없다.** `observation-pt.toml`의 그래프는 `observation.toml`의 것과 바이트 단위로 동일하고 — 모든 노드, 모든 포트, 모든 내부 파라미터 — 그럼에도 `observation_hash`는 다르다. 따라서 Task IR을 조금이라도 바꾸는 일은 하류 문서 집합 전체를 다시 발행한다. 해시 체인이 설계상 매기는 비용이고, 이 패킷이 그것을 온전히 지불한 첫 패킷이다.

### 12.3 함수 하나, 그리고 `Rs`는 비트 단위로 오늘의 것

`es_env::render::sensor_cfg(camera, spec, render, frames_dir) -> EnvRendererCfg`가 손으로 만들던 세 config를 대체한다. `Rs`는 `EnvRendererCfg::rgb(...)`에 **필드 단위로** 대응하고 — 오라클이 구조체 전체에 대한 `assert_eq!`라서, `EnvRendererCfg`에 필드가 추가되고 `sensor_cfg`에서 잊히면 여섯 달 뒤 골든이 아니라 지금 이 테스트가 깨진다 — 그 `RenderConfig`는 `tests/golden/render/so101_frame0`을 비트 단위로 재현한다. `Pt`는 R3의 추정기(NEE 켬, `ReSTIR`/`SVGF` 끔)와 **누적 없음**에 대응한다: R4의 `temporal`은 이 경로에서 일부러 `None`으로 남는다. 그래야 관측 프레임이 포즈의 순수 함수로 남고, 수집/평가 동등성 오라클(T7)이 `Rs`와 똑같이 `Pt`에도 성립한다.

그 결과로 `EnvRendererCfg`는 `exposure`와 `tonemap`을 얻지만, 그것은 **문서가 설정한 값의 통과 필드**이지 CLI 노브가 아니다. R3의 거절은 유효하다: `es video showcase --exposure`는 여전히 자유 카메라의 것이고, 쇼케이스의 씬 카메라가 센서를 따르게 하는 새 플래그 `--task`는 그 옆의 `--path`, `--spp`, `--bounces`, `--exposure`, `--tonemap`, `--look`, `--accumulate`, `--max-history`, `--width`, `--height`를 *거절한다* — 둘 중 하나가 조용히 이기게 두지 않는다.

### 12.4 비용, 두 카드에서 측정

`pt_observation_cost_and_ssim`(`crates/es-env/tests/render_loop.rs`, `--ignored`): 커밋된 `nominal-00.estraj` 궤적에서 고르게 뽑은 32틱, 96×96, 프레임 전체 벽시계(테셀레이션, 업로드, dispatch, 리드백), `EnvRenderer`가 그러듯 하나의 `Renderer`를 틱 사이에 유지.

| 렌더 | RTX 3060 (로컬) | RTX 4090 (오라클 서버) |
|---|---|---|
| `Rs` — 오늘의 관측 | 2.77 ms/frame | 2.90 ms/frame |
| `Pt` NEE, 64 spp, 3 bounces | **127.53 ms/frame** | **57.50 ms/frame** |
| 비율 | 46.0배 | 19.8배 |

**패킷의 "오라클 서버에서 96×96 64 spp 프레임 하나에 ~3 ms"는 19배 틀렸다.** 57.5 ms이고, 그 문장이 기억하고 있던 숫자는 아마 `Rs` 행이다. 200개 시연 × 약 185틱이면 V15의 5분에 대해 35분의 수집이고, 96개 평가 에피소드면 분이 아니라 시간 단위다. 여기 어느 것도 하지 말라는 이유는 아니다 — 시작하기 전에 값을 알라는 이유다.

`Rs` 행은 거의 전부 업로드와 리드백이다([section 8.4](#84-남은-것은-리드백이고-그것은-es-gpu의-몫이다)): 96×96 래스터화는 아무것도 아니고, 두 카드가 5 % 안에서 일치하는 것은 둘 다 일하고 있지 않기 때문이다. `Pt` 행은 트레이스이고, 거기서 4090은 3060의 2.2배다.

### 12.5 관측 해상도에서의 §15.3 SSIM 숫자

같은 32틱, 각 틱의 `Rs` 관측과 `Pt` 관측에 대한 `es_render::ssim`:

**평균 0.3547, 최소 0.3035, 최대 0.4227** — 그리고 **두 카드에서 소수 넷째 자리까지 동일**하다. §3.4의 결정론 주장이 부수 효과로 드러난 것이다: 두 GPU가 같은 바이트를 만들었다.

[Section 10.4](#104-153의-ssim-숫자가-마침내-존재하고-그것은-낮다)는 쇼케이스 카메라의 320×180에서 `Rs Full`과 `Pt` 사이 0.2910을 측정했고, 거기서 세운 임계값이 왜 렌더러가 아니라 장면 조명에 대한 임계값이 되는지 설명했다. 이것은 학습에 중요한 크기에서, `Full` 룩이 아니라 `Rs` **`Lambert`** 관측을 상대로 한 같은 이야기이며, 결론을 바꾸지 않는다. 어떤 §15.3 임계값도 여전히 `Target / Status: unverified`다. 이것이 더하는 것은, 예쁜 렌더 대신 정책이 읽는 렌더를 보기 시작해도 숫자가 나아지지 않는다는 사실이다.

`target/plan-u/r5/contact-sheet.png`은 전문가 시연 하나 전체(시드 1, 511틱, 그중 여덟 틱)를 `task.toml`과 `task-pt.toml`로 각각 한 번씩 수집한 것이며, `Rs` 행이 위, `Pt` 행이 아래다. 두 실행 모두 같은 데이터셋 `content` 다이제스트 `ef2e904d…`를 보고하므로 두 행은 정말로 같은 상태이고, 차이는 그것이 어떻게 그려졌는지뿐이다. 사람이 거기서 보는 것은 위의 어떤 숫자도 말하지 않는 것이다: **64 spp에서 패스 트레이싱된 관측은 눈에 띄게 거칠다.** 그 거칠기는 결정론적이므로(고정 `seed`, 픽셀로 주소 지정되는 샘플 키) 정책이 에포크를 거치며 평균 내어 없앨 수 있는 잡음이 아니라 포즈마다 고정된 패턴이다 — 증강보다는 텍스처에 가깝고, [visible-learning 7.32](visible-learning.ko.md)의 row U4가 무엇을 말하든 그 가장 유력한 이유다.

### 12.6 노출, 이 패킷이 내려야 했던 결정

패킷의 `task-pt.toml` 스케치는 `spp`와 `bounces`를 고정하고 `exposure`는 기본값 1.0에 두었다. 1.0에서 패스 트레이싱된 관측은 래스터화된 관측의 188 대비 **평균 바이트 34**다: 데모 셀에는 0.24 m 발광 패널 하나가 있고 `Pt` 경로에는 방향광이 없으므로, 정직한 그림은 어두운 그림이다. 그 위에서 정책을 학습시키는 일은 밝기 차이를 측정해 놓고 렌더 경로라고 부르는 일이 된다.

스윕, 한 틱, 모든 단, 같은 틱의 `Rs` 관측에 대한 SSIM:

| exposure | 1 | 2 | 4 | 8 | 16 | 32 | **64** | 128 |
|---|---|---|---|---|---|---|---|---|
| 평균 바이트 | 34 | 49 | 69 | 94 | 123 | 154 | **184** | 209 |
| `Rs` 대비 SSIM | 0.1798 | 0.2351 | 0.2866 | 0.3296 | 0.3608 | 0.3845 | **0.4143** | 0.4655 |

`exposure = 64`가 평균 바이트(184)를 래스터화된 관측(188)에 가장 가깝게 두는 단이므로 **`task-pt.toml`은 64를 선언하고**, 패킷과의 차이는 여기 기록한다. SSIM 열은 그 너머로도 계속 오르는데 section 10.4가 말하는 이유 — Reinhard가 모든 것을 평평하게 만든다 — 때문이고, 노출을 SSIM이 아니라 평균 바이트로 고른 이유가 정확히 그것이다.

### 12.7 R5가 건너뛰는 것

- **`Rs`의 조명을 가진 `Pt` 센서.** [Section 10.4](#104-153의-ssim-숫자가-마침내-존재하고-그것은-낮다)의 선택지 2(패스 트레이서에 래스터라이저의 방향광과 반구 조명을 주어 SSIM이 조명이 아니라 렌더러에 관한 것이 되게 하기)는 여전히 튜닝되지 않았다. `light_rgb`와 `sky`는 Rust에서는 닿지만 문서에서는 닿지 않는다; 그것을 `SensorRender`에 올리는 것이 다음에 추가할 명백한 필드이고, 아무도 요청하지 않았다.
- **관측 경로에서의 누적**, 의도적으로 (section 12.3).
- **두 번째 이미지 채널.** `--frames`는 여전히 정확히 하나만 렌더하므로, IR이 담을 수 있음에도 "센서 하나는 `Pt`, 하나는 `Rs`"는 끝까지 표현되지 않는다.
- **자유 카메라에 관한 어떤 것도.** `es video showcase --path pt`는 그대로다.

### 12.8 샘플 시드가 에피소드의 틱을 따라 움직일 수 있다 (M10/W1a)

R5는 아무도 요청하지 않은 성질을 남겼다. `RenderConfig::seed`는 상수 `0x5eed_1234`이고 관측 경로에는 누적이 없으므로(section 12.3) 호출마다 `frame == 0`이며, 샘플 키 `rng::key(seed, view, px, py, sample, bounce, stream)`는 **(픽셀, 포즈)의 순수 함수**다. 64 spp에서 그것은 정책이 에폭에 걸쳐 평균 내어 없앨 수 있는 잡음이 아니라, 포즈가 입고 있는 고정된 텍스처 — 그 포즈를 방문할 때마다 똑같은 것 — 이다. U4 행(`visible-learning.md` 7.32)은 래스터화된 U3보다 *더 낮은* 손실까지 학습하고도 held-out 16개 중 0개, 자기 학습 시드 16개 중 1개를 기록했다. 텍스처를 지문으로 쓰면 그렇게 보인다(`docs/reviews/M7.md` R13).

**선언.** `SensorRender`가 필드 하나를 얻는다: `seed = "fixed" | "tick"`(§6). `fixed`가 기본값이고, 부재가 기본값이며, 기본값은 오늘의 바이트다 — 그래서 `task.toml`(`86a7f3a3…`)과 `task-pt.toml`(`02036847…`)의 `task_hash`는 움직이지 않고 U4 행의 숫자는 측정된 그 문서들에 관한 것으로 남는다(`cargo test -p es-ir committed_task_hashes_are_unmoved_by_seed_stream`, §28.10 규칙 1). `tick`은 해시를 움직이므로 새 문서 `task-pt-tick.toml`(`51b60dad…`)이 되고, section 12.2가 말하는 이유로 그 뒤에 자기 관측 IR과 평가 IR을 끌고 온다.

**메커니즘은 곱셈 하나다.** `es_env::render::frame_seed`가 그 산술이 사는 유일한 곳이다:

```rust
match stream {
    SeedStream::Fixed => base,                                  // 건드리지 않음, 오늘의 바이트
    SeedStream::Tick  => es_render::rng::mix32(base ^ tick),    // Murmur3 fmix32,
}                                                               // 샘플 키 자신의 믹서
```

그리고 `Renderer::set_seed`가 다음 `render` 전에 파라미터 버퍼의 슬롯 `p[13]`을 다시 쓴다. 아무것도 재빌드하지 않는다 — 시드는 파이프라인의 일부가 아니라 *파라미터*다 — 그리고 CPU 레퍼런스가 같은 `RenderConfig::seed`를 읽으므로 시드가 바뀌어도 CPU/GPU 동일성은 그대로다(`cargo test -p es-render gpu_path_tracer_matches_the_cpu_reference_after_set_seed`). 데모의 96×96 센서에서 측정: 고정된 포즈 하나의 틱 0과 틱 1은 **27,648바이트 중 26,927바이트**가 다르고, 같은 `(포즈, 틱)`을 두 번 렌더하면 비트 동일하다(`cargo test -p es-env --features render pt_seed_varies_per_tick_and_is_reproducible`).

**어떤 틱이고, 각 단계는 그것을 어디서 얻는가.** 에피소드 상대 **렌더 인덱스**다: 에피소드를 여는 리셋에서 0, 렌더된 제어 스텝마다 +1. env의 누적 물리 시계가 아니다 — 그것은 같은 `Env`가 이미 몇 에피소드를 돌았는지에, 따라서 런이 어떻게 스케줄되었는지에 의존하며, M7/R1이 `StepEvent::tick`을 꺼낸 바로 그 함정이다. 문서를 렌더하는 세 단계는 그것을 서로 다른 세 곳에서 읽지만, 각각이 같은 그 인덱스이므로 일치한다:

| 단계 | 틱 0이 오는 곳 |
|---|---|
| `es loop collect --frames` | 에피소드의 첫 제어 스텝 전에 방출되는 `CollectEvent::EpisodeBegin`이 `EnvRenderer::begin_episode`를 호출한다 |
| `es eval run --frames` | 백엔드 시계가 0을 읽는 순간. `(cell, episode)` 분할(M8/S1) 이후 셀당 정확히 한 번 일어난다: 러너가 **에피소드마다 `Env` 하나**를 만든다 |
| `es video showcase --task` | `.estraj`의 행 인덱스 — 궤적 하나가 에피소드 하나이므로 행이 곧 런이 렌더한 틱이다 |

마지막 행이 `seed = "tick"` 런의 리플레이가 프레임을 다시 노이즈 내는 대신 재현하게 만드는 것이다.

**12.8이 건너뛰는 것.**

- **누적, 여전히**(12.3). `Temporal`은 하나의 시드에서 뽑은 프레임들을 평균한다; 둘은 결합하지 않으며, `Renderer::set_seed`는 그것을 막는 대신 문서에 적는다 — 관측 경로에는 충돌할 누적이 없다.
- **`observation_delay` 아래의 정렬.** 평가기는 제어 스텝이 아니라 *렌더*를 센다. 그래서 관측을 떨어뜨리는 스위트는 같은 스텝의 수집기보다 시드를 느리게 전진시킨다. 내부적으로 일관되고 재현 가능하지만 같은 번호 매김은 아니며, 데모의 수집은 관측을 떨어뜨리지 않는다.
- **스트림 id.** 틱은 `rng::key`의 자기 좌표를 받는 대신 시드에 섞인다. 좌표가 더 단정한 설계였겠지만 Slang 쪽(`rng.slang`)을 맞물려 고쳐야 했을 것이다; 시드를 섞는 것은 비용이 없고, 다른 `RenderConfig::seed`로 같은 장면을 렌더하는 것과 비트 동일하며, 그것은 CPU 레퍼런스가 이미 할 줄 아는 일이다.

### 12.9 센서가 SVGF를 선언할 수 있다 (M11/X6)

§28.14 규칙 5는 `Pt` 관측의 노이즈를 선언된 문서 필드로만 다룬다고 말한다 — `render.seed = "tick"`(12.8)과 `render.svgf` — 관측 경로의 누적이나 벤더 디노이저로는 결코 다루지 않는다. 이것이 두 번째 필드다.

**선언.** `SensorRender`가 `svgf: bool`을 얻는다. 기본값은 `false`이고, 정규 형식에는 **`true`일 때만**, `seed` 뒤에 쓰인다 — 12.8의 규칙을 한 번 더. `task.toml`(`86a7f3a3…`), `task-pt.toml`(`02036847…`), `task-pt-tick.toml`(`51b60dad…`)의 `task_hash`는 움직이지 않고, `svgf = false`를 명시해도 부재와 같은 해시이며, `true`는 해시를 움직인다(`cargo test -p es-ir committed_task_hashes_are_unmoved_by_svgf`). `Rs` 센서의 `svgf = true`는 검증 오류 **`TASK-003`**이다: 래스터라이저에는 거를 노이즈가 없고, 조용히 아무것도 하지 않는 필드라도 해시는 움직였을 것이다. 새 문서는 `task-pt-tick-svgf.toml`(`3249363e…`), `observation-pt-tick-svgf.toml`(`2ecd5ddf…`), `evaluation-pt-tick-svgf.toml`(`06122b67…`)이며 `generate_pt_fixtures`가 `task-pt-tick.toml`에서 생성한다; 두 태스크 문서의 차이는 `svgf = true` 한 줄이다.

**매핑.** `sensor_cfg`가 필드를 `RenderPath::Pt { svgf }`로 복사한다; `svgf_iterations`는 `RenderConfig`의 기본값(4)에, `temporal`은 `None`에 머문다. 히스토리가 없으면 필터의 휘도 가중치는 정확히 `1.0`을 곱하는 것이므로(4.3절), 실행되는 것은 한 프레임 위의 M4 깊이/법선 에지 정지 à-trous 필터다 — 그 프레임의 radiance와 g-buffer의 순수 함수. SVGF의 커널과 상수는 바뀌지 않았다. `es video showcase --task`는 `sensor_cfg`를 거치므로 문서를 따른다.

**비용, 그리고 여전히 비트 단위인가.** 데모의 96×96 센서, `seed = "tick"`, 고정 포즈 하나에서 `cargo test -p es-env --features render --test render_loop pt_svgf_sensor_`:

| 주장 | RTX 3060 (로컬) | RTX 4090 (오라클 서버) |
|---|---|---|
| 수집기 경로(렌더러 하나, 이전 에피소드, `begin_episode`) == 평가기 경로(새 렌더러), 틱 0..2 | 비트 동일 | 비트 동일 |
| GPU == CPU 레퍼런스(`cpu::path_trace`, 같은 설정, 틱 1 시드), `Rgb8` | **27,648바이트 중 0 다름** | **27,648바이트 중 0 다름** |
| 같은 `(포즈, 틱)`에서 SVGF 프레임 vs 필터 없는 프레임 | 27,648바이트 중 26,722 다름 | 27,648바이트 중 26,722 다름 |
| `EnvRenderer::frame`, `Pt` 64 spp NEE | 133.6–134.6 ms/frame | 64.8–65.1 ms/frame |
| … + SVGF | 134.9–135.0 ms/frame | 68.6–69.0 ms/frame |
| SVGF 오버헤드 | +0.3–1.3 ms (≤ 1 %) | +3.8–3.9 ms (5.8–5.9 %) |

워밍업 후 16프레임의 프레임 전체 벽시계, 디버그 빌드, 세 번 실행; 다른 GPU 작업과 겹친 3060 실행 하나(162.6 / 190.3 ms)는 제외했다. 필터는 9,216픽셀 위의 à-trous 디스패치 네 번으로, 픽셀당 64 샘플 × 3 바운스 옆에 있다. 4090 실행은 ±0.2 ms 안에서 안정적이었고 필터를 일정한 ~3.8 ms로 잡았다; 3060에서는 같은 ms 단위의 비용이 두 배 느린 트레이스의 실행 간 편차 안에 묻힌다. 어느 쪽이든 프레임의 몇 퍼센트이며, 끄고 둘 이유는 아니다. 이 두 카드 밖의 것은 `Target / Status: unverified`.

**12.9가 건너뛰는 것.**

- **정책에 도움이 되는가.** 그것은 U6 행(§28.14 웨이브 1 행 3: U5 + `svgf = true`, 학습 시드 두 개)이며, 이 패킷이 돌리지 않는 서버 런이다.
- **분산 유도 휘도 가중치.** 히스토리가 필요하고, 관측 경로의 히스토리는 12.3이 거부하는 누적이다. 단일 프레임 SVGF는 에지 인식 스무딩이지 분산 유도 디노이징이 아니다.
- **문서 필드로서의 `svgf_iterations`.** 4가 기본값이고 다른 숫자를 요청한 사람이 없다; 필드는 고정해야 할 해시 입력 하나를 더할 뿐이다.
- **센서의 `ReSTIR`**, CPU와 1e-5 이내로 일치하지만 비트 단위는 아니다(`gpu_restir_and_svgf_match_the_cpu_within_tolerance`).

## 13. 렌더 시점의 시각 랜덤화 (M11/X5)

패킷 `docs/packets/M11/X5-visual-dr.md`, spec 28.14 규칙 4. 오너는 비전 RL을 위한 Task IR `Randomization` 타깃으로 조명(세기, 방향, 색, 앰비언트), 지오메트리 색, 카메라 외부 파라미터와 내부 파라미터를 골랐다. 문법과 추첨은 `batch-domains.md` 5절이다. 이 절은 추첨이 프레임에 하는 일이다.

### 13.1 `Pt` 경로에는 이미 방향광이 있었다; 어떤 문서도 닿지 못했을 뿐

`docs/reviews/M10.md` S-6은 `Pt` 센서에 방향광이 없어 `light_direction`이 거기서 아무것도 측정하지 않는다고 한다. *렌더러*에는 R3부터 있었다: `RenderConfig::light_rgb`는 `light_dir` 쪽 델타 광원의 복사휘도이고, 발광 삼각형과 하늘 옆에서 NEE로 추정된다(10.1절; `common.slang`의 `es_nee_direct`와 `cpu.rs`의 미러, 그림자 광선 하나, BSDF 샘플은 델타 광원에 맞을 수 없으므로 MIS 없음). 기본값은 0이고 `sensor_cfg`는 그것을 설정한 적이 없다. 그래서 X5는 **셰이더 항을 추가하지 않는다**: `light.radiance`(흰색 복사휘도; `Constant`는 선언, 그 밖의 분포는 랜덤화)가 `light_rgb`를, `light.sky`가 `sky`를 설정하며, 둘 다 선언하지 않은 문서는 오늘의 바이트를 렌더한다. 둘 다 `Rs` 센서가 있는 태스크에서는 거부된다 — 래스터라이저에는 둘 다 없다.

`dr_pt_directional_light_lights_a_dark_scene`: 천장 패널을 끈 코넬 박스는 `Pt`에서 검다(4,096픽셀 중 0이 아닌 것 0개). 열린 끝으로 태양을 비추면 1,577개가 밝아지고, GPU도 같은 1,577개를 0 ULP로 밝힌다. 데모의 96×96 `Pt` 센서(4 spp, 2 바운스, 노출 64)에서 뽑힌 태양은 평균 바이트를 119.8에서 ~244로 올린다(`dr_env_pt_sensor_gets_a_directional_light`).

### 13.2 세기와 색, 경로별

의미는 하나 — *모든 광원의 복사휘도에 `intensity * color`를 곱한다* — 이고 정확한 구현은 둘이다. 두 경로가 서로 다른 것에 선형이기 때문이다:

| 경로 | 무엇을 곱하나 | 왜 정확한가 |
|---|---|---|
| `Rs` | 모든 삼각형의 albedo **와** emission | `albedo * (ambient + n.l (1 - ambient)) + emission`은 채널별로 albedo에 선형이고, 발광체의 emission은 곧 그 albedo다(`TriScene`) — `LightOverride::scene`이 이미 했던 논증을 채널별로 |
| `Pt` | emission, `light_rgb`, `sky`; albedo는 그대로 | 렌더링 방정식은 광원에 선형이다. albedo까지 곱하면 매 바운스마다 이득이 또 곱해진다(평가기의 `LightOverride`가 달고 있던 `ponytail:` 메모) |

`geom.<n>.rgba`는 두 경로 모두에서 그 지오메트리의 albedo와 emission을 곱한다(색이 바뀐 발광체는 새 색을 낸다). 모든 배율은 지오메트리별 캐시 다음, 테셀레이션된 `TriScene`에 `f32`로 적용되므로 프레임마다 `SceneDesc`를 복제하지 않는다. 평가기의 `light_intensity` 섭동은 `LightOverride::scene`(테셀레이션 전 `rgba`의 `f64` 편집)을 유지한다 — 타입은 그대로 `es-env`로 옮겨졌고 커밋된 모든 보고서는 바이트 단위로 같다 — 그래서 같은 그림으로 가는 두 길은 반올림이 다르며 비트 단위 일치를 단언하지 않는다.

### 13.3 방향과 앰비언트

`light.direction.yaw`는 평가기의 커널 그대로인 `LightOverride::rotate_dir`(`+Z`에 대해, `approx::sin`/`cos`)이다. 그다음 `light.direction.pitch`가 광원을 그에 수직인 수평축(`h = z × d / |z × d|`, `h (h·d)` 항이 0인 로드리게스) 둘레로 돌려, 양의 각에서 `+Z` 쪽으로 올린다. 바로 머리 위의 광원은 그런 축이 없어 그대로 둔다. 두 경로 모두 `light_dir`를 읽으므로 방향은 `Rs`와 `Pt`를 똑같이 움직이는 유일한 추첨이다 — 그리고 `light.radiance`가 선언되면 `Pt` 센서에도 드디어 `light_direction`이 돌릴 것이 생긴다.

`light.ambient`는 `Rs`에서 `RenderConfig::ambient`를 곱하고(Lambert 혼합이 `a + n.l (1 - a)`이므로 `[0, 1]`로 클램프; `Full`의 반구 색도 마찬가지) `Pt`에서는 하늘을 곱한다(빛 이득도 함께 곱해, `intensity`가 여전히 모든 광원을 곱하도록).

### 13.4 카메라, 그리고 하나의 발견

`camera.<n>.pose.*`는 카메라의 `OpenCV` 포즈 오른쪽에 포즈를 합성한다(카메라 자신의 축을 따른 이동; yaw, pitch, roll 순서, `approx` 사용). `camera.<n>.fov`는 주점을 중심으로 `fx`, `fy`에 초점 배율을 곱한다. 에피소드의 `image_specs`도 같은 숫자를 지닌다(`INV-14`, `batch-domains.md` 5절).

**뽑힌 포즈가 어떤 골든도 드러낼 수 없던 GPU/CPU 불일치를 드러냈다.** RTX 3060에서 `Pose` 추첨의 첫 실행은 `Rgb8`과 세그멘테이션은 비트 단위로 맞았지만 **깊이 901픽셀이 최대 20 ULP** CPU와 어긋났다. 모든 골든 카메라의 쿼터니언 성분은 2의 거듭제곱이다(`LOOK_ALONG_X`는 ±0.5, 데모의 `MJCF_TO_OPENCV`는 `(1, 0, 0, 0)`). 그래서 `es_qrot`의 모든 곱이 정확했고 반올림 순서는 문제가 되지 않았다. 뽑힌 카메라는 임의의 성분을 가진다. `es_qrot`는 드라이버가 구현하는 확장 명령 GLSL.std.450 `Cross`를 불렀고, `NoContraction`은 *우리의* 산술을 장식할 뿐 드라이버의 것은 아니다 — 그 안에서는 융합이 자유였다. 이제 `es_qrot`는 CPU의 `cross`처럼 세 차이를 항 단위로 풀어 쓴 `es_cross`를 부르고, 뽑힌 카메라는 모든 채널에서 **0 ULP**다. 커밋된 프레임은 하나도 움직이지 않았다: 골든 카메라에서는 두 형태가 같은 비트다(기존 골든 전부와 `so101_frame0`이 두 카드에서 다시 통과). `common.slang`의 나머지 `Cross` 호출 둘(Möller–Trumbore와 면 법선)은 삼각형 변을 받으며, 여기서 어떤 테스트도 그것을 움직이지 않았으므로 그대로 둔다(13.7).

### 13.5 `set_lighting`과 프레임별 계약

`Renderer::set_lighting(&RenderConfig)`는 `light_dir`, `light_rgb`, `ambient`, `sky`, `shading`을 렌더러의 설정으로 복사한다 — 파라미터(슬롯 6..13, 20..31, 32..35)일 뿐 파이프라인이 아니므로 에피소드별 추첨에 커널 컴파일 비용이 없다. `dr_set_lighting_is_a_parameter`: 기본 렌더러를 다시 밝히면 뽑힌 설정으로 만든 렌더러와 `Rs`, `Pt` 모두 비트 단위로 같은 것을 렌더하고, 기본값으로 되돌리면 다시 `cornell_rs_rgb8`을 렌더한다. `EnvRenderer::frame_with(model, state, env, &RenderOverrides)`는 매 프레임 `drawn_frame`과 `set_lighting`을 돌리고 아무것도 남기지 않는다: `frame`은 항등의 `frame_with`이고, 항등은 `frame`이 전에 쓰던 입력 그대로로 단락되므로 커밋된 모든 프레임은 그대로다(`dr_env_frames_follow_the_draws_gpu_equals_cpu`가 추첨 없는 경우와 `frame()`을 `so101_frame0`에 대어 렌더한다). 카메라 추첨이 있는 프레임은 사이드카에 `intrinsics`를 쓴다(`Tile::write_to_with_intrinsics`). 없는 프레임은 늘 쓰던 사이드카를 쓴다.

### 13.7 X5가 건너뛰는 것

- **수집기와 평가기는 아직 추첨을 적용하지 않는다.** `es loop collect --frames`와 `es eval run --frames`(`crates/es/src/cmd/`)는 X5의 범위 밖이며, 렌더 타깃이 있는 태스크에서도 추첨되지 않은 장면을 렌더한다. 고치는 방법은 수집기에서 `env.render_overrides(env)`를 `frame_with`에 넘기고, 평가기의 프레임 소스에 `RenderOverrides`를 접어 넣는 것이다. X7이 학습하는 RL 경로인 `Rollout`은 적용한다.
- **배치 렌더링 (X3b).** `RenderOverrides`는 env별 평범한 구조체이고 `drawn_frame`은 그것의 순수 함수지만, 조명 절반은 *설정* 단위다: 한 디스패치에서 N개 env가 N개 조명을 가지려면 뷰별 조명 파라미터가 필요하고, 그것은 X3b가 정할 파라미터 배치다(정했다: 14.1절).
- **나머지 두 `Cross` 내장 함수** (13.4).
- **텍스처, 재질, 가림체** — M7 R6과 패킷의 `forbidden`.
- **HSV 지오메트리 지터, 그리고 `Full`의 스펙큘러 항의 색** — 채널별 배율이 고른 방식이다(`batch-domains.md` 5). `Full`의 Blinn-Phong 하이라이트는 흰색으로 남는다.

## 14. 하나의 디스패치에 담긴 N개의 env (M11/X3b)

패킷 `docs/packets/M11/X3b-batched-render.md`, spec 28.14 파동 2, 15.2. X3 이후 `Rollout`은 각 env를 자신의 `EnvRenderer`로 렌더했다 — env마다 업로드 하나, 디스패치 하나, 리드백 하나 — RTX 4090에서 96×96 64-spp `Pt` 프레임 한 장에 57.5 ms(12.4). 1절의 아틀라스는 이미 *한 장면 위의 여러 카메라*를 한 디스패치에 담는다. X3b는 타일을 **env**로 만든다: 각자 자기 포즈의 장면, 카메라, 빛, 시드를 갖고, 각 타일은 그 env의 단일 렌더와 비트 단위로 같다.

새 진입점은 `Renderer::render_batch(&[(TriScene, CameraView, RenderConfig)])`이며, 인자는 `es_env::render::drawn_frame`이 돌려주는 바로 그 세 쌍이다. `Atlas::read_tiles`는 한 채널의 모든 타일을 다운로드 한 번으로 읽는다. `es_env::render::EnvBatchRenderer`는 배치판 `EnvRenderer`이고(env별 `Tick` 시계, env별 추첨, 공유 `SceneCache` 하나), `Rollout`은 env가 둘 이상이면 그것을 쓴다. `Renderer::render`와 `EnvRenderer`는 바뀌지 않았고 오라클로 남는다.

### 14.1 파라미터 배치: env마다 전역 블록의 사본

두 env 사이에서 다른 것은 장면(삼각형과 트리가 어디 있는지), 빛(`light_dir`, `light_rgb`, `ambient`, `sky`, `shading` — `set_lighting`이 옮기는 것), 그리고 시드다. 전부 *전역* 슬롯이었다. 모든 접근자에 뷰 인자를 새로 배관하는 대신, 배치 렌더는 뷰 레코드 뒤에 **env마다 전역 블록 전체의 사본 하나**를 같은 배치로 덧붙이고, 각 뷰 레코드는 패드 슬롯 14에 자기 env의 사본 위치를 적는다. 셰이더는 env별 슬롯을 `es_env_f(i) = es_params[es_env_base + i]`로 읽는데, `es_env_base`는 `es_pixel`이 뷰 레코드에서 한 번 설정하는 스레드 전용 static이다. 단일 렌더는 거기에 0을 쓰므로 접근자는 예전과 똑같이 전역 자체를 읽는다. 새 슬롯은 둘이다: 39는 `es_tris` 안의 env 삼각형 시작 위치(`es_tri`와 `es_light_tri`가 더한다), 40은 14.5의 밴드 행이다. `PARAM_VIEW_BASE`는 39에서 41로 옮겨졌고, 그것에 의존하는 출력은 없다.

샘플 키에는 하나가 더 필요했다. `es_rng_key`는 **뷰** 인덱스로 주소가 매겨지는데, 배치에서 env `k`는 타일 `k`이고 그 단일 렌더는 뷰 0이다. 패드 슬롯 15가 키 뷰를 나른다 — 단일 렌더에서는 타일 자신의 인덱스(그래서 다중 카메라 아틀라스는 예전 그대로 키를 만든다), 배치 렌더에서는 0 — 그리고 `pt.slang`과 `restir.slang`의 키 자리 일곱 곳이 그것을 읽는다. env 블록에 그 env의 시드가 있으므로, 타일 `k`는 env `k`의 단일 렌더가 뽑는 샘플을 그대로 뽑는다.

SVGF, 분산 추정, `ReSTIR`의 공간 재사용은 아무것도 필요 없었다: `svgf.slang`, `accumulate.slang`, `restir.slang`의 모든 이웃 읽기는 이미 픽셀 자신의 타일로 잘려 있었다(`nx`, `ny`를 아틀라스가 아니라 타일에 대해 검사). 다중 카메라 아틀라스가 애초에 옳았던 이유가 그것이다. SVGF를 켠 N = 16의 `batched_tiles_equal_single_renders`(32픽셀 타일에서 보폭 최대 8)가 어떤 탭도 경계를 넘지 않는다는 증명이다.

### 14.2 트리: env마다 월드 공간 BVH 하나, 그리고 2레벨이 아닌 이유

삼각형 버퍼 안의 각 env 블록은 포즈가 적용된 그 env의 삼각형, 그리고 정확히 그것 위에 지은 BVH다 — `Slot::pack`이며, 오프셋 0에서는 `upload_tris`가 늘 하던 업로드와 float 하나까지 같다. env 사이에서 공유되는 것은 포즈에 의존하지 않는 부분이다: `SceneCache` 안의 지오메트리별 로컬 테셀레이션(8.2절), 배치 전체에 캐시 하나.

패킷이 말하는 대안 — 강체마다 로컬 프레임의 BLAS 하나, 바디 변환들의 TLAS(또는 env별 인스턴스 목록), 디바이스에서 광선을 바디 프레임으로 옮기기 — 은 호스트와 업로드에서 더 싸고, **패킷 자신의 합격 기준을 만족할 수 없다**. 모든 골든과 커밋된 프레임이 바이트를 고정하는 단일 경로(spec 28.10 규칙 1)는 `SceneCache`가 호스트에서 `f64`로 포즈를 적용하고 `f32`로 한 번 반올림한 월드 공간 정점과 교차한다. 2레벨 순회는 디바이스에서 변환된 `f32` 광선으로 로컬 정점과 교차한다: 반올림이 다르고, `t`가 다르고, 스치는 모서리에서는 다른 삼각형이 된다. 그러니 타일이 단일 렌더와 같으려면 단일 렌더도 2레벨로 옮겨야 하고, 그러면 모든 골든이 움직인다. env별 월드 공간 트리는 "타일 `k` == env `k` 단독"이 구성상 참인 유일한 배치다 — 타일은 동등한 트리가 아니라 *같은 트리*를 순회한다.

비용, `pt_batched_cost`가 SO-101 셀(삼각형 2,754개, BVH 노드 2,047개)에서 측정:

| env당 | RTX 3060 머신 (Windows) | RTX 4090 머신 (Linux) |
|---|---|---|
| 재포즈(캐시된 테셀레이션) + BVH 빌드, 코어 하나의 CPU 시간 | 0.50–0.88 ms | 0.47–0.90 ms |
| 업로드 (삼각형 + 트리) | 289 KiB | 289 KiB |
| 그 CPU 시간 / 배치의 env당 `Pt` 프레임, N = 64, 4 spp / 64 spp | 12 % / 0.8 % | 45 % / 3.2 % |

배치는 트리를 모든 코어에서 짓는다(env에 대한 `std::thread::scope`, env 순서로 다시 포장 — 트리는 자기 삼각형의 순수 함수이므로 바이트는 스레드 수에 의존하지 않는다). 둘째 행의 45 %가 벽시계로는 그렇게 줄어든다: 4090의 N = 64, 4-spp 프레임은 그것으로 env당 1.06 ms다. 2레벨은 빌드와 업로드 대부분을 아낄 것이다: 4090의 4 spp에서는 실제 몫이고, 센서의 64 spp에서는 몇 퍼센트다. 장면이 커서 빌드가 프레임에 드러나는 순간이 업그레이드 경로이고 — 8.2절의 `ponytail:` 메모가 꼽는 바로 그 계기 — 골든 재생성과 함께 오며, 그 전에는 아니다.

### 14.3 제출 하나, 리드백 하나

`render_batch`는 모든 env 블록을 버퍼 쓰기 한 번으로 올리고, 단일 렌더와 같은 패스를 아틀라스 전체에 대해 기록하며(트레이서, SVGF 반복, 톤 맵 — 각각 모든 env에 대한 디스패치 하나), `read_tiles`는 원하는 채널마다 다운로드 한 번으로 되가져온다. 루프 안의 `read_tile`이었다면 아틀라스 전체를 N번 내려받았을 것이다.

### 14.4 동등성, 측정

`cargo test -p es-render --test render batched_tiles_equal_single_renders`: 32×32의 SO-101 셀, 16개 env가 각자 큐브 포즈, 카메라 오프셋과 초점 거리, 빛 방향, 앰비언트, 하늘, 태양, 알베도 게인, 틱 시드를 가진다. N ∈ {1, 4, 16}을 정사각형에 가까운 격자에 놓아 배치가 타일 열뿐 아니라 행도 건넌다. 모든 타일을 경로가 쓰는 **모든 채널**(`Rs`: `Rgb8`, 깊이, 노멀, 세그멘테이션; `Pt`: 여기에 `PtRadiance`와 `History`)에서, `EnvRenderer`가 모는 방식 그대로 몬 단일 경로(`set_lighting`, `set_seed`, `upload_tris`, `render`)와 비교하고, 처음 4개 env는 `cpu::render_batch`와도 비교한다:

| `es-render`와 `render_loop`의 기존 골든과 GPU 오라클 전부 | 통과 | 통과 |

두 카드는 모든 행에서, env 하나하나까지 ULP 단위로 일치한다.

CPU 대 GPU 행은 **단일 경로 자신의** 일치도다 — 배치 타일이 그 경로의 바이트이므로 — 골든의 것이 아닌 카메라에서. 거기서 깊이는 CPU와 몇 ULP 차이 나며, 13.4가 뽑힌 포즈에서 발견한 것과 같다. 남은 두 `Cross` 내장 함수를 `es_cross`로 바꾸자 (쇼케이스 카메라에서) 오히려 *나빠졌다*(12 ULP). 그러니 잔차는 내장 함수가 아니라 `dot`의 고정되지 않은 합산 순서(9.3)다. 테스트는 깊이를 상대 1e-5로, `Rgb8`, 세그멘테이션, NEE 없는 복사휘도를 비트 동일로 묶는다.

두 `batch_*` 골든은 4개 env의 `Rgb8` 타일을 env 순서로 쌓은 것이며, `Rs`와 `Pt` 16 spp NEE, 오직 `cpu::render_batch`에서 나온다(`generate_batch_goldens`, 더 오래된 골든을 다시 쓸 수 없도록 따로 둔 생성기). 기존 골든과 `so101_frame0`은 전부 바이트 동일하다: 새 파라미터 슬롯은 읽힐 뿐 계산에 쓰이지 않는다.

### 14.5 밴드: 드라이버가 죽일 프레임

첫 비용 측정은 디바이스를 잃었다: 64개 env에 64 spp는 RTX 3060에서 ~4 s짜리 디스패치 하나이고, Windows는 2 s 넘게 바쁜 디바이스를 리셋한다. 그래서 2^24 샘플-바운스(`pixels * spp * bounces`)를 넘는 `Pt` 프레임은 워크그룹 행 단위의 밴드로 나뉘어 트레이싱되고, **밴드마다 제출이 따로**이며, 밴드의 첫 행은 전역 슬롯 40에 있다(`pt.slang`의 `main`이 스레드 id에 더한다). 트레이서의 픽셀은 다른 트레이서 픽셀이 쓰는 것을 읽지 않으므로 밴드로 나눈 프레임은 디스패치 하나짜리 프레임과 같다. 이후 패스(SVGF, 톤 맵)는 마지막 밴드 뒤에 아틀라스 전체에 대해 한 번 돈다. 오늘 크기의 모든 프레임 — 96×96 64-spp 3-바운스 관측은 1.8M — 은 밴드 하나이고, 예전과 똑같이 기록된다.

### 14.6 비용, 두 카드에서 측정

표가 말하는 것:

- **4090은 놀고 있었고, 3060은 아니었다.** 96×96 프레임 하나는 워크그룹 144개다. 4090에는 SM이 128개 있고 그 각각을 거의 비운 채 돌리고 있었으므로, 배치는 센서의 64 spp에서 5.5×를 산다(12.4의 수치 기준 57.5 → 11.4 ms/env, 같은 프로세스 안에서는 62.3 → 11.4). 3060은 env 하나로 이미 거의 바빴고 2.3×를 산다. 배치 경로의 N = 1은 단일 경로와 2 % 안에서 같다.
- **64 spp에서는 N = 16이 최적점이고, N = 64는 env당 더 느리다** — 두 카드 모두. 64-env 64-spp 프레임은 1억 1,300만 샘플-바운스, 밴드 일곱 개(N = 16에서는 둘)이고, 밴드마다 다음 밴드가 시작하기 전에 디바이스를 비우는 제출이다. 밴드 예산은 3060의 것이다(Windows는 더 긴 제출을 죽인다; 4090 머신은 그러지 않을 것이다). N = 64가 밴드 하나나 둘인 4와 16 spp에서는 env당 가장 빠르다.
- **SVGF는 배치되면 env당 측정 가능한 비용이 없다** (아틀라스에 대한 디스패치 넷이 더해질 뿐).
- spec 12.4의 용어로, 4090의 N = 16, 64 spp: `camera_frames_per_sec` 88, `pixels_per_sec` 8.1e5(제어 스텝마다 env당 96×96 프레임 하나); 3060: 16.7과 1.5e5.

X3는 57.5 ms/프레임에서 reach PPO 한 런의 렌더링을 ~65 h로 추정했다. 11.4 ms에서는 ~13 h다 — 이 표에 대한 산수이지 측정한 런이 아니다(`Target / Status: unverified`).

### 14.7 X3b가 건너뛰는 것

- **2레벨 BVH** (14.2): 장면의 빌드가 프레임에 드러나기 전에는 아니고, 그때는 골든 재생성과 함께.
- **디바이스를 따르는 밴드 크기.** 2^24 예산은 Windows의 2 s 한계 아래 3060에 맞춘 것이며, 4090에서 N = 64, 64 spp일 때 ~25 %의 비용을 치른다(14.6). 이후 밴드의 크기를 첫 밴드의 벽시계로 정하면 일정은 바뀌어도 비트는 하나도 바뀌지 않을 것이다.
- **재포즈의 병렬화.** 트리는 모든 코어에서 지어진다. 재포즈(`&mut SceneCache` 하나 위의 `drawn_frame`)는 여전히 env 하나씩, 각 ~0.1 ms다.
- **4090에서의 동시 GPU 테스트.** 서버에서 처음 돌린 `cargo test -p es-render --test render`는 테스트 스레드 ~15개가 각자 `VkDevice`를 잡은 채 20분 동안 멈췄다: 스레드 하나는 드라이버 안에서 돌고, 나머지는 드라이버 뮤텍스에 막혀 있었다. `--test-threads=1`이면 스위트 전체가 67 s에 통과한다. 로컬에서는 기본 병렬 실행이 통과한다. 새 테스트가 드라이버 한계를 넘긴 것인지, 멈춤이 더 오래된 것인지는 모른다.
- **수집기와 평가기의 배치.** `es loop collect`와 `es eval run`은 여전히 `EnvRenderer` 하나에 env 하나를 렌더한다. 패킷 범위 밖이다.
- **배치에서의 시간 누적**은 거부되지 않지만(각 타일의 이력은 다중 카메라 아틀라스에서처럼 픽셀별·뷰별이다) 테스트되지 않았다: 관측 경로는 아무것도 누적하지 않는다(12.3).
