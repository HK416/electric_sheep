# Learning IR → PyTorch lowering

리뷰 유형 **C** (spec 1.3): 이 노트가 산출물이며, `crates/es-policy`의 코드는 그 하위 결과물이다. 명세:
spec 8.1, spec 8.3, spec 8.4, spec 8.5, spec 8.7, spec 8.8, spec 8.9, spec 1.4, spec 2.4.

PyTorch는 Learning IR의 **참조 오라클**이다 (spec 1.4): 동일한 `LearningGraph`를 PyTorch로 실행한
결과가, 다른 모든 `PolicyRuntime`이 판정받는 정답(ground truth)이다. 따라서 이 lowering은 배포
경로가 아니다. 의도적으로 가장 축자적이고 가장 재미없는 변환이다 — 노드당 `nn.Module` 하나, 노드당
forward 한 줄, 퓨전 없음, 재정렬 없음.

## 1. 무엇이 lowering되고, 무엇이 되지 않는가

| 부분 | spec 8.7의 대상 | 여기서는 |
|---|---|---|
| 인코더 프론트엔드 (전처리) | Slang 커널, GPU 상주 | 이미 Observation IR의 것; CPU 참조는 `es-compile` 소관 |
| `PolicyHandle`의 forward pass | `PolicyRuntime` | 이 노트 |
| `ActionChunker` / `Normalizer` / blend | 결정적 CPU 코드, sim과 real에서 동일 | **여기서도 lowering됨** |

세 번째 행은 의도적인 이탈이며 그 이유는 spec 8.9다: 오라클은 배포 경로가 만드는 것과 동일한
텐서를 end-to-end로 만들어내야 한다. chunker와 unnormalizer가 lowering된 모듈 바깥에 있었다면,
tier-4 비교는 파이프라인의 앞부분만 비교하게 되어, 불일치 가능성이 가장 큰 바로 그 두 노드
(`execute_chunk`의 off-by-one, 뒤바뀐 mean/std)를 조용히 면제해 버렸을 것이다. 이 둘은 양쪽 위치
모두에서 순수하고 결정적이므로, lowering하는 비용은 슬라이스 하나와 아핀 표현식 하나에 불과하다.

긍정형으로 진술한 규칙: **`lower_to_torch`는 `LearningGraph` 전체를 경계에서 경계까지 커버한다.**
`PolicyRuntime::infer`는 `PolicyContract::inputs`에 따라 이름이 붙은, 이미 전처리된 텐서를 받아
그래프가 선언한 출력을 반환한다. 런타임 자체는 아무것도 추가하지 않는다 — 정규화도, chunking도,
dtype 정책도 없다. 이것이 spec 2.4의 "IR이 pre/post-processing을 소유하며, 런타임은 그렇지 않다"
(`INV-15`)이며, `TorchRuntime`에 옵션이 하나도 없는 이유다.

## 2. 생성되는 파일의 형태

`lower_to_torch`는 완결되고 자기완비적인 Python 파일 하나를 만들어낸다:

```python
# generated by es-policy; do not edit
import torch
import torch.nn as nn
# (import torchvision  -- only when a VisionEncoder is present)

class EsPolicy(nn.Module):
    def __init__(self):
        super().__init__()
        self.n1 = nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Linear(8, 8))
        self.n4 = nn.Linear(8, 6)

    def forward(self, **inputs):
        v1_out = self.n1(inputs["joint_state"])
        v4_chunk = self.n4(v1_out).reshape(3, 2)
        v5_actions = v4_chunk[:3]
        return {"actions": v5_actions}
```

- 노드 `NodeId(k)`에 대응하는 멤버는 항상 `self.n<k>`다. 파라미터가 없는 노드는 멤버를 만들지
  않는다.
- 노드 `k`의 출력 포트 `p`의 값은 항상 로컬 변수 `v<k>_<p>`다.
- 노드는 `Graph::topo_order()` 순서로 출력되며, 이는 결정적이고 엣지 순서와 무관하다(`BTreeSet`
  에서 pop하기 때문). lowering 안의 다른 모든 컬렉션도 `BTreeMap`이거나 그 순서로 만들어진
  `Vec`이므로, **동일한 그래프는 바이트 단위로 동일한 소스를 만들어낸다**. 이것은 지향점이 아니라
  유닛 테스트다: `lowering_hash = blake3("es.lowering.v1" || source)`이며, 동일 그래프의 두
  lowering 결과는 반드시 일치해야 한다.
- 배치 축이 없다. spec 5.2는 Learning IR에 자유로운 배치 시맨틱을 부여하고, spec 5.4는 선언된
  모든 shape에서 배치 축을 제외한다; 생성된 모듈은 샘플 하나를 기준으로 작성되며, `Linear` 경로
  에서는 torch의 브로드캐스팅 덕분에 선행 배치 축이 있어도 어차피 동작한다. `PolicyHead`의
  reshape은 `.reshape(H, A)`를 쓰는데, 이것이 no-batch 컨벤션을 고정한다. 배치화된 lowering은
  플래그가 아니라 이후의 별도 패킷이다.

## 3. 노드 표

레이아웃은 row-major이며 dtype은 전 구간에서 `f32`다(`PolicyContract::runtime.dtype`; 그 외는
거부된다). 초기화는 무관하다 — 모든 파라미터는 첫 `forward` 이전에 safetensors 파일 값으로
덮어써지며, 키 누락은 항상 오류이지 결코 기본값으로 처리되지 않는다.

| `LearningNode` | PyTorch | forward 라인 | 가중치 |
|---|---|---|---|
| `StateEncoder { Identity }` | — | `v = x` | 없음 |
| `StateEncoder { Mlp { hidden } }` | `nn.Sequential(Linear, ReLU, …, Linear)` | `v = self.nk(x)` | 정확 |
| `VisionEncoder { ResNet18/34 }` | `torchvision.models.resnet{18,34}`, `fc = Linear(512, out_dim)`로 교체 | `v = self.nk(x)` | 접두사 |
| `VisionEncoder { other }` | — | — | `Unsupported` |
| `LanguageEncoder` | — | — | `Unsupported` |
| `Fusion { Concat }` | `Linear(Σin, out_dim)`, `Σin == out_dim`이면 없음 | `v = self.nk(torch.cat([a, b], dim=-1))` | 정확 / 없음 |
| `Fusion { TokenConcat }` | — | `v = torch.cat([a, b], dim=-2)` | 없음 |
| `Fusion { CrossAttention, FiLm, AdaLn }` | — | — | `Unsupported` |
| `TemporalEncoder { None }` | — | `v = x` | 없음 |
| `TemporalEncoder { Transformer }` | `nn.TransformerEncoder(nn.TransformerEncoderLayer(d_model=out_dim, nhead=8, batch_first=True), 1)` | `v = self.nk(x)` | 접두사 |
| `TemporalEncoder { TemporalConv, Gru, Mamba }` | — | — | `Unsupported` |
| `PolicyHead { Regression }` | `Linear(in, horizon * action_dim)` | `v = self.nk(x).reshape(H, A)` | 정확 |
| `PolicyHead { Diffusion, FlowMatching, Discrete, Energy }` | — | — | `Unsupported` |
| `PolicyBundle` | — | — | `Unsupported` |
| `ActionChunker` | — | `v = x[:K]` | 없음 |
| `Normalizer { MeanStd / MinMax }` | `register_buffer(..., persistent=False)` | `v = (x - mean) / std` 또는 그 역연산 | 없음 |
| `Normalizer { Dataset }` | — | — | `Unsupported` |

표에서 자명하지 않은 항목에 대한 설명:

- **`Fusion { Concat }`.** spec 8.3는 fusion에 `out_dim`을 부여하는데, concatenation만으로는
  이를 만족시킬 수 없다. 규칙은 이렇다: 마지막 축으로 concatenate한 뒤, concatenate된 너비가
  `out_dim`과 다를 **때만** `Linear`로 투영한다. 조건부 가중치는 위험 요소이므로, 규칙은 플래그가
  아니라 shape으로 진술되며, 투영의 키는 그것이 존재할 때만 `weight_keys`에 나타난다.
- **풀링된 피처 위의 `TemporalEncoder { Transformer }`.** `token_count == 0`이면 포트는 토큰
  축이 없는 `[dim]`이 된다. lowering은 인코더 앞에 `unsqueeze(0)`을, 뒤에 `squeeze(0)`을
  삽입한다. 즉 토큰 하나짜리 시퀀스로 취급한다. `nhead = 8`은 고정값이다; spec 8.3의 노드
  파라미터에는 이 값이 실려 있지 않으므로 lowering 상수이며, 다른 head 개수로 학습된 체크포인트는
  조용히 재해석되지 않고 shape 검사에서 실패한다.
- **`ActionChunker`.** `execute_chunk`를 제외한 나머지 — `replan_hz`, `mode`, `blend`,
  `buffer_chunks` — 는 텐서 연산이 아니라 런타임 스케줄링(spec 8.6)이다. lowering은
  `execute_chunk`만 소비하고 나머지는 **의도적으로** 무시한다; 비동기 버퍼와 blend 정책은 env
  런타임에 있고 자신의 오라클과 대조되며, `TemporalEnsemble` blend는 단일 `infer` 호출로는
  관측되지 않는다.
- **`Normalizer`의 규약.** `MeanStd`의 forward는 `(x - mean) / std`, inverse는
  `x * std + mean`이다. `MinMax`는 `Normalized { lo: -1, hi: 1 }`(`learning::action_unit`)에
  대응하므로, forward는 `2 (x - lo) / (hi - lo) - 1`, inverse는 `(x + 1) / 2 * (hi - lo) + lo`다.
- **`Normalizer`의 통계값.** 이 값들은 non-persistent 버퍼로 인라인되어 `state_dict`에 결코
  나타나지 않으며, 따라서 가중치 키 집합에도 나타나지 않는다: 값은 IR에서 오므로, 체크포인트가
  IR과 이 값에 대해 불일치할 수가 없다. `StatsSource::Dataset`이 여기서 `Unsupported`인 이유는
  `dataset_hash` 해석이 `es-data`(레이어 10)의 소관이고 `es-policy`는 레이어 8이기 때문이다.

## 4. 가중치 네이밍

safetensors 키 스킴은 다음과 같다

```
nodes.<node_id>.<param path>
```

여기서 `<param path>`는 노드 멤버 **아래의** `state_dict` 경로 그대로다. 따라서 로딩은 순수한
rename이다: `nodes.<k>.<rest>` ↔ `n<k>.<rest>`. 노드 이름이 아니라 노드 **id**를 쓰는 이유는
`Graph`가 노드를 `NodeId`로 키잉하고 그 외에는 유일함이 보장되지 않기 때문이다; id는 저작 상의
정체성이며 `learning_hash`(spec 11.2)에서 제외된다. 따라서 라벨을 다시 붙인 그래프는 다른 키
집합으로 lowering되지만 동일한 아키텍처 해시를 갖는다 — 이는 맞는 동작이다, 체크포인트는
`learning_hash`가 아니라 `policy_hash`로 그래프에 결속되기 때문이다.

ACT 형태의 픽스처(`es_ir::learning::testing::act_like`)의 경우:

```
nodes.0.*                       ResNet18 backbone + fc          (prefix claim)
nodes.1.0.weight  [256, 8]      state MLP, first Linear
nodes.1.0.bias    [256]
nodes.1.2.weight  [512, 256]    state MLP, second Linear
nodes.1.2.bias    [512]
nodes.2.weight    [512, 1024]   fusion projection (2*512 -> 512)
nodes.2.bias      [512]
nodes.3.*                       transformer encoder             (prefix claim)
nodes.4.weight    [400, 512]    regression head (H*A = 50*8)
nodes.4.bias      [400]
```

**두 종류의 항목이 있다.** *exact* 키는 텐서 하나를 이름 짓고 그 shape을 싣는다. *prefix claim*은
`.*`로 끝나며, 내부 파라미터 이름이 우리 것이 아니라 torchvision이나 `torch.nn`에 속하는
서브모듈을 포괄한다. ResNet18의 122개 키를 Rust에서 다시 도출한다면 torchvision 내부 구현의
사본을 이 크레이트에 두는 셈이 되고, torchvision이 이름 하나만 바꿔도 깨진다; claim은 "이 prefix
아래 모든 것은 노드 `k`의 소관이다"라고 말하며, 검증은 그에 맞게 처리한다:

- 모든 exact 키는 선언된 shape과 함께 존재해야 하며, 아니면 `missing` / `shape`이다;
- prefix claim 아래의 파일 키는 검사 없이 받아들여진다;
- 둘 중 어디에도 맞지 않는 파일 키는 `unexpected`다.

그러므로 잘못된 아키텍처용 체크포인트라도 요란하게 실패하며, 그 실패는 해당 노드를 지목한다.

## 5. ACT

ACT는 픽스처와 같은 방식으로 노드 집합에 대응되며, 이 lowering이 직접 작성하지 않는 유일한
부분은 vision backbone이다. **`torchvision`이 제공자다**: `torchvision.models.resnet18()`에서
`fc`를 `Linear(512, out_dim)`으로 교체한다. 이는 참조될 뿐 결코 재구현되지 않는다 — 손으로 짠
ResNet은 정확히 99.9%만 맞고 그래서 오라클로서는 아예 없는 것보다 못한 부류의 물건이다.
`pretrained`는 lowering 시점에 무시되며(가중치는 체크포인트에서 오므로) `frozen`도 무시된다
(여기에는 학습 루프가 없다; spec 8.1은 옵티마이저를 IR 밖에 둔다).

결과를 분명히 말하면: **생성된 파일은 그래프에 `VisionEncoder`가 있을 때만 `torchvision`을
필요로 하고, 그 외에는 `torch`만 있으면 된다.** state만 다루는 경로 — tier-4 하네스 테스트가
실행하는 바로 그 경로 — 에는 torchvision 의존성이 없다.

ACT 자체의 transformer encoder/decoder는 노드 단위로 모델링되지 *않는다*. spec 8.1은 레이어
단위 저작이 PyTorch의 일이라고 명시하며, IR은 인터페이스만 기술한다. 따라서
`TemporalEncoder { Transformer }`는 prefix claim을 가진 단일 opaque `nn.TransformerEncoder`이며,
실제 LeRobot ACT 체크포인트는 M1 게이트 패킷(§8.9)에서 키 리맵이 필요할 것이다 — 그 리맵은
코드가 아니라 데이터이며, 여기 속하지 않는다.

## 6. Tier-4 허용오차 (spec 8.9)

spec 8.9의 표는 `PolicyRuntime` 쌍에 대한 것이다:

| 비교 대상 | 허용오차 |
|---|---|
| PyTorch(fp32) ↔ ONNX(fp32) | 최대 절대 액션 오차 ≤ 1e-5 |
| PyTorch(fp32) ↔ ONNX(int8) | 태스크별; 성공률 하락 ≤ 2 pp |
| PyTorch(fp32) ↔ Vulkan(fp32) | ≤ 1e-4 (소형 정책만) |
| 동일 런타임 재실행 | 비트 단위 일치 |

`compare_actions(a, b, tol) -> Equivalence { max_abs, max_rel, pass }`가 그 하네스다. 기본값:
`Tolerance::TIER4_FP32`는 `abs = 1e-5`, `rel = 1e-5`; `Tolerance::TIER4_VULKAN`은 `1e-4`;
`Tolerance::BITWISE`는 `abs = 0`, `rel = 0`이며 추가로 비트 패턴 일치를 요구하므로, `-0.0`과
`+0.0`은 `abs = 0`은 통과하면서도 이 기준은 통과하지 못한다. 원소별로 `|a-b| <= abs` **또는**
`|a-b| <= rel * |b|`이면 그 쌍은 통과한다 — `b`가 참조 쪽이며, 이는 상대오차 항을 잘 정의된
것으로 만들고 의도적으로 비대칭이 되게 한다.

비교는 그래프의 출력 공간에 있는 원시 액션 청크 `[H, action_dim]`, 즉 unnormalizer 이후 값에
대해 이루어진다. 이것이 Safety Plane과 actuator가 실제로 보는 텐서이기 때문이다. shape이나
dtype이 불일치하는 것은 큰 오차로 취급되지 않고, `max_abs = inf`와 함께
`Equivalence::pass = false`가 된다; 조용히 브로드캐스트하는 하네스는 통과하지 말아야 할 때
통과해 버리는 하네스다.

## 7. 보류된 항목

아래 항목들은 "나중에 하면 될지도"가 아니다. 각각은 그 오라클이 이 패킷에 없기 때문에 보류된
것이다.

- **Diffusion과 FlowMatching 샘플링 루프.** `HeadKind::Diffusion { n_steps, scheduler }`와
  `FlowMatching { n_steps }`는 각자의 노이즈 스케줄과 각자의 RNG를 가진 반복적 샘플러다. 노이즈
  추출의 결정성(spec 3.4는 전역 RNG를 금지한다)이 진짜 설계 문제이며 lowering보다 훨씬 크다.
  어떤 패킷이 샘플러 계약을 소유하기 전까지는 `Unsupported`다.
- **`PolicyBundle` (SmolVLA, π₀).** spec 8.3은 3.5B VLA가 분해되지 않고 통째로 참조된다고
  명시한다. 최종적인 lowering은 *passthrough*가 될 것이다: 번들 자신의 모듈을 로드하고,
  인터페이스를 `PolicyContract`와 대조 검사한 뒤 호출한다. 여기서 반쯤 구현하는 대신
  `Unsupported`로 두는 이유는, 번들의 인터페이스를 검증할 수 없는 passthrough는 에러 메시지보다도
  못하기 때문이다.
- **`LanguageEncoder`.** 토크나이저와 `transformers`가 필요하다; 이는 추론 경로에 걸리는 Python
  의존성인데, spec 2.4는 그것을 학습 경로 안에만 가두고자 한다.
- **`DiscreteHead`, `EnergyHead`.** 아직 이를 쓰는 소비자가 없다.
- **배치화된 lowering, ONNX export, `libtorch` FFI.** spec 2.4는 `OnnxRuntime`을 M2에,
  `VulkanRuntime`을 M3에 둔다. 서브프로세스가 M1의 형태이며, 원래 느리게 의도된 것이다.
- **실제 LeRobot ACT 체크포인트 키 리맵.** M1 게이트(spec 8.9)에 필요하다; 이것은 픽스처이며,
  픽스처는 게이트와 함께 있어야 한다.
