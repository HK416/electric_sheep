# M7 E2 — the 3D replay: an `.estraj` played back inside the editor, no physics, no GPU

Spec: §23.3 ("the editor locally replicates the scene and receives only the pose/joints" — a
recorded trajectory is that stream, offline), §23.1, §28.10 rule 3. Design note to extend:
`docs/design/editor-shell.md` (+ `.ko.md`) section 11. Predecessors: M5 V9 (`es_env::Trajectory`,
`.estraj` holds `qpos ‖ qvel ‖ body poses` per tick; `TriScene::from_scene_with_poses` re-poses
a scene from those poses with no backend in the process), E1 (the selected cell).

## the question

`es video showcase` proves a trajectory can be re-rendered with nothing but the scene file and
the `.estraj`. **Can the editor do the same at interactive rate on the CPU, in an `egui` canvas,
with a scrubber — so that watching an episode does not need `ffmpeg`, a GPU or the server?**

## spec

Headless view-model `crates/es-editor/src/model/replay_view.rs`:

* `ReplayView::open(scene_path, traj_path) -> Result<ReplayView, ReplayError>` — loads the
  `SceneDesc` through the same loader `es video showcase` uses (`es-assets` MJCF/URDF; the editor
  may depend on `es-assets`, `es-env` and `es-render`, layer 12) and the `Trajectory`.
* `ReplayView::ticks()`, `ReplayView::qpos(tick)`, and `ReplayView::project(tick, &Camera) ->
  Projected` where `Camera { eye, look_at, fov_y, width, height }` is the showcase's own free
  camera (`es_env::render::look_at`, reuse, do not rewrite) and `Projected` is a `Vec<Tri2d>` —
  three screen-space points, a flat shaded `[u8; 3]` (the renderer's own `es_shade_lambert`
  formula applied on the CPU through `es_render::cpu`'s public helpers or a small reimplementation
  that the test pins against `es_render::cpu::rasterize` on one triangle) and a depth key —
  **sorted back to front** (painter's algorithm; stable sort on `(depth, triangle index)` so the
  order is a pure function of the inputs). Triangles behind the near plane are clipped away, not
  projected through the eye.
* `ReplayView::orbit(delta_yaw, delta_pitch)` / `zoom(factor)` move the camera on a sphere about
  `look_at`; pure functions on `Camera`.
* Playback state (`playing`, `tick`, `speed`) lives in the model and advances by
  `advance(dt_seconds, control_rate_hz)`; the app only feeds wall-clock deltas.

`app.rs`: a **Replay** panel inside E1's Run tab (or its own tab if E1 has not landed — say
which in the design note). Draws `Projected` as one `egui::Mesh` (two triangles per `Tri2d` is
wrong — one; the mesh's vertex colours are the flat colour), a scrubber over `0..ticks`, play /
pause / step buttons, tick and time labels, drag to orbit, wheel to zoom. Nothing else is
decided there.

Painter's algorithm is the deliberate simplification (`ponytail:` comment naming it): it is
exact for the scene's convex primitives when they do not interpenetrate, and wrong only at
intersections; the upgrade path is a per-pixel `es_render::cpu::rasterize` at low resolution
once R1's BVH makes that cheap.

## oracle

1. `cargo test -p es-editor projection_is_a_pure_function` — `project(t, cam)` twice gives equal
   `Vec<Tri2d>`; the triangle-index order for tick 0 equals the golden; changing the camera by
   one degree changes it.
2. `cargo test -p es-editor a_replay_reposes_what_the_renderer_would` — for tick `t`,
   `TriScene::from_scene_with_poses(scene, traj.poses(t))` and the world triangles `ReplayView`
   projects are the same set (same count, same vertices bitwise before projection) — the replay
   draws exactly the geometry the showcase renders.
3. `cargo test -p es-editor flat_shade_matches_the_renderer` — the colour the replay assigns to
   one triangle equals the `Rgb8` `es_render::cpu::rasterize` produces for a pixel in the middle
   of that triangle, same light, same ambient.
4. `cargo test -p es-editor playback_advances_by_the_control_rate` — `advance(0.02 s, 50 Hz)`
   moves one tick at speed 1, two at speed 2, and clamps at the last tick.
5. `cargo build -p es-editor`; `cargo xtask ci` green; the layering check passes (`es-editor` may
   depend on anything; nothing new depends on it).

## acceptance

Oracles 1–5. The orchestrator opens a real V19b trajectory locally and watches the arm move at a
usable rate (report the frame time as an observation, no target). The design note section 11
records the view-model API, the painter's-algorithm limit and the upgrade path.

## forbidden

`crates/es-render/**`, `crates/es-env/**`, `crates/es-assets/**` (read only; R1 owns the renderer);
the `render` feature of `es-env` (no Vulkan in the editor build); a new external dependency
(`egui` already draws meshes); decisions in `app.rs`; `docs/ARCHITECTURE*.md`; every existing
golden.
