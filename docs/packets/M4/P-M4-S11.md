## spec

S-11: `es-render/src/view.rs:26` computed `fy` as `f64::from(height) * 0.5 / (fovy_rad *
0.5).tan()`. That `tan` is the host `libm`, pinned by nothing, and `fx`/`fy` are on the golden
camera path — `cornell.rs:99` → `ViewParams` → every ray direction → every golden pixel.
`scene.rs:269-271,295,317` used `f64::sin`/`cos` for sphere, ellipsoid, capsule and cylinder
vertices, which the CPU reference traverses *and* `Renderer::upload_tris` uploads to the GPU,
so a `libm` difference would desynchronize the two paths on a different host.
`es_math::approx` had no `tan`.

1. **`es_math::approx::tan(x: f32) -> f32`.** Reuses `reduce_quadrant` unchanged — the same
   Cody–Waite reduction as `sin`/`cos`, one reduction to keep in sync with the mirror. `tan`
   has period π, so only `quadrant & 1` matters: even returns the kernel, odd returns
   `-1.0 / kernel`. The kernel is Cephes `tanf.c`'s 6-term minimax in `r²`
   (`TAN_C0..TAN_C5`), one Horner expression, no `mul_add`, no reassociation.
   **Not** `sin(x) / cos(x)`: the quotient was implemented and measured first at **3 ULP**
   (two kernel errors plus the division), over the 2 ULP target.
   Primary domain `|x| ≤ 6.5` off the poles — narrower than `sin`/`cos` because
   `tan'(x) = 1 + tan²(x)` amplifies the reduction's residual argument error. Non-finite
   input gives `NaN`, matching `sin`/`cos`.
2. **Slang mirror.** `es_tan_kernel` / `es_tan` plus the six `TAN_C*` literals in
   `slang/approx.slang`, in the same order and with the same literal text.
   `slang_mirror.rs` picks up the constants automatically; its Horner spot-check list gains
   the `tan` expression so a reassociated mirror still fails.
3. **`Intrinsics::from_fovy`.** `fovy_rad` stays `f64` (that is how `es_assets::scene::Camera`
   stores it); one cast, then `f32` throughout, fixed order — halve, `approx::tan`, divide.
   `cx`/`cy` lose their pointless `f64::from(w) as f32` round trip.
4. **Tessellation.** `ellipsoid_tris` and `capsule_tris` compute the unit direction in `f32`
   through `approx::{sin, cos}`, then widen exactly to `f64` and scale by the `f64` radii.
   The longitude angle moves into `phi_of`, which folds `seg == SPHERE_SEGMENTS` onto
   segment 0 so the seam closes on identical bits instead of on a `sin(2π)` residue — which
   in `f32` is ~1e-7, nine orders larger than the `f64` residue it replaces.

## oracle

```
cargo test -p es-math approx:: -- --nocapture
cargo test -p es-render -- --nocapture
cargo xtask verify-goldens
```

New tests, written against the un-fixed code first:

- `es-math approx::tests::tan_ulp_within_target` — dense + pseudo-random sweep, ≥ 200k points
  per band, referenced against `f64::tan` rounded to `f32`, points where the reference
  exceeds `1e3` (within ~1e-3 of a pole) skipped and counted. Asserts ≤ 2 ULP on
  `[-1.5, 1.5]` and `[-6.5, 6.5]`; prints `[-1e3, 1e3]` for the record without asserting.
- `es-math approx::slang_mirror::*` — the existing pair, now covering the `tan` literals and
  the `tan` Horner expression.
- `es-render view::tests::intrinsics_come_from_approx_tan_in_f32` — `fy` bit-equals
  `(h as f32 * 0.5) / approx::tan(fovy as f32 * 0.5)`. Pins the arithmetic *and* its order.
- `es-render scene::tests::curved_shapes_upload_the_vertices_the_cpu_reference_traverses` —
  a sphere + capsule + cylinder scene: every vertex in `to_floats()` (what the GPU gets)
  bit-equals the matching component of `tris[i].v` (what `cpu::rasterize` traverses), all
  finite, and a repeat tessellation is `==`.

declared generator and the GPU still reproduces them exactly.

## forbidden

- Any change to `crates/es-gpu` (another packet owns it), or to `es-render/src/renderer.rs`
  beyond re-reading it.
- `sin(x) / cos(x)` for `tan`, or a second range reduction: `reduce_quadrant` is the one
  reduction both files mirror.
- `mul_add`, reassociation, a lookup table, or a device-property branch in `approx`
  (§3.2 contract).
- Editing a coefficient on one side only, or reformatting a literal in `coeffs.rs` — the
  mirror test compares literal text byte for byte.
- Changing `SPHERE_SEGMENTS` / `SPHERE_RINGS` / `CAP_RINGS`, or the Cornell scene: both
  invalidate goldens for reasons unrelated to S-11.
- Regenerating goldens from the GPU path, or hand-editing a `.bin`.
