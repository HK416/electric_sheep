# P-M4-S13 — Task IR rejects an unsupported `schema_version`

Spec: spec 6.1 (Task IR scope), spec 5.3 (the version is hash input). Closes **S-13** of
`docs/reviews/M4.md` and answers its "Human decision — Task IR `schema_version` 1 → 2" with an
acceptance rule.

## context

```
crates/es-ir/src/task.rs
crates/es-ir-types/src/codes.rs
docs/design/ir-types.md
docs/design/ir-types.ko.md
docs/packets/M4/P-M4-S13.md
```

## spec

`task.rs` bumped `SCHEMA_VERSION` to `2` for IR-C and hashes `self.schema_version` into
`task_hash`, but `TaskIr::validate` never looked at it: a file claiming `99` validated clean and
got a hash pinned to a schema this build cannot read. `DeploymentIr::validate` already rejects
its own (`DEP-001`).

The rule, chosen to match what hashing the field already implies:

```
accept  1 ..= SCHEMA_VERSION       reject  0, and anything > SCHEMA_VERSION   -> TASK-002
```

- `0` is an unwritten field, not a version.
- A version past this build's carries nodes and fields this build cannot see; deserializing it
  silently drops them, and the resulting `task_hash` would name something never validated.
- Older supported versions stay readable with **no migration step**. They keep their hashes
  because the version is itself hash input — that is the property, not an accident.

`TASK-002` ("unsupported Task IR schema version", Error, spec 6.1) joins `codes::CODES`.
The check sits in `TaskIr::validate`, the one guard every path routes through: `task_from_toml`
and `serde_json` both produce a `TaskIr` that is then validated, so the load paths are covered
without a second copy of the rule (and without a new `SerialError` variant).

## oracle

```
cargo test -p es-ir --features testing task::tests::unsupported_schema_versions_are_rejected
cargo test -p es-ir-types codes
```

The first asserts `0` and `SCHEMA_VERSION + 1` each report exactly `[TASK-002]`, that every
`1 ..= SCHEMA_VERSION` validates clean, and that a `SCHEMA_VERSION + 1` task written with
`task_to_toml` and read back with `task_from_toml` reports `TASK-002` too. The second is the
pre-existing codes-registry suite: `every_exported_constant_has_an_entry` and
`codes_are_sorted` now cover `TASK-002`.

## acceptance

- The new test passes; `cargo test -p es-ir -p es-ir-types --features es-ir/testing` is green
  (no existing fixture used an out-of-range version).
- `cargo check --workspace --all-targets --features es-ir/testing` passes: no downstream crate
  built a `TaskIr` that this now rejects.
- `cargo xtask check-spec-refs` resolves the new `6.1` reference.
- `cargo fmt --check` and `clippy -D warnings` clean for both crates.

## forbidden

Anything outside `context`. Changing `SCHEMA_VERSION`, what `task_hash` mixes in, or the
canonical encoding. Adding a migration/upgrade path (that is a separate decision, recorded as
"no migration" in `ir-types.md`). Adding the same check to `serial.rs` as a second guard.
Touching `DeploymentIr`, `ObservationIr`, `LearningGraph` or `EvaluationIr` version handling.
