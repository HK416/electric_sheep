# P-M4-S16 — `es-ir`를 다시 사양 1.5의 컨텍스트 예산 안으로

Spec: 사양 1.5(크레이트별 컨텍스트 예산: 목표 ≤ 6,000 코드 줄, 하드 캡 ≤ 10,000),
사양 4.2 rule 1(동일 레이어 의존성 금지). `docs/reviews/M4.md`의 **S-16**을 닫는다.

## context (범위)

```
crates/es-ir/src/task.rs
crates/es-ir/src/hash.rs
crates/es-ir-types/src/expr.rs      (new)
crates/es-ir-types/src/chain.rs     (new)
crates/es-ir-types/src/lib.rs
docs/design/ir-types.md
docs/design/ir-types.ko.md
docs/packets/M4/P-M4-S16.md
```

## spec (사양)

IR-C는 `es-ir`을 6,000 목표를 넘는 **6,205** 코드 줄로 만들었다(M3 시점엔 5,842였다).
Rule 1은 `es-ir`이 의존할 수 있는 두 번째 layer-6 크레이트를 금지하므로, 분리는
**아래로** 내려가 기존의 layer-2 `es-ir-types`로 향한다 — `P-M0-R4`가 `types` /
`image` / `diag` / `codes`에 대해 했던 것과 같은 조치다. 두 블록이 조건에 맞으며, 둘
다 이미 `Graph`, `IrNode`, `NodeId`로부터 자유롭다:

| 이동 대상 | 이동 원본 | 코드 줄 수 |
|---|---|---|
| `es_ir_types::expr` | `task.rs`의 사양 6.3 매개변수 열거형(`JointQuantity`, `ArithOp`, `CmpOp`, `LogicOp`, `ReduceOp`, `NormKind`, `MathFunc`, `Aggregation`, `TerminationKind`, `ActionSpace`, `Distribution`)과 사양 6.5의 `Expr` + `Expr::eval` | 184 |
| `es_ir_types::chain` | `hash.rs`의 `HashChain`, `DatasetHash`, `HardwareCapability`, `ChangedComponent`, `CHAIN_TAG` — digest만 | 89 |

`es-ir`은 둘 다 원래 경로에서 재수출한다(`task`에서 `pub use es_ir_types::expr::{..}`,
`hash`에서 `pub use es_ir_types::chain::{..}`), 그래서 `es_ir::task::Expr`,
`es_ir::CmpOp`, `es_ir::HashChain`을 비롯한 다른 모든 경로가 여전히 해석되며
**하류 크레이트는 아무것도 바뀌지 않는다**. 세 함수가 private에서 `pub`으로
넓어졌는데, 이제 그 호출자가 크레이트 경계 너머에 있기 때문이다:
`JointQuantity::unit`, `MathFunc::is_transcendental`, `Distribution::canonical`.
`Distribution::canonical`은 헬퍼를 수출하는 대신 `task.rs`의 private `wf64s`의 두
줄짜리 본문을 인라인한다.

의도적으로 옮기지 **않은** 것과, 리뷰가 제시한 다른 후보들이 기각된 이유:

- `canonical_hash` / `canonical_order` / `norm.rs`는 `Graph<N>`을 필요로 한다.
- IR-C의 `control.rs`는 `TaskIr`에 대해 검증하고 스스로를 `Graph<ControlNode>`로
  해싱한다 — graph 아래로는 내려갈 수 없다.
- `serial.rs`의 TOML 미러는 `TaskIr` / `ObservationIr` / `LearningGraph`에 타입이
  매여 있다.
- `testing` 생성기는 이미 카운트에서 **제외되어** 있다: `context-budget`은
  `#[cfg(any(test, feature = "testing"))] mod` 본문을 떨어뜨리므로, 이것들을
  옮겨봐야 점수는 0일 것이다.

## oracle (오라클)

```
cargo xtask context-budget
cargo check --workspace --all-targets --features es-ir/testing
```

Before / after:

```
es-ir         6205  WARN   ->  5947  OK
es-ir-types    923  OK     ->  1207  OK
```

워크스페이스 체크가 곧 하류 무변경 오라클이다: `es_ir::task::Expr`, `es_ir::CmpOp`,
`es_ir::HashChain` 등을 참조하는 모든 크레이트가 손대지 않은 채로 컴파일된다.

## acceptance (수용 기준)

- `es-ir` ≤ 6,000 코드 줄이며 여유가 있다; `es-ir-types`도 자신의 예산 안에 넉넉히
  들어간다.
- `cargo test -p es-ir -p es-ir-types --features es-ir/testing`이 초록색이다. 여기에는
  hash-chain `diff` 스위트와, 재수출을 통해 이동된 코드를 실행하는 Appendix B.7
  프로퍼티 테스트가 포함된다.
- `cargo xtask layering`이 깨끗하다: `es-ir`(6) → `es-ir-types`(2)는 아래로 향하는
  엣지다.
- `cargo fmt --check`와 `clippy -D warnings`가 두 크레이트 모두에서 깨끗하다.
- 동작 변화 없음: `pub` 가시성만 넓어졌을 뿐, 어떤 타입, variant, 필드, 인코딩, 해시
  입력도 바뀌지 않았다.

## forbidden (금지)

`context` 바깥의 무엇이든. `graph.rs`, `norm.rs`, `serial.rs`, `control.rs`,
`factory.rs`나 IR 모듈 전체를 옮기는 것. 새 크레이트를 만드는 것. 정규 인코딩, 해시
태그, `SCHEMA_VERSION`을 바꾸는 것. 이동한 항목의 이름을 바꾸거나, 재수출을 없애고
하류 크레이트에 `use`를 바꾸라고 요구하는 것. 새 trait을 추가하는 것(INV-17).
