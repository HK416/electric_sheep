# P-M1-R1 — externally generated observation goldens

Fixes the M1 review blocker (`docs/reviews/M1.md`, Blocker, gate 6): `tests/golden/observation/*`
was generated by `cargo test -p es-compile --test gen_goldens -- --ignored`, i.e. by the
kernels it checks, so it caught a regression but could never catch a wrong answer — a wrong
half-pixel convention would have been enshrined, not flagged (spec 1.4).

Spec: spec 1.4, spec 7.7, spec 11.3, spec 3.4. Design note:
`docs/design/observation-lowering.md`. API digest: `docs/api-notes/torchvision.md`.

## forbidden

`crates/es-compile/src/**` — the kernels are P-M1-R1's *subject*, not its scope. Five of six
goldens reproduce bit-for-bit, so none needed a change; the one measured disagreement found
outside the golden set is recorded in the design note (§12 item 6) for a later packet rather
than fixed here. Also out of scope: `es-policy` (that is P-M1-R2, gate 5) and the CI tier that
installs the oracles (P-M1-R7).

## spec

- `crates/es-compile/python/gen_observation_goldens.py <out-dir>` writes the same six
  `.bin` + `.json` pairs, from torch and torchvision only. It imports nothing from this
  workspace. Deterministic: CPU, one thread, `torch.manual_seed(0)`,
  `torch.use_deterministic_algorithms(True)`.
- Per-golden oracle call: `TF.to_tensor`, `F.interpolate(mode="bilinear", align_corners=False,
  antialias=False)`, tensor slicing, the IEC 61966-2-1 EOTF in f64 rounded to f32,
  `TF.normalize`, `torch.stack`. Each sidecar records the call in a new `"oracle"` field and
  names the script in `"generator"`.
- A sidecar may carry `"tolerance_ulp": n`. `observation_cpu.rs` reads it and allows exactly
  that many ULP and no more; absent, the comparison is byte-for-byte. The sidecar is itself a
  golden, so loosening a comparison requires modifying a CI read-only file.
- `gen_goldens.rs` no longer generates anything. It re-runs the script into a temp directory
  and fails if any byte differs from the checked-in files. It SKIPs loudly (printing why) when
  no interpreter has torch + torchvision, like the other reference-oracle tests; `ES_PYTHON`
  selects one.

cargo fmt -p es-compile --check

## acceptance

- `cargo test -p es-compile --test observation_cpu` passes against goldens whose bytes came
  from torch, with no tolerance anywhere except `srgb_to_linear_lut256`'s declared 7 ULP.
- With `ES_PYTHON` set, `gen_goldens` regenerates and matches byte-for-byte — provenance is
  machine-checked, not asserted in a comment. Without it, the test prints `SKIPPED` and every
  other test still runs (spec 1.4: the harness exists whether or not the oracle is installed).
- Exactly one `.bin` moved: `srgb_to_linear_lut256.bin`, because the Rust LUT is a polynomial
  fit and the golden is now the reference formula. The other five `.bin` files are unchanged,
  which is the finding: the half-pixel resize convention, the `/255` order, the CHW permute,
  the division in `normalize` and the oldest→newest window were all already right.
