# P-M1-R2 — a real LeRobot ACT checkpoint loads and reproduces its actions

Closes the M1 review follow-up (`docs/reviews/M1.md`, P-M1-R2, gate 5) and with it spec §1.4's
M1 gate: *"자체 추론 런타임이 LeRobot의 ACT/SmolVLA 체크포인트를 로드해 동일 출력을 내는지가
M1의 게이트다"*. Before this packet every `es-policy` equivalence test ran against a synthetic
checkpoint generated by the same lowering it was checking — the same circularity P-M1-R1 fixed
for the observation goldens. `Tolerance::TIER4_FP32` had never been applied to weights anyone
else produced.

Spec: spec 1.4, spec 8.4 (PolicyContract), spec 8.7 (lowering), spec 8.9 (tier 4), spec 5.3
(hash chain), `INV-16`. Design note: `docs/design/learning-lowering.md`. API digest:
`docs/api-notes/lerobot-act.md` (new, **verified** — not reconstructed).

## forbidden

- `crates/es-ir/**`. The finding below — that spec §8.3's node parameters cannot express ACT —
  is reported, not fixed: widening `TemporalEncoder` is a spec change, not a packet.
- `crates/es-data/**`. `lerobot_config.rs` converts a config into Learning IR at layer 10;
  `es-policy` is layer 8 and may not depend on it (spec §4.2), so `ActConfig` reads the same
  file independently. The two are pinned against one real config, not against each other.
- `crates/es-compile/**` and the Observation IR resize path: this checkpoint's `config.json`
  declares `[3, 480, 640]`, which is the native camera resolution, so ACT applies no resize and
  there is nothing for `Resize`/`ImageSpec` to do here (`INV-14` is untouched).
- Committing weights. The 197 MiB checkpoint lives under `target/lerobot-cache/` and is reached
  through `ES_ACT_CHECKPOINT`.

## spec

- `ActConfig::parse` reads the checkpoint's own `config.json`. It **refuses** rather than
  approximates: a non-`act` type, `pre_norm`, a non-`relu` activation, `n_obs_steps != 1`, a
  non-null `temporal_ensemble_coeff`, a non-`MEAN_STD` normalization mode, more than one
  camera, a missing state or action feature, an odd `dim_model`. Each would otherwise be a
  silently wrong action chunk, which spec §8.9 exists to prevent.
- `remap_act_keys(&ActConfig, keys) -> BTreeMap<String, String>` maps LeRobot's names onto
  `nodes.<id>.<param>` by longest-prefix-first (so `model.encoder.` cannot swallow
  `model.encoder_latent_input_proj.`). Keys with no entry are absent from the result: the 56
  `model.vae_encoder*` tensors and the 2 `normalize_targets.*` buffers, all training-only.
- `remap_checkpoint` rewrites the safetensors **at the byte level** — header rebuilt, each
  surviving tensor's bytes copied verbatim, `BTreeMap` order — so no value is decoded or
  re-rounded and the result's `blake3` is a stable `WeightsRef::hash` (spec §3.4, §5.3).
- `lower_act` emits the real ACT forward pass: `IntermediateLayerGetter(resnet18(
  norm_layer=FrozenBatchNorm2d))` truncated at `layer4`, a 1×1 conv projection, the computed
  2-D sinusoidal camera embedding, a `[latent, state, *300 image tokens]` encoder sequence, the
  DETR decoder over `chunk_size` learned queries, the action head, and the checkpoint's own
  MEAN_STD buffers as nodes 9/10/11. `use_vae` is honoured by *omission*: the CVAE branch is
  gated on `self.training`, so the latent is zeros and the module has no sampler and no RNG.
- The four transformer layer classes are written out rather than built from
  `nn.TransformerEncoderLayer`, for exactly one reason: ACT adds the positional embedding to
  the **query and key only**, never the value, and `torch.nn`'s layer cannot express that.
  Their parameters are still `nn.MultiheadAttention`/`nn.Linear`/`nn.LayerNorm`, which is why a
  prefix rename is the whole of the weight remap.
- `act_policy` projects the config onto spec §8.4's `PolicyContract`, with the LeRobot file's
  hash in `base_model` and the remapped file's in `weights`, so both are in the hash chain.
- `TorchRuntime::load_lowered` takes a module lowered outside `lower_to_torch` and performs
  every check `load` does — declared weights hash, then key and shape validation — before
  Python sees the file. `PolicyRuntime::load` now delegates to it. `INV-16` is untouched:
  safetensors in, safetensors out, and `act_ref.py` reads the file with `struct` and `json`.

## acceptance

- **Measured, `lerobot` 0.6.1 / `torch` 2.11.0+cpu / `torchvision` 0.26.0+cpu:**

  ```
  RAN act_checkpoint: lerobot 0.6.1 torch 2.11.0+cpu shape [100, 14] max_abs 0e0 max_rel 0e0
  ```

  **Bitwise identical** over the full `[100, 14]` chunk — inside spec §8.9's tier-4 `1e-5` with
  five orders of magnitude to spare. The test asserts `Tolerance::BITWISE`, not the tier-4
  threshold, so a future divergence cannot hide inside the tolerance. No module diverges; there
  is no ceiling to document.
- The comparison covers the whole path: `config.json` → `lower_act` → key remap → byte-level
  repack → hash check → `validate_keys` → `TorchRuntime` subprocess → `compare_actions`,
  against `ACTPolicy.predict_action_chunk` from the installed `lerobot`.
- The observation is a fixed integer-derived ramp both sides build independently
  (`((i * step + offset) % 4096) / 2^k`), so it is exact in f32 on both sides and no tensor
  crosses the process boundary. Reproducing `torch.Generator` in Rust, or shipping a 3.7 MB
  image over a pipe, were the alternatives.
- The test SKIPs loudly, printing why, when `ES_ACT_CHECKPOINT` is unset, when `lerobot` is
  missing, or when no Python has `torch` — never a silent pass (spec §1.4). Eight unit tests in
  `lerobot.rs` cover the remap, the key/shape declaration, determinism and every refusal
  without needing Python at all.
- `docs/api-notes/lerobot-act.md` carries no `unverified` mark. Every key name, shape and
  behavioural claim in it was read out of the real checkpoint or checked by running the real
  policy; `lerobot-config.md`'s ACT section is updated from the same reading, and its
  "image stats might be per-pixel" question is now answered (`[3, 1, 1]`, per channel).

## findings for later packets

1. **Spec §8.3 cannot express ACT.** `TemporalEncoder { Transformer }` carries a width and
   nothing else — no layer count, no feed-forward width, no decoder, no latent dimension — so
   `lower_to_torch` cannot produce this module from a `LearningGraph`, and the architecture
   parameters come from the checkpoint's `config.json` instead. `act_policy` bridges the gap by
   projecting onto the §8.4 contract the compiler does check, but the claim "the IR represents
   a real policy" currently holds at the *contract* level, not at the *graph* level. Widening
   the node is a spec decision.
2. **`lerobot` 0.6.x moved normalization out of the policy.** `ACTPolicy` no longer has
   `normalize_inputs`/`unnormalize_outputs`; the checkpoint's eight statistics buffers load as
   *unexpected keys* and are ignored. Our lowering carries them, which is the behaviour spec
   §8.7 wants (the IR owns pre/post-processing), but any `es-data` code that assumes the policy
   normalizes should be checked against this.
3. **One camera only.** The node-id table reserves 9/10/11 for the state, image and action
   normalizers, which does not extend to a multi-camera ALOHA checkpoint without a rule for the
   extra image normalizers. Refused explicitly rather than guessed.
4. `es-data`'s flat `FeatureStats` still cannot parse a `VISUAL` feature's nested `[3, 1, 1]`
   statistics (`lerobot-config.md`). Out of scope here; that loader was not exercised.
