# P28 — TOML / `.esgraph` 직렬화 + `.eslayout` sidecar round-trip

Spec: spec 14.1 (저작 프론트엔드들은 canonical IR에 합의한다), spec 14.3 (저장 포맷 표:
`*.toml`, `*.esgraph`, `*.eslayout`, `bundle.eslock`), spec 4.2 rule 7 (`es-ir`는 UI 타입을
알지 못한다; layout은 `.eslayout` sidecar에 존재한다), spec 23.2 (그래프 에디터 뷰 — layout
sidecar가 무엇을 담아야 하는지 읽기 위한 참조이며, 여기서 구현하지 않음).

## context (범위)

```
crates/es-ir/src/serial.rs
crates/es-ir/tests/serial_*.rs
docs/packets/M0/P28.md
```

## spec (사양)

- `IrKind { Task, Observation, Learning, Deployment, Evaluation }`와 태그가 붙은 envelope
  `IrFile<T> { es_schema, kind, body }`로 `.toml`/`.esgraph` 파일이 스스로를 식별하게 한다
  (spec 14.1: `es run task.toml` / `task.esgraph`가 일치해야 한다).
- 제네릭 `write_toml<T: Serialize>` / `parse_toml<T: DeserializeOwned>`에 더해, IR마다
  `{ir}_to_toml` / `{ir}_from_toml` 쌍 하나씩(`task_to_toml`/`task_from_toml`, 그리고
  `observation`, `learning`, `deployment`, `evaluation`도 동일). `{ir}_from_toml`은 파일의
  `kind`가 일치하지 않으면 `SerialError::KindMismatch`를 반환한다.
- TOML에는 `nan`/`inf`를 금지할 방법이 없다(포맷이 이를 bare literal로 받아들인다); `write_toml`은
  유한하지 않은 float를 만나면 `SerialError::NonFiniteFloat`로 거부한다.
- `Graph<N>::nodes`는 `BTreeMap<NodeId, N>`이다. `NodeId`의 derive된 `Serialize`는 bare
  `u32`를 쓰는데 TOML 테이블은 문자열 키를 요구하므로, `TaskIr` / `ObservationIr` /
  `LearningGraph`에 그대로 `toml::to_string`을 호출하면 "map key was not a string"으로
  실패한다. **이 파일 안에서만** 고친다(다른 패킷이 소유하는 `graph.rs`, `task.rs`,
  `observation.rs`, `learning.rs`를 건드리지 않고): private `GraphToml<N>` mirror가
  `nodes`를 10진 문자열로 재키잉하고, IR별 TOML mirror(`TaskIrToml`, `ObservationIrToml`,
  `LearningGraphToml`)가 `graph`/`nodes` 필드에 `GraphToml`을 대신 넣는다. `DeploymentIr`와
  `EvaluationIr`은 `NodeId`로 키잉된 맵이 없으므로 직접 직렬화하며 mirror가 필요 없다.
- `Layout { positions: BTreeMap<NodeId, [f32; 2]>, collapsed: BTreeSet<NodeId>, notes:
  BTreeMap<NodeId, String> }` — `.eslayout` sidecar이며(spec 14.3, spec 23.2의 노드
  위치/collapse 상태/notes) **layout이 존재하는 유일한 곳**이다(rule 7). 두 `BTreeMap`이
  동일한 `NodeId` 키 문제를 겪으므로, `Layout`은 derive 대신 동일한 문자열 키 mirror를 통해
  손으로 작성한 `Serialize`/`Deserialize`를 갖는다.
- `AnyIr { Task(TaskIr), Observation(ObservationIr), Learning(LearningGraph),
  Deployment(DeploymentIr), Evaluation(EvaluationIr) }`는 디코딩된 IR이 다섯 중 무엇인지
  태그한다(`IrKind`를 그대로 반영, 새 trait 없음). `write_esgraph(&AnyIr, Option<&Layout>) ->
  Result<(String, Option<String>)>`는 `.esgraph` 본문을 쓰고, 주어지면 `.eslayout` sidecar를
  독립된 두 문자열로 쓴다; `parse_esgraph(graph_toml, Option<layout_toml>) ->
  Result<(AnyIr, Option<Layout>)>`는 이를 다시 읽는다. layout은 결코 IR에 도달하지 않는다:
  `.esgraph` 문자열은 layout이 붙어 있든 없든 동일하며, `parse_esgraph`는 `graph_toml`만으로
  IR을 디코딩한다.
- `SerialError`는 `es-ir`의 `Cargo.toml`이 `thiserror`에 의존하지 않고 이 패킷이
  `Cargo.toml`을 수정하지 않으므로, 손으로 작성한 `Display`/`Error`를 갖는 평범한 enum
  (`Ser`, `De`, `NonFiniteFloat`, `BadNodeId`, `KindMismatch`)이다.

## oracle (오라클)

```
cargo test -p es-ir serial
```

## acceptance (수용 기준)

- 다섯 IR 모두를 손으로 만든 픽스처에 대해 `parse_{ir}_toml(write_{ir}_toml(ir)) == ir`이
  성립하고, round trip 후 각 IR의 `*_hash()`가 변하지 않는다(`serial_*_round_trips_and_keeps_hash`).
- 임의의 positions/collapsed/notes를 가진 `Layout`은 붙어 있든 없든 `.esgraph` 문자열과
  디코딩된 IR의 해시를 변화시키지 않는다(`serial_layout_never_changes_the_ir_or_its_hash`).
- 한 `IrKind`의 파일을 다른 것으로 파싱하면 일반적인 파싱 실패가 아니라 `KindMismatch`로
  에러가 난다(`serial_mismatched_kind_is_an_error`).
- 어디에든 `NaN` 또는 `±inf`를 담은 값을 쓰면 `NonFiniteFloat`로 실패한다
  (`serial_non_finite_float_is_rejected_on_write`).

## forbidden (금지)

`context` 밖의 모든 파일 — 특히 `graph.rs`, `task.rs`, `observation.rs`,
`learning.rs`, `deployment.rs`, `evaluation.rs`, `hash.rs`, `lib.rs`, `Cargo.toml`(모두
동시 진행 패킷이 소유). `testing` 모듈의 fixture/proptest 헬퍼에 의존하는 것(진행 중인
패킷이 이름을 바꾸는 중) — 여기 픽스처는 손으로 만든다. 그래프 에디터 UI 자체를 구현하는 것
(spec 23.2는 `Layout`이 무엇을 담아야 하는지 알기 위한 읽기 전용 컨텍스트일 뿐). 새 trait
추가 — `AnyIr`은 평범한 enum이며 extension point가 아니다.
