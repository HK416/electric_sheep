# P29 — `TaskNodeFactory` / `LearningNodeFactory` extension points

Spec: spec 6.3 (Task IR node set), spec 8.3 (Learning IR node set), spec 14.5 (editor / LLM
node generation), spec 28.7 gate 10 (built-in node type IDs frozen in M1), Appendix C.1 rule 38
/ `INV-17` (7 allowed extension points). Spec 28.2 Wave 3. Review class B.

## spec

- `TaskNodeFactory` / `LearningNodeFactory`: `kinds() -> &[&'static str]`, `create(kind,
  params: &toml::Value) -> Result<TaskNode | LearningNode, Diagnostic>`, `schema(kind) ->
  Option<NodeSchema>`. These are 2 of the 7 extension points `INV-17` allows in total; no other
  trait is added by this packet.
- `NodeSchema { kind, inputs: Vec<Port>, outputs: Vec<Port>, params: Vec<ParamSchema> }`,
  `ParamSchema { name, ty: ParamType, required, default }`, `ParamType { Bool, Int, Float,
  String, Enum(Vec<String>), Shape, PortType }` — data only, enough for an editor or an LLM
  generator to enumerate nodes and their parameters without linking `TaskNode` /
  `LearningNode`.
- `BuiltinTaskNodes` / `BuiltinLearningNodes` implement the two traits for every variant of the
  spec 6.3 / spec 8.3 node sets by re-tagging `params` and deserializing it as the node enum
  (both derive serde's default externally tagged representation, so this needs no per-kind
  mapping code).
- `BUILTIN_TASK_KINDS` / `BUILTIN_LEARNING_KINDS`: the frozen kind-ID tables (gate 10
  precursor) — every string `IrNode::kind()` can return for that enum, in the same order the
  `kind()` match arms use.
- `TaskNodeRegistry` / `LearningNodeRegistry`: hold registered factories, resolve a kind to the
  one factory that owns it, and reject a `register()` whose kinds overlap an already-registered
  one with a `Diagnostic`.

## acceptance

- `TaskNodeRegistry::with_builtins()` / `LearningNodeRegistry::with_builtins()` build every kind
  in `BUILTIN_TASK_KINDS` / `BUILTIN_LEARNING_KINDS` from `schema(kind)`'s own defaults, and the
  built node's `kind()`, `inputs()`, `outputs()` match the schema.
- `create()` on an unknown kind returns a `Diagnostic` (`FACTORY-001`); `schema()` on an unknown
  kind returns `None`.
- `register()` returns a `Diagnostic` (`FACTORY-002`) when a factory claims a kind that is
  already registered, and leaves the existing owner in place.
- Renaming what `IrNode::kind()` returns for a builtin variant, without updating
  `BUILTIN_TASK_KINDS` / `BUILTIN_LEARNING_KINDS`, fails the schema/create round-trip test
  (gate 10 precursor: a kind rename is caught here before it silently changes `*_hash`).

## forbidden

Any file outside `context`. Editing `Cargo.toml` or `lib.rs` (the `pub mod factory;` line
already exists). Adding a trait beyond `TaskNodeFactory` / `LearningNodeFactory` (`INV-17`).
Adding a diagnostic code to `codes.rs` directly — this packet defines its own `FACTORY-*`
consts locally, `// TODO(P27-merge)`, same as `task::TASK_001`. `HashMap` anywhere in this
module.
