# P06 — CI 계층 구성

Spec: §26.2 (CI 계층 — PR 단계 < 10분), §1.6 (`xtask/`가 모든 검증의 단일
진입점).

## context (범위)

```
.github/workflows/ci.yml
.gitattributes
xtask/src/main.rs
docs/packets/M0/P06.md
```

## spec (사양)

CI는 진입점이 하나다: `cargo xtask ci`. GitHub Actions 워크플로는 툴체인을
준비하고 그것을 호출하는 것 외에는 아무 일도 하지 않으므로, "CI가 무엇을
검사하는가"는 한 곳(`xtask`)에만 존재하고 YAML에 중복되지 않는다.

- `xtask/src/main.rs`의 `cmd_ci`는 순서대로 실행하며 첫 실패에서
  단락(short-circuit)한다: `cargo fmt --check`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace`, 그다음 P01-P03의
  프로세스 내 검사 세 가지(`context-budget`, `layering`, `check-spec-refs`,
  `verify-goldens`) — 이것이 정확히 §26.2 PR 단계 항목 목록이다(단위, 레이어링,
  clippy, fmt; 그 행의 IR/결정성 관련 항목들은 해당 크레이트가 존재하게 되면
  추가된다).
- `.github/workflows/ci.yml`: `ubuntu-latest`, `rustfmt`+`clippy` 컴포넌트를
  갖춘 stable Rust(`dtolnay/rust-toolchain`), target 디렉터리 캐시를 위한
  `Swatinem/rust-cache@v2`, 전체 git 히스토리(`fetch-depth: 0` —
  `verify-goldens`의 merge-base diff에 필요), 단계는 하나: `cargo xtask ci`.
  예산은 §26.2 PR 행의 "10분 미만"이며, 캐싱이 `ubuntu-latest`에서 처음부터 하는
  Rust 빌드를 그 안에 들어오게 해준다.
- `.gitattributes`(`* text=auto eol=lf`): 저장소 전체의 줄 끝을 정규화하여
  `verify-goldens`/`check-scope`의 `git diff`와 `pre-commit`/`commit-msg` 훅이
  Windows와 Linux 체크아웃에서 동일한 바이트를 보게 한다.

## oracle (오라클)

```
cargo xtask ci
```

(CI가 실행하는 것과 정확히 같은 순서를 실행한다; 로컬에서 클린하게 실행되는 것이
"CI가 통과할 것"이라는 오라클이다.)

## acceptance (수용 기준)

- `cargo xtask ci`는 일곱 단계를 순서대로 실행하고 첫 실패에서 멈춘다(0이 아닌
  종료 코드가 즉시 전파되며, 이후 단계는 실행되지 않는다).
- `.github/workflows/ci.yml`은 main으로의 push와 pull request에서 트리거되며,
  유일한 로직 단계는 `cargo xtask ci`다.
- `.gitattributes`가 적용된 상태로 새로 클론하면 어떤 플랫폼에서도 `xtask/**`,
  `docs/**`, `crates/**`가 `LF` 줄 끝으로 체크아웃된다.

## forbidden (금지)

- 워크플로 YAML에 검사 로직을 중복하지 않는다 — 새 검사가 필요하면 새 `run:`
  줄이 아니라 `cmd_ci`에 들어가야 한다.
- merge 단계/nightly/weekly/release CI(§26.2의 나머지 네 단계)는 여기서 다루지
  않는다 — Wave 0는 PR 단계만 배포한다.
- `crates/**` 아래는 수정하지 않는다.
