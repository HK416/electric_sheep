# P14 — Job system + deterministic partitioning

Spec: §3.4 (deterministic scheduling = static partitioning, no device-derived branching),
§18.4 (order-independent merge), §28.2 Wave 2. Review class C.

## context

```
crates/es-core/src/job.rs
crates/es-core/src/lib.rs
docs/design/job-partitioning.md
docs/packets/M0/P14.md
```

## spec

- `partition_static(n_items, n_workers) -> Vec<Range<usize>>` — a pure function of its two
  arguments. No device query, no `available_parallelism`, no load balancing, no work stealing.
  Empty ranges are not emitted.
- `JobSystem::new(n_workers)` — the worker count is always explicit (spec 3.4 forbids
  algorithms derived from device properties).
- `par_for_each_chunk(&mut [T], f)` — `f(chunk_index, range, chunk)`, scoped threads.
- `par_reduce(&[T], map, merge) -> Option<R>` — per-chunk `map` results are merged in
  chunk-index order, never in completion order. `merge` is a caller-supplied closure and is
  not floating-point specific; `es-math`'s `DeterministicAcc` plugs in later.

Design note: `docs/design/job-partitioning.md`.

## oracle

```
cargo test -p es-core --lib job::
```

## acceptance

- `partition_static` covers `0..n_items` exactly once, ascending, over a proptest sweep of
  `(n_items, n_workers)`.
- `par_reduce` equals the sequential fold for every worker count in `1..=8`, and is identical
  across 20 repeated runs (scheduling independence).
- `par_for_each_chunk` visits every element exactly once.

## forbidden

Any file outside `context`. Work-stealing pools, rayon, device-derived worker counts,
floating-point-specific accumulators (that is `es-math`, INV-17 `DeterministicAcc`).
