# P27 — `Diagnostic` type + diagnostic code dictionary

Spec: spec 5.4 (`TYPE-014`), spec 7.2 (`OBS-021`, `OBS-034`), spec 6.6 (`DET-*`),
spec 11.1 (semantic checks), spec 28.2 Wave 3. Review class A.

## context

```
crates/es-ir/src/diag.rs
crates/es-ir/src/codes.rs
crates/es-ir/src/lib.rs
docs/packets/M0/P27.md
```

## spec

- `Diagnostic { code, severity, message, node, port, hint }`, builder-style
  (`Diagnostic::error(code, msg).at(node).port(name).hint(text)`), `Display` mirroring the
  spec's multi-line format:

  ```
  ERROR TYPE-014  time alignment is not specified

    at node 7, port "camera_front"
    <message>

    hint: <hint>
  ```
- `DiagCode` — a newtype string, `Severity { Error, Warning, Info }`.
- `codes::CODES` — one `CodeEntry { code, severity, title, section }` per diagnostic code,
  covering every code printed in the spec plus the codes the checks mandated by spec 5.4 and
  spec 11.1 need in order to be reportable at all. A code's severity comes from this table.

## oracle

```
cargo test -p es-ir --lib -- diag:: codes::
```

## acceptance

- Every entry in `CODES` is unique and matches `^[A-Z]{2,6}-\d{3}$`.
- Every `pub const` code string in `codes.rs` has an entry in `CODES`.
- `Diagnostic::error` picks its severity from the table (`DEP-114` is a warning even when built
  through the error constructor's code path).
- `Display` reproduces the block format above, omitting absent `node` / `port` / `hint`.

## forbidden

Any file outside `context`. Inventing codes for checks no spec section mandates. Running the
checks themselves — this packet supplies the vocabulary, not the compiler passes. Localized
message text (source is English only).
