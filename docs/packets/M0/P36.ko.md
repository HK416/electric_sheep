# P36 — `PhysicsBackend` 트레이트 + `MuJoCoCpu` 어댑터

사양: spec 4.3 (백엔드가 기본 경로이며 capability + 결정성을 선언), spec 17.1 / spec 17.2 /
spec 17.3 (백엔드 레이어, 시맨틱 매핑, 결정성), spec 11.6 (컴파일 타임 capability 확인),
spec 18.1 (정수 tick), spec 18.5 (실패 시맨틱), spec 12.1 (배치 도메인), spec 3.5 (결정성
등급), spec 4.2 (레이어 3, 4). Spec 28.2 Wave 5. 검토 등급 B.

## spec (사양)

### `es-physics-core` (레이어 3)

- `PhysicsBackend` — `INV-17`이 정한 일곱 확장점 중 하나이며, 이 패킷이 추가하는 유일한
  트레이트이다. 오브젝트 세이프(`Box<dyn PhysicsBackend>`)하므로 `es backend compare`가
  런타임에 하나를 선택할 수 있다(spec 17.2):

  ```rust
  fn capabilities(&self) -> &Capabilities;
  fn load(&mut self, scene: &SceneDesc, cfg: &LoadConfig) -> Result<ModelInfo, PhysicsError>;
  fn model_info(&self) -> Option<&ModelInfo>;
  fn reset(&mut self, envs: Option<&[u32]>, state: Option<&StateView<'_>>) -> Result<(), PhysicsError>;
  fn set_ctrl(&mut self, ctrl: &[f64]) -> Result<(), PhysicsError>;
  fn step(&mut self, n_substeps: u32) -> Result<StepReport, PhysicsError>;
  fn state(&self) -> StateView<'_>;
  fn set_state(&mut self, state: &StateView<'_>) -> Result<(), PhysicsError>;
  ```

- `Capabilities { name, determinism: DeterminismTier, batch: BatchSupport { max_envs,
  gpu_resident }, joints / actuators / sensors / contact: BTreeSet<Feature>, float:
  FloatPrecision, supports_reset_subset, supports_state_get_set, quirks: Vec<BackendQuirk> }`.
  `DeterminismTier`는 spec 3.5가 정한 0..4 등급이다. 외부 백엔드는 결코 tier 1을
  선언하지 않는다(spec 4.3). `BackendQuirk { feature, description }`는 근사 매핑을
  숨기지 않고 *선언*하는 방법이다(spec 17.2).
- `Requirements::from_scene(&SceneDesc)`는 씬이 사용하는 기능들을 수집한다.
  `check_requirements(&Requirements, &Capabilities) -> Vec<Unsupported>`는 컴파일러가
  실행 전에 호출하는 함수이다(spec 11.6). 빈 벡터는 해당 백엔드가 씬을 실행할 수 있음을
  뜻한다.
- `LoadConfig { n_envs, rate: Option<TickRate>, seed }`, `ModelInfo { nq, nv, nu,
  nsensordata, nbody, n_envs, rate, qpos / dof / actuator / sensor / body:
  BTreeMap<StableId, IndexRange> }`, `StateView<'a> { n_envs, tick, qpos, qvel, act,
  sensordata, xpos, xquat }`(env-major 슬라이스), `StepReport { tick: PhysTick,
  failures: Vec<(u32, FailureKind)> }`.
- 시간은 전 구간에서 정수 tick으로 표현한다: 어떤 메서드도 초 단위를 받지 않으며, 스텝
  크기는 load 시점에 고정되는 `TickRate`이고, `TickRate::period_secs_f64`는 백엔드
  자신의 경계에서 단 한 번만 호출된다(spec 18.1, spec 3.4).
- 발산(divergence)은 패닉이 아니라 데이터이다: 백엔드가 유한하지 않은 상태를 스스로
  감지하여 `StepReport::failures`로 보고한다(spec 18.5).

### `es-physics-backend` (레이어 4)

- `MuJoCoCpuBackend`: Python 서브프로세스를 통한 MuJoCo(CPU). `python/mujoco_ref.py`는
  stdlib + `mujoco`로 이루어지며 `include_str!`로 임베드되어 `python -c`로 실행되고,
  줄 단위 JSON(`load` / `reset` / `set_ctrl` / `step` / `state` / `set_state` / `quit`)으로
  통신한다. `ES_PYTHON`이 인터프리터를 오버라이드하며, 없으면 `python`, 그다음 `python3`
  순으로 시도한다. `MuJoCoCpuBackend::is_available()`은 `python -c "import mujoco"`를
  실행하여 실패 원인을 설명한다.
- 선언된 capabilities: 결정성 tier 3(물리적 의미에서 — 이것이 곧 MuJoCo이므로), `float:
  F64`, `gpu_resident: false`, `max_envs: 1`. `n_envs > 1`도 동작하지만(스크립트가 env마다
  하나의 `MjData`를 유지하며 반복함) 이는 어댑터 측 에뮬레이션이므로 배치 capability로
  선언하지 않는다: 배치를 요구하는 태스크는 컴파일 타임에 다른 백엔드로 보내진다
  (spec 11.6).
- `scene_to_mjcf(&SceneDesc) -> Result<String, PhysicsError>`: 바디, hinge / slide / ball /
  free 조인트, 기본 geom, 조인트 위의 `motor` / `position` / `velocity` 액추에이터,
  `jointpos` / `jointvel` 센서, 그리고 `<option>` 전체(timestep, gravity, integrator, cone,
  jacobian, solver, iterations, impratio)를 변환한다. 그 밖의 것은 해당 항목의 이름을 담은
  `PhysicsError::Unsupported`가 된다 — spec 17.2는 추측하지 말고 선언하라고 규정한다.
  쿼터니언은 MJCF의 wxyz로 변환되며, 각도는 라디안으로 기록된다.
- `docs/api-notes/mujoco.md`는 `mujoco` 버전, 사용되는 정확한 호출 및 필드, JSON 프로토콜을
  고정(pin)한다.

### 패킷 개요와의 차이 및 그 이유

- `set_ctrl`과 `set_state`는 `Result`를 반환한다: 버퍼 길이는 경계에서 검증되며
  (`ShapeMismatch`), 프로세스 외부 백엔드는 쓰기 자체에서 실패할 수 있다.
- `model_info`는 `&ModelInfo`가 아니라 `Option<&ModelInfo>`를 반환한다: `load` 이전에는
  모델이 존재하지 않으며, 패닉하는 접근자를 모든 백엔드에 강제하는 것은 트레이트가 할 일이
  아니다.
- `LoadConfig`는 초 단위 timestep이 아니라 `TickRate`를 담으므로, spec 18.1은 관례가
  아니라 타입으로 강제된다.
- 이미터는 `timestep`과 `gravity`만이 아니라 `<option>` 전체를 기록한다: `integrator`나
  `cone`을 누락하면 물리 동작이 조용히 바뀌게 되는데, 이는 spec 17.2가 방지하고자 하는
  실패 양상이다.

## oracle (오라클)

```
cargo test -p es-physics-core -p es-physics-backend
```

MuJoCo에 의존하는 테스트는 `is_available()`이 실패하면 `SKIP <name>: <reason>`을 출력하고
통과 처리되므로, 선택적 패키지인 `mujoco`가 없는 머신에서도 CI가 실패하지 않는다. 설치되어
있으면 실제로 실행되며, `ES_PYTHON=<interpreter>`로 venv를 선택할 수 있다.

## acceptance (수용 기준)

- `check_requirements`는 충족되지 않은 모든 요구사항을 각각 한 번씩, 안정적인 순서로
  보고하며, 충족된 요구사항에 대해서는 아무것도 보고하지 않는다.
- `PhysicsBackend`는 오브젝트 세이프하다: `NullBackend` 테스트 더블이
  `Box<dyn PhysicsBackend>`를 통해 검증된다.
- `scene_to_mjcf`는 `tests/fixtures/mjcf/pendulum.xml`과 `arm2.xml`을
  `es_assets::parse_mjcf`를 통해 왕복시키며, 바디/조인트/geom/액추에이터/센서의 개수와
  종류가 보존된다. 매핑 불가능한 모든 항목(mesh geom, tendon, site sensor, general
  actuator)은 메시지에 이름이 포함된 채로 거부된다.
- 프로토콜 encode/decode는 Python 없이 미리 준비된 JSON 라인을 대상으로 단위 테스트되며,
  `f64`의 비트 단위 왕복과 잘못된 형식의 응답 처리를 포함한다.
- MuJoCo가 설치된 경우: 0.3 rad로 들어올린 진자를 1 ms 간격으로 100 tick 스텝하면 유한한
  상태와 보고된 실패 없이 매달린 위치를 향해 움직인다. 동일한 상태에서 시작한 두 실행은
  비트 단위로 동일하다. `n_envs = 2`는 두 개의 독립된 env를 스텝하며, 부분집합 리셋은
  자신의 env에만 영향을 준다.

## forbidden (금지)

`context` 밖의 모든 파일. `crates/es-assets/**`(인접 패킷이 `gltf.rs`, `urdf.rs`,
`fuzz.rs`를 소관). 루트 `Cargo.toml`, `clippy.toml`, `rustfmt.toml`. `PhysicsBackend` 외의
어떠한 트레이트도 추가 금지(`INV-17`: 일곱 확장점은 고정되어 있다). `HashMap` /
`HashSet`(spec 3.4). 스텝 루프 어디에서도 부동소수점 시간 누산 금지(spec 18.1). 발산한
env 상태를 보고하는 대신 패닉시키는 것(spec 18.5). 외부 백엔드가 결정성 tier 1을
선언하는 것(spec 4.3). 물리 구현: 이 크레이트는 엔진에 매핑할 뿐 엔진 자체가 아니다
(spec 17.4는 M4+ 범위이며 이 패킷의 범위 밖).
