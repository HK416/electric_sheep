## spec

Archetype-based SoA storage, minimal by design.

- `Entity` — `{ index: u32, generation: u32 }`, `Copy + Ord`; a stale handle never resolves.
- `Component` — blanket marker for `'static + Send + Sync`.
- `World` — `spawn`, `despawn`, `insert`, `get`, `get_mut`, `query::<Q>()`.
- `query::<(&A, &mut B)>()` yields `(Entity, Q::Item)` over every archetype that holds all of
  the query's component types.
- Iteration order is deterministic: archetypes in creation order, rows in the order the entity
  entered that archetype (`despawn` swap-removes, which permutes rows — still a pure function
  of the operation sequence).
- `BTreeMap` / `Vec` only; `HashMap` is denied by `clippy.toml` (spec 3.4).
- No change detection, no events, no schedules, no systems, no component removal.

`unsafe` is confined to the column pointer fetch in the query iterator; every site carries a
`// SAFETY:` comment. Duplicate component types in one query panic (aliasing).

```
cargo test -p es-core --lib ecs::
```

## acceptance

- Round trip: `spawn` -> `insert` -> `get` / `get_mut` -> `despawn`; a stale `Entity` gives `None`.
- Archetype migration preserves previously inserted component values.
- Proptest: replaying the same operation sequence into two `World`s yields identical query
  iteration order (order is a pure function of the operation sequence).
- `cargo clippy -p es-core --all-targets -- -D warnings` clean.

## forbidden

Any file outside `context`. Systems / schedules / events / change detection. `HashMap`.
Parallel queries (P14 owns threading). Depending on `es-math`.
