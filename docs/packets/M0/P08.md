# P08 — transcendental minimax polynomials (`es_math::approx`)

Spec: §3.2, §3.4, Appendix D `DET-010`. Design doc (written first): `docs/design/transcendental.md`.

## context

```
crates/es-math/src/approx/mod.rs
crates/es-math/src/approx/coeffs.rs
crates/es-math/src/lib.rs
docs/design/transcendental.md
docs/packets/M0/P08.md
```

## spec

`f32` implementations of `sin`, `cos`, `exp`, `ln`, `atan2`, `sqrt`, `rsqrt` with a fixed
evaluation order, so that a kernel gets the same bits on every host and (P09) on the GPU.

- Coefficients live as decimal literals in `approx/coeffs.rs`, one `pub const` per
  coefficient, with the provenance comment required by the design doc. No digit separators
  (they would break the P09 literal comparison); `clippy::unreadable_literal` is allowed in
  that file only.
- Horner form, written as one expression per polynomial. No reassociation, no `mul_add`, no
  `fast-math`, no lookup tables, no branch on device properties.
- Range reduction exactly as tabulated in the design doc, including the `_LO` companion
  constants for `PI`/`PIO2`/`PIO4` that the `atan2` quadrant fix-up needs to stay under
  2 ULP.
- IEEE specials handled explicitly (`NaN`, `±inf`, `±0`, `ln` of non-positive).
- Target ≤ 2 ULP over the primary domain; outside it the value is sensible but unbounded.

## oracle

```
cargo test -p es-math approx:: -- --nocapture
```

The test prints the measured maximum ULP per function and fails above 2 ULP.

## acceptance

- Dense linear sweep + deterministic pseudo-random sweep, ≥ 200k points per function over the
  primary domain, referenced against the `f64` `std` implementation rounded to `f32`.
- Measured max ULP ≤ 2 for every function; the table in `docs/design/transcendental.md`
  matches the printed numbers. Measured: `sin` 1, `cos` 1, `exp` 1, `ln` 1, `atan2` 2,
  `sqrt` 0, `rsqrt` 1.
- Specials: `sin(NaN)`, `exp(-inf) == 0`, `exp(inf) == inf`, `ln(0) == -inf`, `ln(-1)` NaN,
  `atan2(0, 0) == 0`, `rsqrt(0) == inf`.

## forbidden

- No `std` transcendental calls in `src/approx/mod.rs` other than `f32::sqrt` (the one
  correctly-rounded IEEE primitive the design doc allows) — the `f64` `std` functions appear
  in the test module only, as the reference oracle.
- No Payne–Hanek reduction, no `f64` fallback path, no per-target specialisation.
- Do not touch `scalar.rs`, `conventions.rs`, `reduce.rs`, `simd.rs`.
