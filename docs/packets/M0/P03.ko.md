# P03 — golden 정책 + `verify-goldens`

Spec: §1.4 (오라클 우선 원칙 — "골든은 CI 읽기 전용"), §1.7 (실패 모드 표: "테스트
고치기").

## context (범위)

```
xtask/src/goldens.rs
xtask/src/main.rs
docs/packets/M0/P03.md
```

## spec (사양)

`tests/golden/**`는 통과하는 테스트가 일치시켜야 할 참조 픽스처(골든
이미지/텐서, §1.4)를 담고 있으며, 그 반대는 성립하지 않는다 — 에이전트는 자신의
출력에 맞춰 골든 파일을 수정해서 실패하는 테스트를 "고쳐서는" 안 된다. `cargo
xtask verify-goldens`는 이를 기계적으로 강제한다:

- `HEAD`와 `main`과의 merge-base 사이에서 `tests/golden/**`를 diff한다(둘 다
  해석되지 않으면 `origin/main`으로, 그다음 `HEAD` 자신으로 폴백한다 — 예를 들어
  `main` 위에 있거나 detached 체크아웃 상태여서 의미 있는 비교 대상이 작업
  트리뿐인 경우). 여기에 `HEAD`에 대한 작업 트리 diff를 더한다(커밋되지 않은
  수정을 포함시키기 위함).
- `git diff --name-status`는 `A`/`M`/`D`/`R…` 중 하나를 보고한다; `A`(완전히 새로운
  골든 파일)만 허용된다. `M`, `D`, 이름 변경은 모두 위반이다.
- `GOLDEN_UPDATE=1`은 검사를 우회한다(드물게 의도적으로 골든을 갱신할 때를 위한
  것으로, 에이전트가 자신의 PR을 조용히 통과시키는 것이 아니라 사람/리뷰된
  커밋으로 이루어져야 한다).
- `tests/golden/` 디렉터리가 아직 없으면 → 검사할 것이 없으므로 명령은 통과한다.

`classify(&[Change]) -> Vec<String>`가 순수 규칙이다(테스트에서는 리터럴
`Change{status, path}` 픽스처를 입력한다); `run()`은 그 주위를 감싸는 얇은 git 셸
래퍼다.

## oracle (오라클)

```
cargo test -p xtask goldens::
cargo xtask verify-goldens
```

## acceptance (수용 기준)

- 단위 테스트: `A` 변경은 위반을 만들지 않는다; `M`/`D`/`R…`은 각각 위반을
  만든다.
- `cargo xtask verify-goldens`는 현재 저장소에서 통과한다(`tests/golden/`이 아직
  없음).
- `GOLDEN_UPDATE=1`을 설정하면 실패할 뻔한 상황이 통과로 바뀐다(`tests/golden/`이
  생긴 뒤에 실제로 실행된다; 그 전까지는 죽은 기능이 아니라 아직 실행되지 않는
  코드 경로다).

## forbidden (금지)

- 골든 파일의 내용이나 형식 정책은 여기서 다루지 않는다 — 이 패킷은
  `tests/golden/**` 아래에 무엇이 오든 그것의 읽기 전용성만 강제한다.
- 이 패킷에서 `tests/golden/` 디렉터리나 어떤 픽스처도 추가하지 않는다.
- `crates/**` 아래는 수정하지 않는다.
