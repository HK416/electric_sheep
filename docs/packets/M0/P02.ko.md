# P02 — 레이어링 검사 (§4.2 rule 9종)

Spec: §4.2 (크레이트 레이어링), Appendix B.8 (LAYERS 테이블 + 레이어링 검사).

## context (범위)

```
xtask/src/layering.rs
xtask/src/main.rs
docs/packets/M0/P02.md
```

## spec (사양)

`cargo xtask layering`은 워크스페이스 루트에서 `cargo metadata --no-deps
--format-version 1`을 실행하고, 모든 워크스페이스 패키지에 대해 그 *직접* 선언된
의존성 이름을(이것으로 충분하다 — 규칙 1은 간선 단위로만 성립하면 패키지 전체에
대해 이행적으로 성립한다) Appendix B.8의 `LAYERS` 표와 §4.2의 번호가 매겨진
규칙들에 대조한다:

1. 크레이트는 엄격히 더 낮은 레이어에만 의존한다; 동일 레이어 의존성은 없다.
2. `es-physics-cpu`와 `es-physics-gpu`는 서로 의존하지 않는다.
3. 레이어 ≤ 2는 `es-gpu`를 제외하고 `ash`나 `gpu-allocator`에 의존해서는 안 된다.
4. 어떤 것도 `es-editor`에 의존하지 않는다.
5. `es-transport`만이 `cust`, `cudarc`, 또는 이름이 `hip*`인 크레이트에 의존할 수
   있다.
6. `es-ir`는 `es-compile`, 어떤 `es-physics-*`, `tch`, `torch*`, `ort`에도 의존해서는
   안 된다.
7. `es-ir`는 `egui*`나 `winit`에 의존해서는 안 된다.
8. `es-safety`는 `es-policy`에 의존해서는 안 된다(INV-11).

`LAYERS` 표에 없는 `es-*` 워크스페이스 크레이트는 그 자체로 오류다(표는 크레이트
목록과 항상 동기화되어야 한다); 표에는 있지만 아직 `crates/`에 존재하지 않는
크레이트는 오류가 아니다 — Wave 0는 트리 대부분보다 앞서 진행된다.

규칙 평가(`check_layering`)는 `&[Pkg]`(`Pkg { name, deps }`)에 대한 순수 함수다;
`cargo metadata` 파싱은 그 주위를 감싸는 얇고 별도로 검사 가능한 shim이므로, 규칙
로직 자체는 테스트에서 셸을 호출할 필요가 없다.

## oracle (오라클)

```
cargo test -p xtask layering::
cargo xtask layering
```

## acceptance (수용 기준)

- 단위 테스트는 가짜 `&[Pkg]` 의존성 그래프를 입력하여 8개 규칙 각각이 위반
  픽스처에서는 발동하고 준수 픽스처에서는 조용함을 검증한다.
- `cargo xtask layering`은 현재 `crates/*`를 가진 실제 워크스페이스에 대해 0으로
  종료한다.
- 알 수 없는 `es-*` 크레이트 이름(`LAYERS`에 없는)은 조용히 건너뛰지 않고 오류로
  보고된다.

## forbidden (금지)

- `cargo_metadata` 크레이트에 대한 의존 금지 — 이 검사가 필요로 하는 필드
  (`packages[].name`, `packages[].dependencies[].name`)는 `cargo metadata`의
  JSON에서 `serde_json`으로 직접 읽는다.
- 누락된 크레이트에 대해서는 빌드를 실패시키지 않는다; 존재하지만 잘못 배치되었거나
  존재하지만 목록에 없는 경우에만 실패시킨다.
- `crates/**` 아래는 수정하지 않는다.
