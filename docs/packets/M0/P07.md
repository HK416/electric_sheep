## spec

`Scalar` is one of the seven allowed extension points (INV-17). It is the type parameter
§3.3 calls for: `F64Native` / `DoubleFloat` / `F32`, here `f64` / `DoubleF32` / `f32`.

- Sealed trait (`sealed::Sealed` supertrait): the three representations are the whole set,
  so a fourth impl is a spec change, not a user extension.
- Required surface: `Add`/`Sub`/`Mul`/`Div`/`Neg`, `sqrt`, `abs`, `PartialOrd`/`PartialEq`,
  `from_f64`/`to_f64`, `ZERO`/`ONE`/`EPSILON`, `is_finite`.
- `DoubleF32` is an error-free-transformation pair of `f32` (`hi`, `lo`) with
  `|lo| ≤ ½ ulp(hi)`: Dekker/Knuth `two_sum` + `two_prod`, Bailey double-double `add`/`mul`/
  `div`/`sqrt`.
- `two_prod` is the **only** place `mul_add` is used, and it is required there:
  `err = fma(a, b, -p)` is what makes the product split exact. `f32::mul_add` is a
  guaranteed-fused single-rounding operation in Rust, so this is deterministic on every host.
  Nothing else in the crate may use `mul_add` (§3.4 forbids hidden contraction).

## acceptance

- `f32`, `f64`, `DoubleF32` all implement `Scalar`; no other impl exists and none can be
  added outside the crate.
- proptest: `DoubleF32::from_f64(x).to_f64()` round-trips `x` to within `2^-47` relative
  (the representation carries ~48 significand bits, not 53), and `DoubleF32` add/mul are
  never less accurate than the `f32` result when measured against `f64` ground truth.
- proptest: `two_sum` / `two_prod` are error-free — `a + b == s + e` and `a * b == p + e`
  exactly in `f64`.
- `cargo clippy -p es-math --all-targets -- -D warnings` clean; no `unsafe`.

## forbidden

- No generic numeric tower (`num-traits`), no `Float`-style trait with dozens of methods, no
  transcendentals on `Scalar` (those are `approx`, P08, and `f32`-only).
- Do not touch `approx/`, `conventions.rs`, `reduce.rs`, `simd.rs` (P08–P12).
- No root `Cargo.toml` edits.
