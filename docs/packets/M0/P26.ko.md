# P26 — IR 간 교차 검사 규칙

Spec: spec 11.1 (`Cross-IR Check` 단계), spec 5.1 (IR 경계), spec 7.4
(`ObservationSpec` <-> Observation IR), spec 8.4 / 8.5 (정책 계약, 액션 모델링),
spec 9.2 / 9.3 / 9.5 (Deployment IR, envelope, 시뮬레이션-실제 동일성), spec 10.4 (평가

## spec (사양)

- `IrBundle<'a> { task, observation, learning, deployment, evaluation: Option<_> }`와
  `check(&IrBundle) -> Vec<Diagnostic>`: spec 11.1이 명시하는, IR 경계를 *가로지르는* 모든 규칙을 다룬다.
  각 IR 자체의 `validate`가 먼저 실행되어 자신에 대해 답하고, `check`는 경계에 대해서만 답한다.
- 규칙은 spec 11.1이 경계를 나열하는 순서를 따른다:
  1. `Observation::task_ref`는 Task IR의 `task_hash`여야 하며(`XIR-001`), 모든 Observation
     소스 노드(`ImageInput` / `StateInput` / `LanguageInput`)는 Task IR이 선언한 채널을
     (`XIR-002`) 그 채널이 선언한 타입으로(`PortType::compatible`을 통한 `TYPE-001..TYPE-020`)
     읽어야 한다 — Task가 선언하고 Observation이 구현한다(spec 7.4).
  2. `Observation::outputs`와 `PolicyContract::inputs`는 동일한 텐서를 지칭해야 하며(`XIR-010`)
     elem, shape, unit, frame이 일치해야 한다; 이미지 출력은 그래프가 실제로 전파하는 지오메트리를
     알려야 하고(`TYPE-020`, `INV-14`); 정책 입력은 Normalized, Dimensionless 또는
     Token이어야 하며(`TYPE-011`); `TemporalWindow::n_steps`는 `observation_window`와
     같아야 한다(`XIR-011`). 클록과 `ImageSpec`이 교차점이다: `TimeRef::Tick` 텐서 포트는
     센서 클록을 정당하게 소비할 수 있고, 텐서 포트가 `ImageSpec`을 다시 명시할 필요는 없다.
  3. `Learning` <-> `Deployment`: `action_dim`을 배포된 액션 계약과 비교하고
     (`XIR-020`), 실행 모드(`XIR-021`), `horizon` / `execute_chunk`(`XIR-022`),
     `replanning_hz`가 `dt_ctrl`과 정수 관계에 있는지(`XIR-023`), `runtime.deadline_ms`가
     워치독의 추론 예산 안에 있는지(`XIR-024`), 그리고 측정된 지연이 그 예산을 초과하거나
     청크 버퍼링 없이 제어 주기를 초과할 때 `LRN-052`를 검사한다.
  4. Task `ActionSpec`을 정책 계약 및 배포된 액션과 비교: `dim`(`XIR-030`),
     space(`XIR-031`), `control_rate_hz`를 `rate.control`과 비교(`XIR-032`).
  5. `Deployment.envelope` <-> 로봇 capability: envelope가 해당 로봇에 대해 Task IR의
     `JointState` 채널이 선언한 것보다 많은 관절을 포함하면 `DEP-031`.
  6. `Evaluation` <-> `Task` / `Observation`: 다이제스트인 참조는 반드시 번들의 다이제스트여야
     하며(`XIR-040`); `INV-15` — `training_only`가 아닌(따라서 구조적으로 끌 수 없는) `Augment`
     노드는 평가 allow-list에 이름이 올라 있어야 하고(`XIR-050`), allow-list는 실제 `Augment`
     노드만 이름으로 담아야 한다(`XIR-051`).
- `XIR-0xx`는 `codes.rs`에 `XIR-` 블록이 생기기 전까지 `// TODO(P27-merge)`로 로컬 선언한다;
  `LRN-052`, `DEP-031`과 `TYPE-*` 코드는 `codes.rs`에서 온다.

## acceptance (수용 기준)

- 유효한 번들 — 7-DoF + 그리퍼 Franka급 로봇, 224x224로 리사이즈된 640x480 sRGB 카메라 1대,
  ACT 형태의 learning 그래프, 50/20 청크의 100 Hz 제어 — 는 진단을 하나도 내지 않아야 하고,
  다섯 IR 각각이 단독으로 clean하게 validate되어야 한다.
- 규칙당 위반 픽스처 1개가 정확한 코드를 검증한다: `XIR-001`, `XIR-002`, `TYPE-002`
  (선언), `XIR-010`, `TYPE-002`(계약), `TYPE-011`, `TYPE-020`, `XIR-011`,
  `XIR-020`, `XIR-021`, `XIR-022`, `XIR-023`, `XIR-024`, `LRN-052`, `XIR-030`, `XIR-031`,
  `XIR-032`, `DEP-031`, `XIR-040`, `XIR-050`, `XIR-051`.
- `evaluation: None`인 번들은 앞의 다섯 규칙만 검사하고 여섯 번째에 대해서는 침묵한다.
- 저작 경로로 작성된 Evaluation 참조는 해시가 아니므로 검사 대상이 아니다.
- `cross.rs`는 하나의 context window 안에 머문다(소스 599줄).

## not checkable yet (아직 검증 불가)

`DEP-031`의 완전한 형태 — envelope의 *값*을 로봇의 토크, 속도, 위치 capability와 비교하는 것 —
는 로봇 capability 기술(記述)을 필요로 한다. `RobotRef`는 이름, target, 관절 수만 담고 있고
어떤 IR도 capability 테이블을 담고 있지 않으므로, 여기서는 envelope의 폭만 검사 가능하다.
spec 11.6의 capability 데이터가 들어오면 다시 다룬다.

## forbidden (금지)

`context` 밖의 모든 파일. `codes.rs`(P27이 코드를 병합 중) 수정, `lib.rs`, `Cargo.toml`,
또는 다섯 IR 모듈 중 하나라도 수정 — 여기서 발견된 불일치는 보고만 하며 IR 쪽을 패치하지 않는다.
IR 모듈의 `testing` 헬퍼에 의존하는 것(픽스처는 손으로 만든 것이므로, 이웃 패킷의 일관성
개념이 경계 버그를 숨길 수 없어야 한다). IR이 이미 자신에 대해 수행하는 검사를 재구현하는 것.
`HashMap`(spec 3.4). 새 trait나 extension point(`INV-17`).
