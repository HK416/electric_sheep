# M14 Q-V — 플랜 Q의 실제 실행(S3, 동작 블록)

플랜 Q의 Task Q5, 이 PC(Windows 11, RTX 3060 12 GB, RAM 64 GB)에서, 2026-09-29, 오너가 요청한
대로 실행마다 에디터를 열어 둔 채로. 모든 프로젝트는 에디터 자신의 모델(`Project::create`,
`write_run`)이 만들었고, 모든 실행은 에디터의 Start가 쓰는 argv로 시작했다.

## 1. ②에서의 시도(패킷 Q4)

임시 힌트 카드 프로젝트; 블록 1 "큐브 위"를 ②에서 4.5 cm에서 6 cm로 바꿨다; "한 번 해 보기"가
`es eval run --jobs 1`을 시드 1001(모든 평가 시드 밖의 시드, Q3 리뷰)에서 한 에피소드로 돌렸다:
**성공**, 511프레임, 유도한 `evaluation.toml`에서 `report.json`까지 16.5초. ②는 블록 1에
손목 각도 경고("이 손목 각도에서는 팔이 항상 닿지는 않는다")를 표시했다 — 그 한 번의 시도는
마침 닿는 위치였다.

## 2. 편집한 프로그램의 짧은 실행(Q5): 버그 세 개를 찾았다

같은 편집, 새 프로젝트(`target/yv/cube-hint-q5`), short 프리셋, 시연 200개.

| stage | result |
|---|---|
| collect | **성공 10, 실패 187, 타임아웃 3**; 에피소드 길이 `511, 520, 520, 1800, …, 11, 1, 1, 1, …` — **1프레임**짜리 에피소드 186개 |
| expert gate | 통과, nominal 11/16 (0.6875 ≥ 0.5) |
| train | 손실이 **1,130걸음부터 NaN**; 에디터의 불은 초록으로 남음; 3,800걸음에서 손으로 멈춤 |

- **수집기가 중단을 이후 모든 에피소드로 새게 했다**(P-M14-R1, 버그 1). 13번째 에피소드는 진짜
  실패였다 — 블록 1이 닿지 못했고, 시연은 이름으로 끝난다(스펙 17.2) — 그런데 `Intervened`
  래퍼의 `aborted` 플래그가 지워지지 않아서 이후 각 에피소드가 첫 프레임 뒤에 끝났다. 같은 16개
  시드(1001–1016)에서 측정하면 편집한 프로그램은 평가가 돌리든 수집기가 돌리든 16개 중 11개에
  성공한다; 13번째 에피소드 전에는 수집이 13개 중 10개였다. 같은 래퍼는 오래된 `injected` 플래그도
  들고 있어서, 모든 전문가 데이터셋은 두 번째 에피소드부터 각 에피소드의 첫 프레임들을 사람이
  조작한 것으로 기록했다: 다시 수집한 데이터셋은 이제 `intervention` 열과 content 해시가 다르다.
  원래 프로그램은 중단하는 일이 없어서(200/200) 이전 실행에서는 드러나지 않았다.
- **발산한 학습이 보이지 않았다**(버그 2). `train_act.py`가 JSON이 아닌 `"loss": NaN`을 출력했고,
  `es train`은 그 줄들을 버렸으며 텔레메트리 와이어도 NaN 프레임을 거부해서, 1,130걸음 이후의 어떤
  점도 에디터에 닿지 못했고 에디터의 "망가짐" 규칙은 한 번도 발동하지 않았다. 이제 비유한 값은
  `null`로 쓰고 NaN으로 다시 읽으며, 트레이너는 처음 나온 비유한 손실에서 이름 있는 메시지와 함께
  멈추고, 불의 *망가짐*이 *멈춤*보다 우선한다.
- **사이클이 대부분 실패한 수집으로 학습했다**(버그 3). 이제 `es loop cycle`은 성공한 시연이 절반
  미만이면 학습 단계 전에 거부하고, ②에서 프로그램을 고치라고 알려 준다.
- **에디터를 지켜보며:** 수집 도중에 열면 붙은 뒤에 들은 시연만 셌다(25개가 끝났는데 "200개 중
  2개") — 고침(`9ef9b24`: 개수는 에피소드 인덱스에서 오고, 성공은 "에디터가 본 N개 중"으로
  읽힌다).

## 3. 그립 대기(M13/Z7의 발견, 측정)

Z7은 커밋된 프로그램의 모든 시연이 그리퍼를 닫고 들어 올리기까지 221프레임(4.4초, 에피소드의
43 %) 동안 가만히 있고, 오래 학습한 정책이 시간 초과된 시도 90개 중 65개를 *들어 올리지 못함*으로
실패한다는 것을 발견했다. 두 그립 대기를 1초로 하면 시연자는 여전히 4개 중 4개에 성공하고(시드
5000–5003) 평면 횟수는 같으며, 시연은 38 % 짧아진다.

실험: *long*(60,000걸음)의 힌트 카드, Z7과 같은 시드와 설정, ②에서 바꾼 것은 하나 — 두 "wait"
블록을 5초에서 1초로. 프로젝트 `target/yv/cube-hint-wait1`.

| | Z7 (5초 대기) | 1초 대기 |
|---|---|---|
| demonstrations | 200/200, 103,881프레임 | 200/200, 63,901프레임 |
| expert gate | 통과 | 통과 |
| previews 1,000 / 5,000 / 20,000 / 60,000 | 각각 0/4; 16개 어디서도 큐브가 들리지 않음 | 각각 0/4; 마지막 셋에서 1, 2, 2개가 들렸고, 통까지 옮겨졌지만 놓지 못함 |
| train (60,000걸음) | 54.8분 | 약 55분 (1,150 samples/s) |
| eval, nominal | 0/16 | **2/16** |
| eval, all suites | 6/96 | 4/96 |
| 큐브를 든 시도(96개 중) | 30 | 38 |
| 큐브가 통 안에서 / 통 위에 든 채 끝남 | 14 / 12 | 17 / 9 |
| `envelope_violation_rate`, nominal (토크 잡음) | 0.117 (0.436) | 0.135 (0.707) |
| whole run | 1시간 38분 | 1시간 24분 |

**이것이 말하는 것과 말하지 않는 것.** 더 짧은 대기는 nominal을 0/16에서 2/16으로 옮겼다 — 오늘의
데이터에서 힌트 카드의 첫 nominal 성공이다 — 그리고 들어 올리기는 96개 중 30에서 38로 늘었지만,
모든 스위트는 6에서 4로 떨어졌고, 팔마다 학습 한 번은 M10 리뷰가 측정한 ±0.3의 실행 간 편차(S-4)를
안고 있다. 따라서 4.4초의 정지 구간이 정책이 실패하는 이유라는 것은 **입증되지 않았다**; 팔마다
학습 시드 하나를 더 돌리면 정리된다. 프리뷰는 차이를 과장했다: Z7의 프리뷰 위치 네 곳은 마침 한
번도 들리지 않았지만 최종 평가에서는 96개 중 30개에서 들렸다 — 에피소드 넷은 진행을 지켜보는
용도이지 실행을 비교하는 용도가 아니다.

**두 실행이 공유하는 것: 로봇이 놓지 않는다.** 두 실행 모두에서 시도 다섯 번 중 한 번쯤(96개 중
20개와 22개, 성공 제외)은 큐브가 통 안이나 위에 있는데 과제가 그것을 세지 않은 채 끝났다 — 손으로
확인한 것들은 그리퍼가 닫혀 있어서 과제의 `gripper > 0.85` 절에 못 미쳤다. 모든 시연은 놓는 동작을
**27프레임**(0.54초)만 담는다. release 블록의 대기가 얼마이든 그렇다 — 그리퍼가 0.85를 넘는 순간
에피소드가 성공으로 끝난다 — 그래서 놓는 동작이 데이터에서 가장 얇은 부분이다. 에디터는 그런
시도를 *너무 늦음*이라 불렀고(고침: `NotReleased`, P-M13-R4) 통 위에 든 경우는 *바깥에 남음*이라
불렀다(고치는 중); R4의 첫 조언("연 뒤에 더 기다려라")은 도움이 될 수 없어서 고쳤다(`e88f920`).
