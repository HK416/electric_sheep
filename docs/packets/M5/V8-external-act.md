# M5 V8 — an external ACT through the runtime

Design note: `docs/design/visible-learning.md` **section 7.16**, and sections 7.12–7.15 for the
harness it runs on. Spec: §1.4, §5.3, §7, §8.1, §8.4, §8.7, §8.9, §9.2, §19.1, §25.1. API notes:
`docs/api-notes/lerobot-act.md`, `docs/api-notes/lerobot-dataset.md`, `docs/api-notes/lerobot-config.md`.
Depends on V1/V1b/V1c (the demonstrations and the v3.0 export), V3 (the suite), V5 (`--jobs`),
V6/V6b (the harness that passes the expert and executes chunks the way collection does).

## the question this packet exists to answer

Spec §8.1 opens with a promise: **the network internals are opaque and the interface semantics
are typed** — "we do not invent a proprietary policy architecture". Plan V has not tested that
promise. V2/V2b trained an IR-*shaped* ACT: `VisionEncoder{ResNet18, pretrained=false}` →
`Fusion{Concat}` → `TemporalEncoder{Transformer}` → `PolicyHead{Regression}`, which has no CVAE,
no DETR decoder, no pretrained backbone and no per-camera token grid, because spec §8.3's node
parameters carry a width and nothing else. That policy scores 0/16 after every harness fix, and
V7a's sim-privileged variant scores 0–1/16 (sections 7.13–7.15).

So there are two hypotheses and the measurements so far cannot separate them:

1. **the model** — our ACT-shaped graph is not ACT, and a real one would do the task;
2. **the data, the physics or the expert** — 50 demonstrations of a 7 s scripted motion at
   96×96 are not enough, or the contact model is not learnable, and no policy would.

**V8 replaces the model and nothing else.** Same demonstrations, same Task IR, same Deployment
IR and Safety Plane, same `es eval run`, same seeds, same acceptance — but the policy is
LeRobot's own ACT (CVAE, DETR encoder/decoder, ImageNet-pretrained ResNet18), trained by
`lerobot-train`, imported through `crates/es-policy/src/lerobot.rs`, the lowering the M4 gate-5
test already proved bitwise-equal on `lerobot/act_aloha_sim_transfer_cube_human`.

**Either outcome is information, and the stop rule is written before the measurement.** If V8
reaches `success_rate ≥ 0.5` nominal, hypothesis 1 is confirmed and the Learning IR's node set is
the thing to fix. If V8 also fails, hypothesis 1 is refused: the next packet opens the scene, the
contact model or the expert's trajectories, **not** the optimizer and not the IR. No threshold in
`evaluation-v8.toml` is lowered either way.

## the decisions, and what each rests on

### 1. Where an external policy's architecture lives

**In its checkpoint, and the IR declares the hash of the bytes that carry it.**

`crates/es-policy/src/lerobot.rs` already said why this cannot be otherwise: spec §8.3's
`TemporalEncoder { Transformer }` carries a width, no layer count, no feed-forward width and no
latent dimension, so `lower_to_torch` cannot emit DETR-style ACT from a `LearningGraph`. Widening
the node is a spec change, not a packet. What *is* available is spec §8.1's own division:

```
   LearningGraph → Preprocessor (fully described in the IR)  +  PolicyHandle (opaque)
```

An external ACT needs no preprocessor nodes — the Observation IR does all of it — so the bundle's
`LearningGraph` has **an empty node graph and a fully typed `PolicyHandle`**, which is exactly the
shape §8.1 draws for this case. The architecture parameters ride in the checkpoint's own
`config.json`, which `remap_checkpoint` records in the output safetensors' `__metadata__` under
`es.lerobot.act.config`, and `TorchRuntime::load` lowers with `lower_act` when it finds one.

Three properties make that honest rather than a back door:

* **The hash chain still covers it.** The config is inside the bytes `WeightsRef::hash` names, so
  it is inside `policy_hash` (§5.3). `load` verifies the declared hash before Python sees
  anything, so the IR decides which module runs — transitively, through the hash.
* **Nothing loosened.** `validate_keys` still runs, `parse_header` already skipped `__metadata__`,
  the module source is still generated by our `lower_act` from a `check()`ed config, and `INV-16`
  is untouched: safetensors in, safetensors out, no pickle anywhere.
* **It is where it already was.** `act_policy` and `lower_act` have read the checkpoint's
  `config.json` since M4; V8 only stops requiring a directory to still be on disk at inference.

### 2. `meta/stats.json` — the one thing the export was missing

`lerobot-train` normalizes every policy feature from `LeRobotDataset.meta.stats`, and section
7.7's "three deliberate omissions" listed `meta/stats.json` first: *"`load_stats` returns `None`
when it is absent and no read path needs it… nothing in plan V trains through `lerobot`."* V8
does, so the file is written — **natively, in Rust**, in `crates/es-data/src/lerobot/v3.rs`, in
the same pass that writes the parquet, so there is one traversal of the values and not two.

What it contains, established from `lerobot/datasets/compute_stats.py` and `io_utils.py` at 0.6.1:

* `{feature: {stat: nested list}}`, the shape `load_stats` → `cast_stats_to_numpy` casts;
* `min`, `max`, `mean`, `std` (population, `ddof = 0`, matching `RunningQuantileStats`) and
  `count`, for every non-string feature including the five bookkeeping columns;
* a `[n]` feature is a flat list of `n`, a `shape: [1]` feature is a list of one, and an image
  feature is `[3, 1, 1]` per channel in `[0, 1]` — the three shapes
  `compute_stats._validate_stat_value` accepts.

**The `qNN` quantile keys are not written.** They are 5000-bin histogram estimates in LeRobot's own
code, only `NormalizationMode.QUANTILES` / `QUANTILE10` read them, and ACT is `MEAN_STD` on every
feature. Re-implementing an approximation of an approximation to fill a key nothing reads is the
same mistake section 7.7 refused when it declined to invent the file wholesale.

**Two export options come with it**, and both exist because `lerobot` classifies a policy feature
**by name alone** (`lerobot.utils.feature_utils.dataset_to_policy_features`: every key starting
`action` is an ACTION feature, every `observation.*` a STATE or VISUAL one):

* `--drop <a,b>` — `action_commanded` and `action_source` would otherwise arrive at the policy as
  two more action heads. Dropping them is a training decision, so the caller states it.
* `--state-dim <n>` — `es loop collect` records `observation.state` as env 0's whole `qpos`
  followed by its whole `qvel` (25 for this scene). A policy trained on all 25 **could never be
  run**: `es_eval`'s state capture reads `qpos` (`Capture::Qpos`, `Capture::Joints`) and there is
  no `qvel` arm at all. `--state-dim 6` keeps `qpos[..6]`, which is precisely what
  `Capture::Joints(6)` hands the Observation IR at inference. The refusal this prevents is a
  training run that converges on an observation the runtime cannot produce.

### 3. What V8 is fed, and what it is deliberately not

**The arm's six joint angles and the 96×96 overhead frame.** Not V7a's `sim_cube_pose`: LeRobot
gives a policy exactly one `observation.state` feature, so there is nowhere for a second state
port to land, and V8 is the *vision* question — the one V7a set aside on purpose.

`tests/fixtures/visible-learning/observation-v8.toml` is a second Observation IR on the same Task
IR (§7: same `task_hash`, different `observation_hash`), generated by the same declared generator
as the others. It differs from `observation.toml` in three ways and each is forced:

* **the state port carries raw radians** (`Unit::Angle`, no `Normalize`). ACT stores its
  normalization statistics in the checkpoint
  (`normalize_inputs.buffer_observation_state.{mean,std}`) and applies them as the first operation
  of its forward pass — our lowering carries them as nodes 9/10/11 — so a `Normalize` here would
  be the same affine map applied twice. The network is still not fed raw; its own first layer is
  the normalizer;
* **there is one state port**, for the reason above;
* **the port names are the checkpoint's feature names** with dots replaced by underscores
  (`observation_state`, `observation_images_rgb_overhead`). `XIR-010` matches the Observation IR's
  output names against `PolicyContract::inputs` verbatim, and those come from `config.json`; a dot
  is illegal in a `forward(**inputs)` keyword.

The image branch is `observation.toml`'s, byte for byte: `ImageInput` (U8 HWC) → `Dequantize`
(CHW F32, /255) → `Normalize{0..1}`. That is already exactly the tensor LeRobot's loader produces
from a PNG. No `Resize` and no `Crop` were added, so no intrinsics transform is owed (§7.2,
`INV-14`).

`evaluation-v8.toml` is `evaluation.toml` with one field moved — the `observation` it names
(`XIR-040`). Every suite, perturbation, metric and acceptance threshold is identical, including
`success_rate ≥ 0.5`.

### 4. Chunk scheduling belongs to the Deployment IR

`deployment.toml` does not move and `deployment_hash` does not move. `horizon = 16`,
`execute_chunk = 10`, `TemporalEnsemble { decay = 0.01 }`, 50 Hz control, 5 Hz inference, and
every safety limit, are V6's.

Two consequences for the training run:

* **`--policy.chunk_size=16`.** LeRobot's ACT default is 100; `XIR-022` requires the chunk the
  runtime buffers to be the chunk the policy predicts.
* **`--policy.n_action_steps=16`, not 10.** `lower_act`'s module returns
  `actions[0][:n_action_steps]`, and the runtime needs all 16 rows because *it* owns the execution
  cadence — `execute_chunk = 10` and the temporal ensemble are the Deployment IR's (§9.2), not the
  checkpoint's. `n_action_steps` does not enter the ACT loss, so this changes the artefact, not
  the optimization. `es policy import-lerobot` **refuses** a checkpoint that disagrees, naming the
  two flags, rather than reshaping the chunk.

`act_policy` leaves `replanning_hz`, `execution_mode` and the deadlines at zero because a
`config.json` has no control rate; the import fills them from the Deployment IR, which is what
`act_policy`'s own comment already said would happen.

### 5. Training knobs

LeRobot's ACT defaults, which is the point of the packet — `vision_backbone = resnet18` with
`ResNet18_Weights.IMAGENET1K_V1`, `use_vae = true`, `latent_dim = 32`, `dim_model = 512`,
`n_heads = 8`, `dim_feedforward = 3200`, 4 encoder / 1 decoder layers, `kl_weight = 10.0`,
`optimizer_lr = 1e-5`, `optimizer_lr_backbone = 1e-5`, `dropout = 0.1`, all `MEAN_STD`. Batch 8
and seed 0 match V2b/V7a. Steps 100,000 with a checkpoint every 10,000 — measured throughput put
that well inside the packet's 3 h budget; had it not, the run would have stopped at 50,000 and
said so.

The demonstrations are V1c's 50 episodes, `action` = the *executed* `SafeAction` (section 7.10),
so what the policy imitates is what the plane let through.

## spec

* **§8.1.** The network is opaque, the interface is typed. The bundle's `LearningGraph` carries a
  `PolicyHandle` and no nodes, which is what that sentence looks like when the network was not
  authored here.
* **§8.4 / `XIR-010`, `XIR-011`, `XIR-020`–`XIR-024`.** The contract is projected from
  `config.json` by `act_policy` and completed from the Deployment IR by the import, and every
  cross-IR rule is checked by `PolicyBundle::build`/`open` — not by a new code path.
* **§8.7.** Pre/post-processing stays in the IR: the Observation IR normalizes the image, and the
  chunker, the ensemble and the unnormalizer stay where they were. Nothing moved into
  `PolicyRuntime`.
* **§8.9.** The M1 gate generalizes from the pinned upstream checkpoint to *any* ACT checkpoint
  and from a synthetic ramp to a recorded frame.
* **§5.3 / §25.1.** Weights cross a trust boundary; the declared hash is checked before the
  architecture is read out of them, and the source checkpoint's own hash is recorded in
  `BaseModelRef`.
* **§19.1.** `meta/stats.json` is part of the v3.0 format, established from the installed package
  and checked against it.
* **`INV-16`.** safetensors only. **`INV-17`.** No new trait. **`INV-11`/`INV-12`/`INV-13`.**
  `es-safety` is not touched.

`observation-v8.toml` has no Learning IR fixture beside it, on purpose: the V8 Learning IR is
*derived* by `es policy import-lerobot` from the checkpoint and the Deployment IR, so there is
nothing to type in and `es ir check` has no fifth document to be given. Its cross-IR pass runs in
`PolicyBundle::build`, and the import command failing is the refusal.

`ES_LEROBOT_PYTHON=<venv>/bin/python cargo test -p es-data --test lerobot_v3` is where
`meta/stats.json` is judged: `lerobot_stats_ref.py` opens the export with `LeRobotDataset`,
recomputes the statistics with LeRobot's own `compute_episode_stats` + `aggregate_stats` on the
same parquet, and reports the largest disagreement; the Rust side holds the threshold (`< 1e-5`)
and requires every feature present with all five keys at the same shape.

## acceptance

1. `meta/stats.json` is loaded by `LeRobotDataset` with every feature present, and its numbers
   agree with LeRobot's own `compute_episode_stats` + `aggregate_stats` to `< 1e-5`. **RAN**.
2. `lerobot-train` completes on the export with no change to the trainer.
3. `es policy import-lerobot` produces a bundle that `PolicyBundle::open` re-validates, and
   `es eval run --policy` loads with **no change to the eval path** — the assertion
   `policy_pack_output_is_accepted_by_eval_run` was written to describe and section 2.5 of the
   design note recorded as out of reach.
4. The equivalence gate passes on a recorded frame at spec §8.9 tier 4 (≤ 1e-5), with the measured
   `max_abs` / `max_rel` recorded in section 7.16.
5. The nominal sweep on seeds 101–116 and the full suite are measured on the final checkpoint and
   on at least two earlier ones, and the numbers go into section 7.16 **as measured**. The demo's
   own acceptance (`success_rate ≥ 0.5`) is the verdict, and the stop rule in "the question this
   packet exists to answer" is applied as written — including when it says to stop.
6. `cargo fmt --check`, `clippy -D warnings`, `cargo xtask ci`.

## forbidden

* **`es-safety`.** Not one line, not one number in `deployment.toml`. `INV-11`, `INV-12`,
  `INV-13` all stand, and the external policy runs behind the same envelope the expert and every
  Plan V policy ran behind.
* **`es-ir`.** No new node, no new field, no new `ArchKind`. If the IR could not describe an
  external policy the packet was to stop and report; §8.1 describes it exactly.
* **`evaluation.toml` thresholds.** `success_rate ≥ 0.5` is the demo's acceptance and is not
  lowered to make a table pass — the same rule as editing a golden.
* **`lower_to_torch`, `python/es/train_act.py`, `es dataset bake`.** V8 does not go through the
  IR lowering or the bake at all; LeRobot's trainer reads the LeRobot dataset directly.
* **The v2.1 writer and `es loop collect`.** No column was added and no demonstration was
  re-collected; `dataset_schema_hash` does not move.

## as built

Measured on the oracle server (RTX 4090, `~/venvs/es-lerobot-cuda` for training and the
reference, `~/venvs/es` for evaluation), 2026-09-15. Full write-up: design note **section 7.16**.

**The verdict, and the stop rule applied.** `success_rate = 0.0625` (1/16) nominal at 100,000
steps, 0/16 at 20,000 and 50,000; every perturbation suite scores the same 1/16. The demo asks
for `0.5` and **no threshold was lowered**. The packet's hypothesis 1 — "our ACT-shaped graph is
why the demo does not work" — **is refused**: a real LeRobot ACT with a pretrained backbone, a
CVAE and a DETR decoder, trained five times longer, does no better. Per the stop rule, the next
packet opens the scene, the contact model or the expert's trajectories, not the optimizer and not
`es-ir`.

| checkpoint | `success_rate` | mean episode length | `envelope_violation_rate` |
|---|---|---|---|
| 20,000 | 0.0000 (0/16) | 900.0 | 0.180 |
| 50,000 | 0.0000 (0/16) | 900.0 | 0.370 |
| 100,000 | 0.0625 (1/16) | 865.5 | 0.356 |
| 100,000, full suite (6 × 16) | 0.0625 in every suite | 864.6 – 873.0 | 0.253 – 0.352 |

Acceptance, item by item:

1. **Met.** `RAN lerobot_v3_stats`, worst disagreement `5.5e-08` against LeRobot's own
   `compute_episode_stats` + `aggregate_stats`, nothing missing, nothing extra.
2. **Met.** `lerobot-train` completed 100,000 steps on the export with no change to the trainer
   (33 m 50 s; loss 4.270 → 0.026).
3. **Met.** The bundle re-opens and `es eval run --policy` loads it with no change to the eval
   path. `deployment_hash 3b2ad568…6db1` and `task_hash 6cf826c1…6b7b` did not move.
4. **Met, bitwise.** `max_abs 0e0`, `max_rel 0e0`, chunk `[16, 6]`, on a recorded frame of this
   project's own dataset, at both the 20,000- and the 100,000-step checkpoint.
5. **Met.** Tables above and in section 7.16; the 100,000-step nominal run was repeated and
   `report.json` came back byte-identical.
6. **Met.**

**Three things the packet did not know, all in section 7.16 in full.**

1. **A raw `Unit::Angle` policy input is refused by `TYPE-011`,** which the cross-IR pass checks
   against `PolicyContract::inputs` and not only against the graph boundary. The fix is not a
   second affine map — that would have to be applied to the exported dataset too, i.e. a second
   implementation of `Op::Normalize` — but to say what is true: `Normalize{Range{0..1}}`, the
   identity, declared in the node that owns the decision. The import then takes each contract
   input's unit from the Observation IR, because `config.json` records none.
2. **A checkpoint `lerobot-train` 0.6.1 writes keeps its normalization statistics in a separate
   processor state file,** not in `model.safetensors`; the pinned upstream checkpoint the M4 gate
   used is the older layout. Both now load. `docs/api-notes/lerobot-act.md` section 9.
3. **An empty Learning IR graph is refused by `LRN-021`,** and the hint names the right answer,
   which spec §8.3 also names outright: reference the policy whole with `LearningNode::PolicyBundle`.

**Open question (V8-1)** is stated at the end of section 7.16 and belongs in that note's section
12 list: what the external ACT's failure is allowed to conclude, and that the next packet should
be a diagnosis of the scene (replay the expert's own recorded actions through `es eval run`)
rather than a bigger training run.
