## 발견

캠페인의 산출물은 정책이 아니라 정책이 드러낸 런타임 결함 목록이다. 아래 모두가 학습을 먼저 탓한 뒤
측정으로 발견됐고, 그 패턴을 끊으려는 것이 §28.9의 "하네스 선행" 규칙(M5-R1)이다. 표시가 없으면
닫힌 것이다.

### 블로커

- **B-1** `es-eval` — 한 스위트의 숫자가 문서에 다른 스위트가 있는지에 따라 달라진다.
  `evaluation-v8.toml`을 nominal 하나로 자른 문서는 어떤 체크포인트에서 0.625를, 같은 체크포인트의
  6스위트 스윕은 같은 nominal 시드에서 0.5625를 내며 성공하는 셀이 다르다; `--jobs`는 배제됐다(4·6·8에서
  바이트 동일). §10.4는 "각 스위트는 자기 `stream`에서 뽑으므로 행을 추가해도 다른 스위트의 숫자는
  움직이지 않는다"고 하고, V11 이후의 모든 잘린 문서 표가 그것에 기댔다. 미해결 질문 28. 틀린
  숫자는 아니다 — 각 실행은 자기 문서 아래서 재현된다 — 그러나 선언된 불변식이 성립하지 않으며, 이
  리뷰가 모든 수치를 측정된 문서와 나란히 적는 이유다.

### M5 중에 닫힌 것(각각 사양의 규칙 후보)

- **F-1 엔벌로프 의미론**(V6, §9.3). 플레인의 동적 단계가 한 경로에서는 서보의 추종 오차를, 다른
  경로에서는 플레인 자신의 명령을 제한했다. 규칙: 속도/가속도/rate 한계는 플레인의 명령 체인을
  제한한다; `envelope_reference.rs`가 고정한다.
- **F-2 제어 주기**(V11, §12.1). 기록된 한 행이 물리 한 스텝이었다: 시연이 50 Hz 문서에 대해 200 Hz로
  돌았다. 규칙: 추론 주기는 `rate.control`과 물리 timestep에서 유도하고(`BatchDomains::single_env_at`),
  나누어떨어지지 않는 쌍은 이름으로 거부한다.
- **F-3 관측–행동 짝짓기**(V12, §13.2). 행이 스텝 전 상태로 계산된 행동 옆에 스텝 후 상태를 실었다.
  규칙: 기록은 관측과 그 관측으로 계산된 행동을 짝짓고, 프레임과 궤적은 같은 순간에 찍는다.
- **F-4 학습된 함수 ≠ 배포된 함수**(V13, §8.3). 단일 샘플 lowering과 BatchNorm이 N=1 통계로 학습하고
  running 통계로 배포했다. 규칙: lowering은 train과 eval 모드에서 같은 함수이며 비트 단위로
  단언한다; 처음부터 학습하는 백본은 GroupNorm으로 lowering한다.
- **F-5 선언된 재계획 주기를 아무도 읽지 않았다**(V17, §9.2). 두 루프가 매 제어 틱 추론했고 모든
  청크의 1행 이후가 죽어 있었다. 규칙: 두 경로 모두 `es_env::replan_interval`; 나누어떨어지지 않으면
  거부.
- **F-6 플레인의 시계**(V17, §9.4). 두 루프가 `SafetyPlane`에 시뮬 틱을 넘겼는데 그 주기는 제어
  주기다. 규칙: 플레인의 `now`는 제어 틱이며 API에 명시한다.
- **F-7 재계획 주기 대비 데드라인**(V17, §9.4). 5 Hz 재계획은 40 ms `inference_budget`을 만족할 수
  없다. 규칙 후보: `DEP_0xx` — 재계획 한 주기보다 작은 `inference_budget`은 검증 경고다. 런타임은
  설계상 한 주기를 기다리기 때문이다.
- **F-8 측정으로서의 엔벌로프**(V18, §9.3). `acceleration_max = 20`에서 플레인이 정책 틱의 99.8 %를
  깎고 매 실행의 1/10에서 폴백을 래치했다; V13부터 V17까지의 모든 숫자가 플레인을 측정했다. 규칙:
  `envelope_violation_rate`와 래치 비율을 `success_rate` 옆에 보고하고, 엔벌로프는 조심이 아니라
  액추에이터에서 유도한다(픽스처 주석).
- **F-9 임포트가 측정값을 지어냈다**(V19, §8.4). `import-lerobot`이 추론 예산을 `expected_latency_ms`에
  써 넣었고, 예산이 재계획 주기를 넘자 `LRN-052`가 거부했다. 규칙: 임포트는 상한 `min(budget, period)`을
  선언한다; 측정값은 `es bench`에서 온다.
- **F-10 MJCF 에미터 누락**(B1/B1b, §17). `ls_iterations`, `eulerdamp`, geom `priority`, `inheritrange`,
  중복 자동 geom 이름. 규칙: 에미터 왕복 패리티는 가정이 아니라 오라클이다.

### 고쳐야 할 것

- **S-1** `es-eval/src/runner.rs` — 추론 지연 모델이 없다; `es loop collect`는 모든 청크를
  `expected_latency_ms`만큼 `AsyncInference`로 늦추는데 평가기는 tick 0에 실행한다. 한 시드의 궤적이
  tick 1에서 갈라진다(미해결 질문 24, 사다리 5). 지연 0으로 평가된 정책은 존재하지 않는 로봇에서
  평가된 것이다.
- **S-2** `execution_hash`가 실행 시점의 측정값을 읽는다(`runtime`, `hardware_capability`): 비트 동일한
  두 평가가, 하나는 GPU 경합 아래서, 다른 이름을 가진다(미해결 질문 26).
- **S-3** 데이터셋 ↔ 술어 출처. `gripper > 0.6`으로 수집된 시연과 `> 0.85`로 수집된 시연이 서버에
  나란히 있고 트리의 어떤 것도 하나를 폐기로 표시하지 않는다; V19의 패킷이 잘못된 쪽을 지목해 구조적으로
  0/16을 측정했다(미해결 질문 27). 수집 당시의 `task_hash`는 이미 export에 있다; `dataset bake/export`와
  `import-lerobot`은 현재 문서와의 불일치를 거부하거나 표시해야 한다.
- **S-4** `es-telemetry` transport 테스트가 부하 의존(L15); `ECONNRESET`을 허용하거나 직렬화한다.
- **S-5** `es` CLI 오라클(`expert_passes_the_evaluation_harness`, 케이던스 패리티, 재생)이 오라클
  서버에서만 돈다; GitHub 오라클 계층이 `ES_PYTHON`을 두고 돌려야 한다.
- **S-6** torch 런타임의 `--jobs N`은 `--jobs 1`과 바이트 동일하지 않다(스레드 수 의존 리덕션, 미해결
  질문 16); 리포트가 실행 당시의 스레드 상한을 실어야 한다.
- **S-7** `es-safety`가 강제하지 않는 선언된 안전 한계(`ee_velocity_max`, 접촉, 거리; L6, 사다리 12)는
  여전히 문서상의 한계다.
- **S-8** `Cargo.lock`이 gitignore되어 `compiler_hash`가 빌드를 재현하지 않는다(L11, 사다리 7).
- **S-9** Learning IR의 16행 horizon과 IR 그래프 정책의 lowering된 `[10, 6]` 청크가 서로, 그리고 그것을
  설명하는 문서와 어긋난다; 10틱 재계획 아래서 16행 청크는 청크 둘을 살려 두고 10행은 그렇지 않으며, 두
  정책은 그 차이를 사이에 두고 비교됐다(7.27절).
- **S-10** 쇼케이스가 프레임당 약 80 ms에 렌더되고 PT 톤맵에 오라클이 없다(V9).

## 판정

**M5 게이트: 다시 세운 기준으로 통과.** 이 프로젝트가 설계하지도 학습하지도 않은 ACT가 Observation IR,
Deployment IR, 안전 플레인, 평가를 마지막 비트까지 같은 함수로 통과하고, 커밋된 문서에서 학습·홀드아웃
시드 모두 시연의 수용 기준을 넘기며, 플레인은 틱의 1/5을 깎을 뿐 한 번도 폴백하지 않는다. 그것이 실제
산출물 위에서 이행된 §8.1의 약속이고, 오너가 말한 이 프로젝트의 존재 이유다. 마일스톤의 비용 — 먼저
탓을 받은 정책 뒤에서 하나씩 찾아낸 런타임 결함 열 개 — 이 사양에 중요한 발견이다: F-1..F-10 어느
것도 학습 문제가 아니었고, 오라클 선행 규칙(§1.4)은 형식으로는 지켜졌으나(모든 패킷에 실행 가능한
오라클이 있었다) V6까지 실질에서는 깨져 있었다(오라클이 하네스가 아니라 정책을 시험했다). B-1이 유일한
열린 정확성 항목이며 전체 문서로 측정된 시연의 기록에는 닿지 않는다. 안전 불변식은 내내 유지됐다:
플레인은 두 번 넓혀졌고(INV-12: V17의 데드라인, V18의 `acceleration_max`) 한 번도 우회되지 않았으며,
`validate`의 시그니처는 그대로(INV-13), pickle은 들어오지 않았고(INV-16), trait은 추가되지 않았다(INV-17).

## 후속 패킷

- **R1 스위트 독립성.** `cargo test -p es-eval`: 한 스위트 문서와 6스위트 문서의 nominal 스위트가 같은
  시드에서 셀별 결과가 바이트 동일; 스트림이 문서에 의존하도록 의도된 것이면 §10.4를 대신 바꾼다(B-1,
  미해결 질문 28).
- **R2 평가의 지연.** `cargo test -p es-eval`: `expected_latency_ms`가 선언되면 tick 0은 chunk underrun이고
  한 시드의 수집/평가 궤적이 마지막 틱까지 일치한다(S-1, 사다리 5).
- **R3 결정적 출처.** `execution_hash` 슬롯이 선언값을 읽는다; 같은 평가를 단독과 부하 아래서 돌려 해시
  하나를 단언하는 오라클(S-2, 미해결 질문 26).
- **R4 데이터셋 출처.** `es dataset export`와 `es policy import-lerobot`이 기록된 `task_hash`가 현재
  문서와 다른 데이터셋을 `--allow-retired-task`로 지목하지 않는 한 거부한다(S-3).
- **R5 하네스 선행 규칙(M5-R1).** 새 수직 슬라이스 패킷의 acceptance가 학습 스텝 전에
  전문가-하네스와 수집=평가 오라클을 이름으로 든다(사다리 2).
- **R6 CI의 CLI 오라클.** GitHub 오라클 계층이 `ES_PYTHON`으로 `es` 하네스 오라클을 돌린다(S-5).
- **R7 `Cargo.lock` 커밋**과 `cargo xtask ci`의 `--locked` 빌드(S-8, 사다리 7).
- **R8 청크 horizon 일관성.** Learning IR horizon, lowering된 청크, Deployment IR 버퍼에 숫자 하나,
  `XIR`로 검사; IR 그래프 대 외부 비교를 다시 한다면 같은 청크 길이로(S-9).
- **R9 살아 있는 안전 한계**(S-7, 사다리 12)와 **R10 telemetry flake**(S-4, 사다리 8)는 §28.9에 이미
  있는 대로.
