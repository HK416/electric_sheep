## Findings

### Blocker

- [BLOCK] `crates/es-eval/src/runner.rs:126` — one `CpuPlan` is compiled for the whole run and its `TemporalWindow` rings (`es-compile/src/plan.rs:157`, mutated at `exec.rs:181`) are never cleared; `CpuPlan` has no reset at all. Episode N's first frames see episode N−1's tail and cell 2's see cell 1's, so the §10.1 table depends on suite order — the one thing §10.4 exists to prevent, and the exact hazard `es-env/src/domains.rs:161` names for the batch case. Fix: `CpuPlan::clear_rings()`, called after `env.reset` in `run_episode`.
- [BLOCK] `crates/es-data/src/lerobot_config.rs:426` — the converter inserts an unwired `Augment { training_only: true }` node. `topo_order` (`plan.rs:199`) visits it anyway and `plan.rs:526` has no `Augment` arm, so **every** LeRobot config carrying `crop_shape` (the checked-in `diffusion_config.json` fixture included) yields an `ObservationIr` that cannot compile; `es-eval/src/runner.rs:237` also refuses it, ignoring `training_only`. W1 and W6 do not compose and no test crosses them. Fix: keep the node out of the deployable graph (or prune unreachable nodes before planning) and let `refuse_augmentation` skip `training_only`.

### Should-fix

- [SHOULD] `crates/es-env/src/domains.rs:271,275` — `with_seq(self.control_tick)` stamps a fresh chunk every control tick, so `plane.rs:298` refreshes `last_chunk_tick` unconditionally and `ViolationKind::InferenceDeadline` (`plane.rs:226`) can never fire through `DomainRunner`; a dead policy shows only as `ChunkUnderrun`. `es-runtime-embedded/src/runtime.rs:170` gets it right (one increment per policy invocation) — fix: carry the producing chunk's arrival tick to the plane.
- [SHOULD] `crates/es-env/src/inference.rs:65` — the submission queue is unbounded; when `inference.batch` is under the arrival rate it grows without limit (its own test at `:224` demonstrates the backlog). At the 4,096-env gate configuration that is the OOM §20.3 says must not happen — fix: cap the queue and count the drop as an underrun.
- [SHOULD] `crates/es-compile/src/budget.rs:420` vs `crates/es-env/src/domains.rs:495` — two in-tree models of the same quantity disagree 8×: the budget uses §20.2's `N_sim × H × NJ × 4B × 2`, the implementation stores `CHUNK_SLOTS = 8` slots of `f64`. Gate 13's ±10% is unreachable until one moves — fix: size the budget from `CHUNK_SLOTS` and `f64`, noting the §20.2 deviation.
- [SHOULD] `crates/es-eval/src/runner.rs:362` — `safe.q[i.min(NJ - 1)]` drives every actuator past `NJ` with a copy of joint `NJ−1`, and `joint_state` (`:439`) pads missing joints with `0.0`; a `nu != NJ` model silently gets wrong commands — fix: `EvalError` on the mismatch.
- [SHOULD] `crates/es-policy/src/reference.rs:26` — the tier-4 "reference" imports `diffusion_schedule` from the lowering it checks, and `ddpm`/`flow` (`:194,:220`) are line-for-line mirrors of `DDPM_PY`/`FLOW_PY`. It proves Rust↔PyTorch agreement, not that the coefficients are right (§1.4). Hand-checked and correct against Ho 2020 / Song 2021: DDPM `c1 = 1/√α_t`, `c3 = −c1·β_t/√(1−ᾱ_t)`; DDIM η=0 `c1 = √(ᾱ_{t−1}/ᾱ_t)` — but see the next item.
- [SHOULD] `crates/es-policy/src/lower/torch.rs:57-71,86` — the linear β schedule spans `BETA_START..BETA_END` across `n_steps` **inference** steps, whereas diffusers/LeRobot build it over `num_train_timesteps` (1000) and subsample; and `σ_t = √β_t` is diffusers' `fixed_large` while its (and LeRobot's) default is `fixed_small` `√β̃_t`. A real Diffusion Policy checkpoint will not reproduce — fix: schedule over `num_train_timesteps`, pin the variance type.
- [SHOULD] `crates/es-telemetry/src/transport.rs:173` — the client cap is applied inside `serve_client` (`:255`), after `thread::spawn` has already run, and `set_read_timeout` is per-read, so a peer dribbling a byte every 4 s holds a thread indefinitely — fix: check `clients.len()` in the accept loop and use an absolute handshake deadline.
- [SHOULD] `crates/es-eval/src/runner.rs:112` — one `&mut dyn PolicyRuntime` serves every cell and the trait (`es-policy/src/runtime.rs:121`) has no seed or reset, so a stateful sampler carries cell N−1's state into cell N. §10.4 pins the perturbation stream; nothing pins the policy's.

### Nit

- [NIT] `crates/es-compile/src/budget.rs:267` — `u64::from(m.nq + m.nv + m.nu + m.nsensordata)` sums in `u32` before widening; one `u64::from` per term is the consistent handling.
- [NIT] `crates/es-env/src/chunk_buffer.rs:156` — `let s = self.slots[i]` copies a whole `[[f64; NJ]; H]` per slot per tick (≈44 KiB/tick at NJ=7, H=100). `next_action` is genuinely allocation-free, but not copy-free — `&self.slots[i]` borrows cleanly here.
- [NIT] `crates/es-compile/src/budget.rs:396-402` — `inference_activations` sums *every* node output rather than a liveness peak as §20.2 asks; the formula string should say "worst case".
- [NIT] `crates/es-policy/src/lower/torch.rs:112` — `_sinusoidal` returns `2*(dim/2)` values, so an odd conditioning width makes `_Denoiser.l0`'s `x_dim + 2*cond` inputs mismatch at run time; the Rust mirror (`reference.rs:171`) repeats it, so the oracle is blind — fix: reject an odd width in `lower_to_torch`.
- [NIT] `crates/es-eval/tests/evaluation.rs:727` — `Ok(_) | Err(EvalError::Plan(_)) => {}` passes on either outcome, so the allow-list path is never actually exercised.
- [NIT] `crates/es-data/src/lerobot_config.rs:534,888` — `vec![0.0; dim as usize]` is sized from an unbounded `config.json` `shape` field.

## Verdict

**M2 gate: not passed — two blockers.** M1's headline weakness is genuinely fixed: the observation goldens now come from torchvision and the torch oracles *run*, with DDPM, DDIM and FlowMatching all inside 1.1e-7. The Evaluation IR determinism machinery is the strongest part — byte-identical reports, seeds keyed exactly as §10.4 specifies, `Unavailable` instead of a fabricated zero. What fails is composition: the eval runner leaks observation history across cells, so the fairness the rest of the crate works for does not hold, and W6's converter emits a graph W1 cannot plan. Both are small diffs with obvious oracles.
