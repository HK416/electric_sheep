## 판정

**M2 게이트: 통과하지 못함 — Blocker 2건.** M1의 headline 취약점은 실제로 고쳐졌다: observation golden은 이제 torchvision에서 나오고 torch 오라클이 *실행*되며, DDPM, DDIM, FlowMatching 모두 1.1e-7 이내다. Evaluation IR의 determinism 메커니즘이 가장 강력한 부분이다 — byte-identical 리포트, §10.4가 명시한 그대로 keyed된 seed, 조작된 0 대신 `Unavailable`. 실패하는 것은 composition이다: eval runner가 observation history를 cell 간에 leak시켜서, 크레이트의 나머지 부분이 애써 지키는 fairness가 성립하지 않게 되고, W6의 변환기는 W1이 plan할 수 없는 그래프를 만들어낸다. 둘 다 오라클이 명확한 작은 diff다.

## 후속 패킷

- **P-M2-R1 — plan의 temporal ring을 episode마다 reset.** 오라클: `TemporalWindow` fixture를 사용해 suite 순서를 뒤집어도 cell 결과가 바뀌지 않음을 assert하는 `cargo test -p es-eval`.
- **P-M2-R2 — 변환된 LeRobot config가 plan되고 evaluate된다.** 오라클: `cargo test -p es-data lerobot_config`가 `crop_shape`를 가진 `diffusion_config.json`으로부터의 `Converted::observation`에 대해 `CpuPlan::compile`을 실행하고 diagnostic이 없음을 assert.
- **P-M2-R3 — inference deadline이 domain runner를 거쳐도 유지된다.** 오라클: 생산을 멈추는 정책을 사용해 `ViolationKind::InferenceDeadline`이 budget 이내에 발동함을 assert하는 `cargo test -p es-env`.
- **P-M2-R4 — inference queue에 상한을 둔다.** 오라클: `batch = 1`, env 4,096개, tick 10,000회로 `pending()`이 cap 이하로 유지됨을 assert하는 `cargo test -p es-env inference`.
- **P-M2-R5 — chunk-buffer 크기 산정 모델을 하나로 통일.** 오라클: §12.4 게이트 구성에 대해 `MemoryBudget::estimate`의 `chunk_buffers`가 `DomainSizing::chunk_buffer_bytes`와 같음을 assert하는 `cargo test -p es-compile budget`.
- **P-M2-R6 — DDPM schedule을 diffusers와 대조.** 오라클: `diffusion_schedule`을 `diffusers.DDPMScheduler(num_train_timesteps, "linear")`의 `alphas_cumprod`와 `fixed_small` variance에 `Tolerance::TIER4_FP32`로 비교하는 torch-tier 테스트.
- **P-M2-R7 — `nu != NJ`는 조용한 broadcast가 아니라 error다.** 오라클: actuator 3개인 모델과 `NJ = 2`로 `EvalError`를 assert하는 `cargo test -p es-eval`.
- **P-M2-R8 — accept-loop 연결 수 상한.** 오라클: `max_clients + 8`개의 silent socket을 열어 서버의 스레드 수가 bounded로 유지됨을 assert하는 `cargo test -p es-telemetry transport`.
