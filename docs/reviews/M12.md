## What plan Y set out to do, and what it did

The owner asked on 2026-09-28 for an editor that someone with no background can use the way they
use Unity or Unreal, to carry out vision-based robot learning, watch it, and read its result. The
owner chose: templates **and** from-scratch projects; three ways to teach (action blocks,
teleoperation, reward); this PC first; egui kept with docking; a step bar over a dock (option B);
templates opening with ① ② done; one button for data + training; checkpoint previews; failure-led
advice. S1 (this plan) is the shell and the template path; S2–S6 are directions in the design note.

- **Backend (Y1, Y2, Y5, Y5b).** `es --check-deps --json`. `episodes.json`, one row per evaluated
  episode, beside an unchanged `report.json`. `es policy init`, the collect bundle a fresh checkout
  could not make before (`untrained.esb` had come from test helpers and server artifacts), and
  with no `--learning` the opaque external-policy shape the camera-only gate needs. Two cube
  templates over committed documents, never copied (the scene path is hash input).
- **Moves (Y3, Y4).** The replay rasterizer to `es_render::raster` (now calling `shade_lambert`
  instead of a copy); reading a finished run to `es_eval::run_dir`, with `Rgb8Image`. Strings a
  person reads stayed in the editor.
- **Model (Y6–Y9, Y15).** Project folders and run recipes; the step bar's state from the ledger
  and the live stages; the traffic light; the results model (verdict, comparison, causes over
  every bucket `es-eval` writes, situations over the twelve perturbation kinds, tiles); the start
  screen's PC check and template availability; the run controller (`Watch`: start guard, kill as
  *stopped by you*, eval code 1 as *did not pass*, resume rewrites `telemetry.txt`); the scene
  preview at the model's own pose.
- **Screens (Y10–Y13, Y15).** The dock (`egui_dock` 0.17.0, the last release on egui 0.32 and
  MSRV 1.85), the step bar, the start screen, ① scene, ② teach, ③/④ progress with the light, ⑤
  results. The five old tabs survive as Advanced panes. Screenshots of each, both languages,
  under `target/plan-y/y10` … `y15` (gitignored), taken from inside the app because the session
  was locked; the owner's `%APPDATA%` store was never written.

## Findings

### Blocker

None.

### Should-fix

- **S-1 `es-editor` is 285 lines under the cap.** S1 alone took it from 6,128 to 9,715. S2 (checkpoint
  previews, failure-led re-training) cannot land without a split, which touches §4.2's layer
  table (H-2). The split packet comes before S2.
- **S-2 "Evaluate what it has learned so far" is unproven and likely refused.** After a kill in
  the middle of training `training.lock` may be missing, and `es loop cycle --from eval` may refuse
  (Y12). The button stays; Y-V item 3 decides whether it changes.
- **S-3 Stop may leave the Python trainer running on Windows.** `LaunchModel::kill` ends `es.exe`,
  not its process tree (Y12). Y-V item 3; a job-object packet if confirmed.
- **S-4 The traffic light's thresholds are first guesses.** Marked `ponytail:` in `health.rs`;
  Y-V item 4 calibrates them on a recorded successful run.
- **S-5 Neither card has a measured number on its own recipe.** The camera-only route has never
  passed this task (0–1/16 on older harnesses); the hint card's `cycle.toml` recipe was never run
  as is (U0, the same documents at other settings, 0.25). Both notices say what is true and claim
  no success. Y-V item 1.

### Nit

- **N-1** `tests/golden/editor/replay-tick0-320x180.json` still names
  `es_editor::model::replay_view::Raster::draw` as its oracle (Y3); corrected at its next
  intentional regeneration, never by hand.
- **N-2** The light's precedence puts *starting* before *slow*; the design note's table listed it
  after. They differ only for inconsistent input; the note now follows the code.
- **N-3** `Next ▶` is usually disabled, because a project opens at its first step that is not done.
  The design note should say what Next is for.
- **N-4** Export copies the bundle on the UI thread (`ponytail:`).
- **N-5** The default project folder is `USERPROFILE`/`HOME` + `Documents`; a Documents folder
  redirected elsewhere is not followed (`ponytail:`; the known-folder API needs `unsafe`, which the
  crate forbids).
- **N-6** `✓`/`✗` have no glyph in egui's fonts or Malgun Gothic; the screens use `✔`/`✖`.
- **N-7** `es-editor` uses `es-safety` only in a test now, and its `Cargo.toml` comment about the Run
  tab is stale (Y4).
- **N-8** `--telemetry-image-every 50` is added to every run the editor starts, unmeasured (Y-V 5).

### Human decision

- **H-1 Should `render` be a default feature of `es`?** A default build has no renderer, so both
  cube cards stay disabled even with every Python tool installed; the start screen now says how to
  rebuild. Making it default changes what every `cargo build -p es` compiles.
- **H-2 How to split `es-editor` before S2.** A crate for the headless view-models under the egui
  shell needs a layer 13 (same-layer dependencies are forbidden), i.e. a change to §4.2 and
  Appendix C.8; or another cut the owner prefers.
- **H-3 Where Y-V runs.** A local venv (multi-GB download: torch with CUDA, mujoco, lerobot) or the
  server, which is currently off-limits.
- **H-4 The collect bundle's declared latency.** Y5b gave the camera-only collect bundle one control
  period (20 ms), so both cards' demonstrator runs as it was measured; `import-lerobot` declares 200 ms
  for trained ACT policies. Related to M11's open "declared source latency".
- **H-5 Language and text size moved to the View menu** (Y10), reversing M7/E6's "always visible";
  the start screen carries a language switch so a first-time reader finds it. Confirm or restore.

## Addendum (2026-09-29, the first real runs)

With the owner's go, a local environment was installed on this PC (`.venv`: torch 2.11.0+cu128,
lerobot 0.6.1, mujoco 3.13.0; `es` with `--features render`) — the remote server stayed
untouched. Both cube cards ran end to end through the editor's own model and argv; the numbers are
in `docs/packets/M12/YV-verification.md` ("Results, 2026-09-29").

- **Y-V items 1 and 2 pass.** Both cards complete collect → gate → train → eval → showcase;
  `episodes.json` equals `report.json` exactly. Both cards *did not pass* at the short preset
  (hint 6/96, nominal 0/16; camera-only 0/96) — reported as measured, as the notices promise.
- **Fixed on the way (merged):** P-M12-R1 (the v3 export's single 2.9 GB row group; one row group
  per episode), P-M12-R2 (the LeRobot route published no progress; the light read *not
  responding*), P-M12-R3 (the editor never noticed a closed telemetry connection). S-5 is
  answered for the short preset; Y5b's gate fix holds on a real run.
- **New findings.**
  - **S-6** One evaluation worker's MuJoCo process died once (`os error 232`) while agents were
    compiling on the same PC; alone and on a quiet PC it did not recur. Unproven; the backend's own
    error line is discarded (`proc.rs`), which is the first thing to fix (packet to come).
  - **S-7** The hint card's plane changed 99.6 % of the IR policy's steps (camera-only: 12 %). It
    is M11's open "envelope for a learning policy" (a human decision), now visible to a beginner
    as a template that clamps nearly every step.
  - **N-9** `torchcodec` cannot load on Windows without FFmpeg's DLLs; LeRobot falls back to
    `pyav` and nothing here decodes video. Harmless today; a `video` export would need FFmpeg.
  - **N-10** The page file is fixed at 4 GB, so the commit limit is RAM + 4 GB (67.9 GB); a quiet
    6-worker evaluation peaked at 41.7 GB.
