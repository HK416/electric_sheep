## Findings

### Blocker

- **B-1** `es-safety/src/counters.rs:59-64` — `ViolationWindow::fraction()` divides by `filled`,
  the steps observed so far, not by the configured `window`. So the **first** dirty step makes
  `envelope_violation_rate()` exactly `1.0`, and `plane.rs:268-273` then raises `ViolationRate` on
  the next step for any `max_frac < 1.0`. That trip runs the fallback (`plane.rs:276-284`), the
  fallback step is itself dirty, the rate stays `1.0`, and the plane is latched into fallback for
  the rest of the run — with `FallbackPolicy::EmergencyStop` it latches the e-stop
  (`plane.rs:282`). §10.3's own example acceptance is `envelope_violation_rate: "<= 0.01"`, so
  a spec-shaped configuration is exactly the one that bricks. A HIL run is the fast path into it
  (its first tick has no chunk yet → `ChunkUnderrun`), but nothing about it is HIL-specific: one
  transient clamp at step 3 of any deployment does the same. `es-safety/tests/properties.rs:242` is
  the watchdog's only appearance and it asserts a **config** rejection for an over-cap window — the
  behaviour has never been tested. W1d found this, could not fix it (`es-safety` is `forbidden` in
  its packet), and did the sanctioned thing: widened to `max_frac: 1.0` (`hil_gate.rs:130-133`) with
  the interaction written out in the fixture. Correct conduct on a broken watchdog, but it leaves
  §9.4's rate watchdog armed-and-inert in the M3 gate and unusable everywhere else.

### Should-fix

- **S-1** `es-ros2/src/actuator.rs:77-78` — `reorder_joint_state` does
  `state.position.get(idx).copied().unwrap_or(0.0)`. `sensor_msgs/JointState` explicitly allows
  `position`/`velocity`/`effort` to be empty or short, so a driver publishing names and positions
  but no velocities feeds a fabricated `qd = [0.0; NJ]` into `SafetyPlane::observe_state`, and a
  short `position` fabricates a joint angle. The module's own doc (`:61-64`) and design note 4.5
  say the opposite: "a partial state never reaches `SafetyPlane::observe_state`". The test
  (`:107`) only covers a missing *name*.
- **S-2** `es-ros2/src/hil/link.rs:250-253` — an accepted `Hello` sets `peer` and resets
  `last_seq` to that datagram's `seq`, but `session_id` is computed once in `bind` (`:98`) and
  never regenerated. A recorded `Hello` plus the recorded `Command`s of the same session therefore
  replay onto a live plane, defeating the only anti-replay mechanism the link has. Design note 7.7
  says "spoofed commands must not reach the plane". One line: draw a fresh `session_id` per
  accepted `Hello`.
- **S-3** CI never re-runs the es-ros2 golden provenance. `.github/workflows/ci.yml:113-127` sets
  `ES_PYTHON` for three other crates and its SKIP guard (`:124`) covers the same three; `:159-164`
  sets `ES_ROS2_ENV` for `rmw_zenoh_interop` alone. `gen_goldens` and `gen_camera_goldens` therefore
  SKIP on every runner, and since no reason contains a GPU word, `xtask/src/main.rs:37`
  (`is_gpu_skip`) ignores them and `cargo xtask ci` is green: 22 camera goldens, 10 CDR goldens and
  `rihs01.json`/`gid.json` unchecked against their oracles anywhere in automation — the hole M4's
  S-7 closed for the GPU crates. W1c also *measured* that `cv-bridge`/`image-geometry` co-install
  with the W1b prefix, so the CI comment at `:150-152` is out of date.
- **S-4** `es-ros2/src/camera.rs:463-494` — the ROI is never bounds-checked against the calibration
  resolution: `roi = { x_offset: 10_000, width: 64, height: 64 }` on a 640×480 `CameraInfo` goes
  straight into `ImageSpec::cropped` (`es-ir-types/src/image.rs:174`), which subtracts the origin
  from `cx` unconditionally, yielding a spec for a rectangle outside the sensor. Only
  `check_declared` catches it, and only when a declared spec exists. `:469-474` also folds a
  zero-dimension ROI into `CAM-006`, whose design-note meaning is "not divisible by binning".
- **S-5** `es-ros2/src/error.rs:198` — `NotCalibrated` shares `CAM-008` with `DeclaredMismatch`, so
  "no `CameraInfo` has arrived yet" (a startup race, retry) and "this camera is calibrated for a
  different stream" (stop the line) are indistinguishable to a caller matching on the code. Two
  tests assert `CAM-008` for the former (`camera.rs:934`, `camera_ingest.rs:699`).
- **S-6** `es-ros2/src/hil/replay.rs:124-133` — a log with zero `Decision` records reports
  `identical: true` and `live_hash == replay_hash` (both are blake3 of nothing). Only `steps` tells
  them apart. The gate is non-vacuous solely because `hil_gate.rs:403-418` asserts `commands > 0`,
  `steps == GATE_TICKS` and five separate event counts by hand; `ReplayReport` itself does not
  carry that weight, and `v1_fixture_still_replays_identically` leans on a bare `steps > 0` (`:470`).
- **S-7** `Cargo.lock` is gitignored (`.gitignore:59`) while `.cargo/config.toml:7` now sets
  `incompatible-rust-versions = "fallback"`. The `zenoh = "=1.8.0"` pin (design note section 2)
  pins one crate; the ~270 transitive crates it drags in are free to resolve differently in two
  clones, and the resolver is explicitly told to fall back when a `rust-version` conflicts. That is
  a `compiler`/`runtime` input of the §5.3 hash chain. Pre-existing repo policy, newly load-bearing.

### Nit

- `hil_gate.rs:126-129` points at "the packet report's open question"; `docs/packets/M3/W1d-hil.md`
  has no such section and design note section 10 was not extended. Dangling reference.
- `camera.rs:516-525` — with `rectified = true` neither `distortion_model` nor `d` is read, so
  `CAM-004` is unreachable there. Right per ROS convention; design note 6.1's table does not say so.
- `camera_ingest.rs:497-527` names four of the twelve fields `check_declared` compares; `dtype`,
  `channels`, `camera_model`, `shutter`, `exposure`, `rate_hz`, `depth_scale`, `extrinsics` have no
  test that the right name comes back. No test combines `rectified = true` with a ROI or binning.
- `session.rs:354` compares the raw topic string before `validate_name` runs (`:303`), so `ROS2-010`
  depends on the caller spelling the topic exactly as the config does.
- `cdr.rs:114,123,133,143` — `expect` on the *write* path for a >4 GiB string or sequence.
  Unreachable from decoded data (64 MiB cap), but a panic in a module whose header promises totality.
- `hil/link.rs:180-182` counts every `recv_from` error as `rx_invalid`; the comment names only the
  oversize datagram, but a Windows `ConnectionReset` lands there too. `hil/stats.rs:82` truncates
  `as_nanos() as u64` — harmless until 2554.

## Human decisions

Each with the default I would take absent a ruling.

1. **`rational_polynomial` with a non-zero `k4..k6`** (W1c 1, design note 10.3). **Keep `CAM-004`.**
   A `RationalPolynomial` variant is an `es-ir-types` schema change under §25.3 that every
   `ImageSpec` consumer inherits; dropping the tail silently changes the projection.
2. **All-zero `r`** (W1c 2). **Treat all-zero as the identity** — ROS drivers publish it for an
   uncalibrated monocular camera and the meaning is unambiguous. `camera_ingest.rs:246` asserts
   `CAM-005` for it today, so this is a deliberate contract change, not a bug fix.
3. **`rectified = true` does not parse `d`** (W1c 3). **Keep, and say so in design note 6.1.** A
   rectified stream's `d` describes the raw image; reading it would be the error.
4. **`CAM-008` reused for "no `CameraInfo` yet"** (W1c 4). **Split it out as `CAM-010`** (S-5).
5. **ROI bounds and zero dimensions** (W1c 5). **Reject an ROI that leaves the calibration
   rectangle, and give the zero-dimension case its own message** (S-4).
6. **`EnvelopeViolationRate` on a cold start** (W1d 1). **The window must not be read before it is
   full** — B-1, and an `es-safety` decision, not a HIL one. §9.4 says nothing about a partial
   window, so a human must pin it; "rate over the last `window` steps, never tripping until
   `window` steps exist" is the reading that matches §10.3's `<= 0.01`.
7. **`es-hil` crate vs `es_ros2::hil` module** (W1d 2, design note 10.1). **Keep the module.**
   `hil_imports_no_ros_module` (`hil_gate.rs:843`) keeps the extraction a file move; a new layer-11
   crate is a §4.2 amendment for no gain today.
8. **`HilConfig.key` has no loader** (W1d 3). **W1e's `es hil` takes the `*.eshilkey` path on the
   command line.** A rig-config field would put a key path inside a file the hash chain covers.
9. **Gate 14** (design note 10.4, §28.7). **Keep it open**, `Target / Status: unverified`. W1d
   proves the host half and says so in `replay.rs:9-11`.
10. **Mode C** (design note 10.5). **Cut from v1.0.** `ROS2-002` already rejects it by name.
11. **HIL key rotation** (design note 10.6). **Defer** while the default bind is loopback; revisit
    with S-2.
12. **zenoh in the PR tier** (design note 10.2). **Leave it and measure.** The loopback suite is
    21.33 s here on a warm build; nobody has timed the cold job against §26.2's 10 minutes.
    `Target / Status: unverified`.
13. **`Cargo.lock`** (S-7). **Commit it.** The workspace ships a binary and claims bitwise
    reproducibility; the MSRV fallback resolver makes an unpinned tree strictly worse.

## Scope and invariants

All four commits stayed inside their packets' `context`, with the one deviation W1c declared and
explained (`tests/gen_goldens.rs`, one line skipping `camera/`). No `unsafe` in the crate. No
`HashMap`/`HashSet`: the encoding table is a 12-entry linear scan (`camera.rs:113`) and joint
reordering a `position()` scan (`actuator.rs:74`). No float time — stamps are `i128`
(`camera.rs:691-734`), tick binning `u64` (`hil/core.rs:140-144`), and `hil_imports_no_ros_module`
proves `Instant`/`SystemTime` appear only in `link.rs`/`stats.rs`. No new trait (INV-17):
`Box<dyn Write + Send>` is `std`'s (`hil/log.rs:256`), dispatch is an enum. INV-12/INV-13 hold —
the only thing leaving `HilCore` is a `SafeAction`, `tick` returns no `Result`,
`ActuatorPublisher::send` takes only a `SafeAction`, and the one test needing room widened the
envelope. INV-14 holds: `camera.rs` writes an intrinsic only at `derive_spec`'s `k`/`p` indexing,
every size change is `cropped`/`resized` with `rescale = true`. Goldens were added in W1a/W1b/W1c
and never re-touched (three commits over `tests/golden/ros2/`, all additions).

## Verdict

**M3 W1 gate: passed, with one blocker that belongs to `es-safety`.** The ROS 2 boundary and the
camera path are the best-oracled work in the repo after the GPU tier: nothing in `camera_ingest.rs`
computes an expected value, every intrinsic is `image_geometry`'s and every YUV byte is both
OpenCV's and `cv_bridge`'s, and `5f2a0dc` shows the right instinct — when the reference check turned
out to be judging uninitialised alignment padding it was narrowed to what the reference actually
decides, and a mutation (one flipped stamp bit) was shown to fail it. The HIL gate is real: a
genuine loopback UDP run with loss, reordering, a `NaN` and a heartbeat gap replays byte-identically,
and it cannot pass vacuously because the test asserts `commands > 0` plus five distinct plane events
before it believes the equality; what it does *not* prove is written in the code, not only in the
packet. B-1 is not W1's fault — W1d hit it, could not touch `es-safety`, widened the envelope as
INV-12 requires and wrote the interaction down — but it leaves a §9.4 watchdog that latches any
deployment into permanent fallback on its first dirty step, untested in the crate that owns it. The
rest is trust-boundary polish: a joint-state reorder that fabricates zeros, a `Hello` that resets
the replay counter, and a CI job where every es-ros2 oracle SKIPs into green.
